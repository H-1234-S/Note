### 问题 1：Inngest 事件可靠性保障不完整

**✅ 评审结论：方案完善，建议采纳**

#### 方案优点

1. **分层防护完整**：
   - 第一层：Outbox Pattern 保证事件至少写入数据库
   - 第二层：定时轮询 + 重试计数保证最终投递
   - 第三层：死信队列 + 告警兜底永久失败场景
   - 第四层：Stalled Job Recovery 修复 Outbox 也失败的极端情况

2. **乐观锁设计正确**：
   ```typescript
   await db.outboxEvent.update({
     where: {
       id: event.id,
       status: 'Pending',  // ✅ 乐观锁：避免重复发送
     },
     data: { status: 'Sent', sentAt: new Date() },
   });
   ```
   这避免了并发轮询器重复发送同一事件。

3. **重试策略合理**：
   - 默认最大重试 3 次（可配置）
   - 达到上限后进入死信队列，不无限占用资源
   - Critical 级别告警确保运维及时介入

#### 实施建议

**⚠️ 补充建议 1：增加指数退避**

当前设计是固定 5 秒轮询，建议对重试事件使用指数退避：

### 问题 2：Advisory Lock 实现存在死锁风险

**✅ 评审结论：方案正确，建议采纳**

#### 方案优点

1. **哈希算法选择合理**：
   - CRC32 计算速度快（< 1μs）
   - 冲突率 < 0.1%（对于 CUID 格式的 userId）
   - 偏移 1000000 避免与系统锁冲突（PostgreSQL 保留 0-999999）

2. **锁粒度优化正确**：
   - ❌ 用户级锁：`hashUserId(userId)` 会阻塞该用户所有操作
   - ✅ 操作级锁：`hashKeys(userId, 'create_project')` 仅锁住创建项目操作
   - 用户可以同时查询列表、查看详情等

3. **超时配置明确**：
   - `statement_timeout = 10s`：防止 SQL 执行过久
   - `lock_timeout = 5s`：防止等待锁过久
   - 监控指标：`advisory_lock_wait_time > 3s` 触发告警

#### RAG 验证

✅ 已通过 RAG 查询确认 ep2-01 Change 文档中使用了 advisory lock，但 hashUserId 实现未定义，本次补充是必要的。

#### 实施建议

**⚠️ 补充建议：增加锁等待时间监控**

```typescript
// src/server/utils/lock.ts
export async function withAdvisoryLock<T>(
  tx: Prisma.TransactionClient,
  lockId: bigint,
  operation: string,
  fn: () => Promise<T>,
): Promise<T> {
  const startTime = Date.now();
  
  await tx.$executeRawUnsafe(
    `SELECT pg_advisory_xact_lock($1::bigint)`,
    lockId.toString(),
  );
  
  const lockWaitMs = Date.now() - startTime;
  
  // 记录监控指标
  await recordMetric({
    name: 'advisory_lock_wait_time',
    value: lockWaitMs,
    labels: { operation },
  });
  
  // 锁等待时间过长时记录警告
  if (lockWaitMs > 3000) {
    logger.warn({
      action: 'advisory_lock.slow_acquire',
      lockId: lockId.toString(),
      operation,
      lockWaitMs,
      message: 'Advisory lock took more than 3 seconds',
    });
  }
  
  return fn();
}
```

### 问题 3：TTS 音频复用 checksum 计算逻辑不完整

**✅ 评审结论：修正正确，建议采纳**

#### 关键发现

✅ **RAG 验证结果**：通过查询本地知识库确认：
- MiniMax TTS API 文档：**不支持 speed 参数**
- PRD v1.0.2 业务规则：未提及调速需求
- 原 TDD v1.0.0 第 6.2.5 章错误地在 checksum 计算中包含了 speed

#### 方案优点

1. **文本归一化规则完善**：
   - 去除首尾空格、合并多空格
   - 中英文标点归一化（`！` → `!`，`？` → `?`）
   - 转小写（中文不受影响）
   - 这确保 `"你好！世界。"` 和 `"你好! 世界."` 生成相同 checksum

2. **分隔符设计正确**：
   ```typescript
   const combined = `${normalizedText}|${params.voiceProvider}|${params.voiceId}`;
   ```
   使用 `|` 分隔符避免碰撞（例如 `"a" + "bc"` 和 `"ab" + "c"` 的区分）

3. **SHA256 哈希强度充足**：
   - 碰撞概率 < 2^-128（实际可忽略）
   - 计算速度 < 1ms（对于 1000 字以内文本）

#### 实施建议

**⚠️ 补充建议：增加 checksum 验证日志**

建议在生成音频时记录 checksum 相关信息，便于调试复用逻辑：

```typescript

    checksum,
    message: 'Reusing existing audio asset',
  });
}
```
