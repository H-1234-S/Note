## 🚨 P0 级问题（必须修复）

### 问题 1：缺少独立的 Feature Breakdown 章节

**要求原文：**
```markdown
# 3. Feature Breakdown

对于每个 Feature：
## Feature Name
### Goal
### User Value
### Technical Scope
### Dependencies
### Risks
### Recommended Order
```

**现状：**
- 文档第 2 章有 Epic Tree，但没有独立的 **Feature Breakdown** 章节
- Feature 的详细信息（Goal、User Value、Technical Scope 等）完全缺失
- Epic 和 Feature 的关系不够清晰

**影响：**
- Tech Lead 和 Architect 无法快速了解每个 Feature 的业务价值
- 无法评估 Feature 之间的优先级
- 不符合模板的核心要求

**修复方案：**
在第 2 章 Epic Tree 之后，新增第 3 章 Feature Breakdown，格式如下：

```markdown
## 3. Feature Breakdown

### Epic 2: 项目管理与 Dashboard

#### F2.1: 项目 CRUD API

**Goal**: 实现项目的完整生命周期管理 API

**User Value**: 
用户可以创建、查看、管理自己的视频项目，无需手动管理文件和状态

**Technical Scope**:
- tRPC routers: project.createAndGenerate, project.list, project.getById, project.delete
- Service 层: 业务逻辑、额度校验、并发限制
- Repository 层: 数据库操作封装

**Dependencies**:
- Epic 1: 数据库 schema 已完成
- Epic 1: tRPC 框架已配置

**Risks**:
- 并发限制可能影响用户体验（多设备登录场景）
- 额度检查性能问题（高并发时数据库查询）

**Recommended Order**:
1. create API（核心功能）
2. list API（查看项目）
3. getById API（详情页）
4. delete/cancel/retry API（管理操作）

---

#### F2.2: 创建项目页面
...（以此类推）
```

**现状：**
文档中有 3 处描述 Phase 和 Change：
- 第 1 章「优化后的实施策略」：Phase 1-6 概述
- 第 2 章「详细 Change Breakdown」：Phase 1-6 详细描述
- 第 4 章「Change Breakdown」：又一次 Phase 1-6 详细描述

**问题分析：**
- 内容重复，读者需要在多个章节之间跳转
- 不符合模板的「Single Source of Truth」原则

3. 将第 2 章的概述内容移到第 4 章的各 Phase 开头

**标准结构：**

## ⚠️ P1 级问题（强烈建议修复）

### 问题 3：违反垂直切片原则

**模板要求：**
> 优先：用户功能 ↓ 数据库 ↓ API ↓ 前端 ↓ 测试 作为一个完整 Change。
> 禁止：数据库 Change、API Change、前端 Change 按技术层拆分。

**现状问题：**
文档采用了典型的"水平切片"（按技术层拆分）：

```
Phase 1: 后端 API 实现
├── api-01-project-crud (API 层)
├── api-02-quota-validation (API 层)
└── api-03-project-actions (API 层)

Phase 5: 前端完善
├── ui-01-generate-tab-integration (前端层)
├── ui-02-history-tab-integration (前端层)
└── ui-03-progress-view (前端层)
```

**为什么这是问题：**
1. **无法尽早验证端到端流程** - API 做完后要等到 Phase 5 才能前端集成
2. **增加返工风险** - 前端集成时可能发现 API 设计不合理
3. **延迟用户价值交付** - 用户要等到 Phase 5 才能真正使用功能
4. **AI Agent 难以理解完整功能** - 需要跨 Phase 理解才能知道完整流程

**特殊情况说明：**
文档中提到"保持现有 UI 架构不变"，这是一个合理的工程决策。
但即便如此，也应该将 API 实现和前端集成作为**一个 Change**，而不是分成两个 Phase。

**修复建议（两个方案）：**

**方案 A：严格垂直切片（推荐）**

```markdown
### Phase 1: 核心用户流程

#### Change: `project-create-flow`
**Goal**: 用户可以创建项目并在 Dashboard 查看（端到端）

**Scope**:
- Database: Project + GenerationJob 表（已有）
- API: project.createAndGenerate mutation
- Frontend: GenerateTab 集成 API + 提交反馈
- Tests: E2E 测试（创建 → 查看）

**Files**:
- src/server/routers/project.ts (API)
- src/server/services/project.service.ts (业务逻辑)
- src/components/main-app/GenerateTab.tsx (前端集成)
- tests/e2e/create-project.spec.ts (测试)

**Acceptance Criteria**:
Given: 用户登录
When: 在 GenerateTab 输入文本并提交
Then: 项目创建成功，跳转到 HistoryTab 显示新项目

---

#### Change: `project-list-flow`
**Goal**: 用户可以查看和管理项目列表（端到端）

**Scope**:
- API: project.list, project.delete
- Frontend: HistoryTab 集成 API + 筛选 + 删除操作
- Tests: E2E 测试（列表 → 筛选 → 删除）

**Files**:
- src/server/routers/project.ts (API)
- src/components/main-app/HistoryTab.tsx (前端集成)
- tests/e2e/project-list.spec.ts (测试)
```

**方案 B：保持现有拆分但说明理由**

如果项目组决定保持当前拆分，需要在文档中明确说明：

```markdown
## 垂直切片原则的例外说明

本项目采用"API 先行，前端后集成"的策略，原因如下：

1. **UI 架构已完成**: MainApp.tsx、GenerateTab、HistoryTab 已有完整 UI 结构
2. **前端工程师未就位**: Phase 1-4 期间只有后端工程师，Phase 5 前端工程师加入
3. **API 可独立测试**: 通过 tRPC Playground 和 Postman 验证 API 正确性
4. **风险可控**: 前端集成前会进行 API 设计 Review

**缓解措施**:
- 每个 API 完成后立即进行 Contract Review（Tech Lead + 前端 Lead）
- Phase 1-4 结束时，邀请前端工程师试用 API 并提出改进建议
- 保留 API 版本兼容性，允许前端集成时微调

**交付节奏**:
- Phase 1: 后端 API Ready → API Review → 前端可开始集成
- Phase 5: 前端集成 → E2E 测试 → 完整功能交付
```

### 问题 4：Change 命名不符合规范

**模板要求：**
> Change ID 格式：domain-feature
> 例如：auth-registration、workspace-member-invite、billing-subscription

**现状问题：**
当前命名采用 `技术层-序号-描述` 格式：

```
api-01-project-crud          (技术层前缀)
ui-01-generate-tab-integration
remotion-01-foundation
tts-01-provider-interface
```

**为什么需要修改：**
1. **不符合 DDD 原则** - 应该以业务领域（Domain）命名，而不是技术层
2. **序号无意义** - `01/02/03` 不传达任何业务信息
3. **跨团队协作困难** - 产品经理看到 `api-01` 无法理解是什么功能

**修复建议：**

按照文档第 1.1 节定义的 5 个 Domain 重新命名：

| Domain | 现有命名 | 建议命名 | 说明 |
|--------|---------|---------|------|
| Project | api-01-project-crud | `project-lifecycle-management` | 项目生命周期管理 |
| Project | api-02-quota-validation | `project-quota-control` | 项目额度控制 |
| Project | ui-01-generate-tab-integration | `project-create-ui` | 项目创建界面 |
| Project | ui-02-history-tab-integration | `project-dashboard-ui` | 项目仪表板 |
| Content | ai-01-storyboard-types | `content-storyboard-schema` | 内容分镜 Schema |
| Content | ai-02-llm-provider | `content-llm-integration` | LLM 集成 |
| Content | ai-03-inngest-storyboard | `content-storyboard-generation` | 分镜自动生成 |
| Asset | tts-01-provider-interface | `asset-tts-provider` | TTS 提供者 |
| Asset | tts-02-r2-storage | `asset-storage-service` | 资产存储服务 |
| Asset | tts-03-inngest-audio | `asset-audio-generation` | 音频自动生成 |
| Render | remotion-01-foundation | `render-foundation-setup` | 渲染基础搭建 |
| Render | remotion-02-templates | `render-ppt-templates` | PPT 模板库 |
| Render | remotion-03-worker | `render-worker-service` | 渲染 Worker 服务 |
| Render | remotion-04-integration | `render-video-composition` | 视频合成 |

**命名规范：**
- 格式：`{domain}-{feature-name}`
- domain: 5 个 Domain 之一（project/content/asset/render/auth）
- feature-name: 2-3 个单词，描述功能而非技术实现
- 使用连字符 `-` 连接，全部小写
- 避免技术术语（api/ui/inngest），使用业务术语

### 问题 6：Business Context 不够突出

**模板要求：**
> ## Business Context
> 解决什么问题。

**现状问题：**
很多 Change 的 Goal 是技术目标，缺少业务视角。

**示例：**

❌ **现状：**
```markdown
**Goal**: 实现 project.createAndGenerate tRPC mutation
```

✅ **应该改为：**
```markdown
**Business Context**: 
用户需要将文字内容快速转化为视频，但手动制作视频耗时且需要专业技能。
当前系统缺少项目管理能力，用户无法保存和追踪生成进度。

**Goal**: 
实现项目创建 API，支持：
- 文本输入（最大 5000 字）
- 参数配置（比例、时长、语音）
- 额度校验（免费用户每日 1 次）
- 异步任务触发（发送 Inngest 事件）

用户价值：一键创建视频项目，3 分钟内自动完成生成。
```

**建议：**
为每个 Change 添加 Business Context 章节，回答：
1. 用户遇到了什么问题？
2. 这个 Change 如何解决这个问题？
3. 交付后用户能获得什么价值？
