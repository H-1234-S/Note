
> 定位：一个从零自研的 **BaaS（Backend-as-a-Service）平台**，对标 Supabase。
> 用户创建「组织 → 项目」后，平台自动为其提供 **独立数据库 Schema、自动 REST API、Realtime 实时订阅、在线建表、SQL 编辑器、对象存储、独立认证体系**。

## 一、亮点（Highlights）

### 亮点 1 ｜ Realtime 实时订阅：打通「Postgres 触发器 → WebSocket 房间」全链路 ★主推

**做了什么**
实现端到端的实时数据订阅能力：用户在控制台打开某张表的开关后，任何对该表的 `INSERT / UPDATE / DELETE` 都会在毫秒级推送到所有订阅端，前端实时渲染事件流。

**完整链路（面试可直接画）**
```
用户写入数据
  → Postgres AFTER INSERT/UPDATE/DELETE 触发器（动态创建的 PL/pgSQL 函数）
  → pg_notify('project_xxx_table', payload) 广播
  → 服务端 Neon Serverless WebSocket 直连 LISTEN 收到 notification
  → 回调 → Socket.IO 房间 project:{projectId}:table:{tableName} 广播
  → 前端 socket.io-client 收到 event，写入事件流
```

**关键工程实现**
- **动态生成触发器**：通过 DDL 动态创建 `xxx_notify()` 函数 + `AFTER INSERT OR UPDATE OR DELETE ... FOR EACH ROW` 触发器，用 `json_build_object` + `row_to_json` 构造包含 `type / table / record / oldRecord / timestamp` 的标准化事件载荷。
- **连接复用**：服务端用 `Map<channel, { client, callbacks: Set }>` 管理 LISTEN 连接——**同一频道 N 个订阅者共享 1 条数据库长连接**，避免订阅数一多就把数据库连接打满。
- **引用计数式释放**：`unsubscribe` 时从 Set 移除回调，Set 为空才 `UNLISTEN` + `client.end()` 并删除 Map 条目；`onModuleDestroy` 统一关闭所有连接。
- **连接即鉴权**：WebSocket 在 `handleConnection` 阶段校验 JWT（因 `handleConnection` 早于 Guard 触发），校验角色白名单后 `join(project:xxx)`，实现租户级房间隔离。
- **前端断线重连**：基于 `useRef` 保存已订阅表快照，`connect` 事件触发后自动重新 `emit(SUBSCRIBE)`，保证断网恢复后订阅不丢。

**价值**：把「数据库变更 → 前端实时感知」的链路完全自研打通，无需轮询、无需第三方消息中间件，复用了 Postgres 原生能力，架构轻量。

**面试加分点**：能讲清 `pg_notify` 的 payload 有 **8000 字节上限**（大行数据要只推主键、让客户端回查）、`LISTEN` 必须在**同一个连接**上执行、以及为什么这里不能用连接池。

### 亮点 2 ｜ 自动 REST API：把 URL 查询串编译成安全 SQL ★主推

**做了什么**
对标 PostgREST，实现「给定一张表，自动暴露一套 REST 接口」的能力，并把 URL 查询参数解析、编译成 SQL。

```
GET /rest/posts?select=id,title&age=gte.18&order=created_at.desc&limit=20&offset=40
```

**关键实现**
- **查询解析器**：区分「保留参数」（`select / order / limit / offset`）与「过滤参数」，把 `字段=操作符.值` 拆解为过滤子句；操作符走**白名单**（`eq/neq/gt/gte/lt/lte/like/ilike/is`）。
- **主键动态发现**：通过 `information_schema` 的 `table_constraints` + `key_column_usage` 联表查询，动态拿到表的主键列，支撑 `PATCH / DELETE` 按行定位。
- **值的安全格式化**：按类型推断输出——字符串做单引号转义（`'` → `''`）、数字/布尔直接输出、对象序列化为 `::jsonb`、`IS` 操作符特殊处理为 `NULL / NOT NULL`。
- **注入防御**：所有**标识符**（表名、列名、排序字段）在拼接前统一走正则白名单 `^[a-zA-Z_][a-zA-Z0-9_]*$`，从源头杜绝标识符注入。

**价值**：让用户「建完表即可用」，是 BaaS 平台的核心体验，也是这个项目区别于普通 CRUD 后台的关键。

---

### 亮点 3 ｜ 多租户架构与「双轨」认证体系 ★主推

**做了什么**
设计并落地两套彼此独立的认证体系，以及一套 Schema 级多租户隔离方案。

**（1）多租户隔离：Schema-per-Project**
- 创建项目时动态 `CREATE SCHEMA proj_xxxx`，所有业务表都落在项目自己的命名空间下（`"${schema}"."${tableName}"`）。
- SQL 编辑器执行用户 SQL 前，先 `SET LOCAL search_path TO "proj_xxx", public`，保证用户只能看到自己的表。
- 跨租户越权防护：项目密钥里携带的 `projectId` 必须与 URL 中的 `projectSlug` 对应，否则 `403 Forbidden`。

**（2）平台侧认证（给控制台用）**
- **双 Token 机制**：`accessToken`（15 分钟）+ `refreshToken`（7 天），均写入 `httpOnly + SameSite=Lax + 生产环境 Secure` 的 Cookie，防 XSS 窃取、防 CSRF。
- **Guard 链**：`JwtAuthGuard`（验签）→ `OrgRoleGuard`（校验用户在组织内的角色 `admin / developer`），实现 RBAC。
- 密码 `bcrypt`（cost 12）加盐哈希；注册即自动创建个人组织并绑定为 admin。

**（3）项目侧认证（给用户的项目用，对标 Supabase Auth）**
- **懒建表**：项目首次使用认证时才 `CREATE TABLE IF NOT EXISTS auth_users`，不浪费资源。
- **每项目独立密钥**：每个项目持有自己的 `auth_jwt_secret`，签发互不影响的用户 Token。
- 支持 **邮箱密码、魔法链接（Resend 邮件，15 分钟过期）、Google / GitHub OAuth** 三种登录方式。
- **项目密钥**：`anon`（只读）与 `service_role`（读写）两级，本质是 JWT，用 `PROJECT_JWT_SECRET` 统一签发。

**价值**：一套平台同时承载「平台自身多租户权限」与「用户项目的独立认证」，边界清晰、互不污染。

---

### 亮点 4 ｜ 在线建表（动态 DDL）与 SQL 编辑器

**在线建表 / 改表**
- 把表单配置编译成 `CREATE TABLE`：类型映射（`text/integer/bigint/boolean/timestamptz/uuid/jsonb/numeric`）、单主键 / 复合主键、`GENERATED ALWAYS AS IDENTITY` 自增、`NOT NULL`、`DEFAULT`（白名单 `now() / gen_random_uuid() / current_timestamp`）、外键约束。
- `ALTER TABLE ADD / DROP COLUMN`；删除表用 `DROP TABLE IF EXISTS` 保证幂等。
- 通过 `information_schema` 反射表结构（列、可空性、默认值、主键、外键），驱动前端表格展示。
- 更新行数据时使用 Drizzle 的 `sql.identifier()` **参数化标识符**，与手写拼接形成对比，体现对注入面的分层处理。

**SQL 编辑器**
- Monaco Editor **动态导入 + `ssr:false`**，避免重型编辑器拖累首屏与 SSR。
- 通过 Neon Serverless 的 **HTTP 事务** 批量执行：`SET LOCAL search_path` + 用户 SQL 原子提交，既做隔离又保证要么全成功要么全失败。
- 安全约束：**单语句校验**（按分号切分，多于一条报错）+ **危险语句黑名单**（`DROP DATABASE / DROP SCHEMA / TRUNCATE`）。
- 记录查询历史（SQL、耗时、影响行数），支持一键回填重跑。

### 亮点 5 ｜ Monorepo 工程化与自研 SDK

- pnpm workspace 统一管理 `apps/*` 与 `packages/*`，`workspace:*` 本地引用，`@novabase/types`、`@novabase/constants` 前后端共享一份定义（类型即契约）。
- 自研 `novabase-js` SDK，用 **tsdown** 打包出 **ESM + CJS 双格式**，`exports` 字段做条件导出，`types` 指向 `.d.ts`，可被 npm 消费。
- **链式查询构建器**：`client.from('posts').select('id,title').eq('id', 1).order('created_at','desc').limit(10)`，内部把链式调用编译成上一节的 REST 查询串。
- **Thenable 设计**：`QueryBuilder` 实现 `then()`，使其**既可 `await` 也可 `.execute()`**，API 手感接近 Supabase 官方 SDK。
- 前端状态处理：表格编辑器多标签页场景引入**请求代际计数器**（`tableFetchGenRef`）丢弃过期响应，避免快速切表时旧请求覆盖新数据（典型竞态）。

## 二、难点（Difficulties）

### 难点 1 ｜ Serverless Postgres 上的 Realtime 长连接治理 ★主推

**问题现象**
本地一切正常，但线上/空闲一段时间后实时推送静默失效；服务端偶发进程崩溃。

**根因分析（三层）**
1. **Neon 空闲挂起**：Neon 对约 5 分钟无活动的计算实例会 `suspend`，挂起时代理会**直接切断 WebSocket**，LISTEN 连接失效。
2. **未处理的 error 事件**：Neon 客户端断连会触发 `'error'` 事件，若没有注册监听器，Node 会视为未捕获异常并**终止进程**。
3. **连接池不可用**：`LISTEN/NOTIFY` 是**连接级**语义，必须走直连；而 Neon 默认给的是带 `-pooler` 的连接串，且带 `sslmode / channel_binding` 等参数。

**解决方案**
- **连接串改造**：拿到连接串后去掉 `-pooler`，清洗掉 `sslmode / channel_binding` 等不被 WebSocket 直连接受的参数，得到可用于 LISTEN 的直连串。
- **错误兜底**：为每条 LISTEN 连接注册 `error` 监听，捕获后从 `listeners` Map 中移除该频道，使后续订阅能**重新建连**；同时避免进程崩溃。
- **前端自愈**：客户端在 `connect` 事件里根据 ref 快照重新订阅，覆盖「服务端重建连接」与「网络抖动」两种场景。
- **资源回收**：`UNLISTEN` + `client.end()` + Map 清理 + `onModuleDestroy` 兜底，避免连接泄漏。

**面试追问 & 答题要点**
- *为什么不用轮询 / Redis Pub-Sub？* → 复用 Postgres 原生能力，零额外中间件；轮询有延迟与空转成本。若未来多实例部署，需要把 `pg_notify` 桥接到 Redis/Kafka 做扇出（这是当前单实例架构的已知演进方向）。
- *payload 大小限制？* → `NOTIFY` payload 上限 8000 字节，大行应只推主键让客户端回查。
- *如何水平扩展？* → 引入消息中间件做跨实例广播，或按 project 分片路由。

---

### 难点 2 ｜ 动态 SQL 场景下的注入防御（标识符无法参数化） ★主推

**问题现象**
表名、列名、排序字段这些**标识符无法用占位符参数化**（占位符只能绑定「值」），必须拼接进 SQL 字符串，天然存在注入面。

**分析与方案**
- **分层防御**：
  - 值 → 类型化格式化（字符串单引号转义、数字/布尔直出、对象 `::jsonb`、`IS NULL` 特判）。
  - 标识符 → 拼接前**统一正则白名单** `^[a-zA-Z_][a-zA-Z0-9_]*$`，非法直接 `400`。
  - 更现代的写法 → 用 Drizzle `sql.identifier()` 做标识符参数化（项目里两种方式并存，可对比说明）。
- **黑名单兜底**：SQL 编辑器对 `DROP DATABASE / DROP SCHEMA / TRUNCATE` 等危险语句直接拒绝，并限制**单语句执行**，防止用户用分号拼接多语句绕过。
- **隔离兜底**：即便绕过，最坏也只能影响自己项目的 Schema（`search_path` 限定）。

**诚实面对残留风险（面试加分）**
代码中仍留有 `// TODO: SQL Verification`、Realtime 处的 `// BUG: SQL 注入？？？` 等标注，说明**当前是「白名单 + 黑名单 + 租户隔离」的多层缓解，而非完整的 SQL 解析级校验**。更彻底的方案是引入 AST 解析（如 `pgsql-ast-parser`）或把权限收敛到数据库层（RLS + 最小权限角色）。

**面试追问 & 答题要点**
- *为什么值能参数化、标识符不能？* → 参数化是「结构先编译、值后填充」，值只能落在 `?` 的坑里当数据；标识符是 SQL 结构的一部分，改结构必须改语句文本。
- *怎么做到真正安全？* → RLS（Row Level Security）+ 为每个租户建独立数据库角色，把安全边界下沉到数据库。

---

### 难点 3 ｜ 多租户数据隔离与越权防护

**问题现象**
所有租户共用一个物理数据库，如何保证「A 项目绝对看不到 B 项目的数据」？

**方案**
- **命名空间隔离**：Schema-per-Project，所有 SQL 强制带 `"${schema}"."${tableName}"` 前缀。
- **执行期隔离**：SQL 编辑器用 `SET LOCAL search_path`（`LOCAL` 保证只作用于当前事务）。
- **身份与资源绑定**：项目密钥 JWT 内含 `projectId`，服务端校验其与 URL 的 `orgSlug/projectSlug` 是否一致，不一致直接 `403`。
- **双层 RBAC**：平台侧按组织角色（admin/developer）鉴权；项目侧按 anon/service_role 区分读写。

**面试追问**：*为什么选 Schema 隔离而不是「每项目一个库」或「加 tenant_id 列」？* → 一个库内多 Schema 兼顾**隔离强度**与**运维成本**；`tenant_id` 方案隔离弱（易漏加 where 条件）、独立库成本高。

---

### 难点 4 ｜ 前端复杂交互下的竞态与一致性

**问题现象**
表格编辑器支持多标签页、快速切换、动态刷新，容易出现「旧请求返回晚、覆盖新数据」的竞态。

**方案**
- **请求代际计数器**：每次发起某表的请求 `gen + 1` 并记录，响应回来时比对 `gen`，不一致则丢弃，从根上解决乱序覆盖。
- **Socket 重连补订阅**：用 `useRef` 保存订阅快照，重连后重放。
- **服务端驱动初始数据 + 客户端增量**：RSC 首屏注入初始数据，交互后走客户端请求，减少瀑布流。
- **重型依赖懒加载**：Monaco 动态导入跳过 SSR。

---

### 难点 5 ｜ 工程化细节：Node 出站代理与 `fetch` 版本一致性

**问题现象**
配置出站代理后，所有带 body 的服务端请求（UploadThing 的元数据登记/回调、邮件、数据库 HTTP）全部失败，报 `invalid content-length header (UND_ERR_INVALID_ARG)`。

**根因**：`setGlobalDispatcher` 用的 `undici@8` 的 dispatcher，而 Node 内建 `fetch` 走的是另一套 undici，两者对 `content-length` 的校验规则不一致。

**方案**：启用代理时，把 `globalThis.fetch` **显式替换为同一个 undici 版本导出的 `fetch`**，保证 dispatcher 与 fetch 同源；并尊重 `NO_PROXY`（`localhost` 直连，OAuth 回调不打代理），代理未配置时完全不启用，避免硬编码代理地址导致环境错配。

**价值**：体现了对 Node 网络栈、代理与多版本依赖冲突的排障能力。

## 四、面试高频追问速查

| 追问 | 答题要点 |
| --- | --- |
| Realtime 为什么不用 WebSocket 直连数据库？ | 浏览器无法直连 Postgres；服务端用 LISTEN 桥接，Socket.IO 对前端屏蔽数据库细节，便于鉴权与房间隔离。 |
| 多实例部署后 Realtime 会怎样？ | 当前 `pg_notify` 只到本实例的连接，多实例需引入 Redis/Kafka 做跨实例扇出（已知演进点）。 |
| 怎么防止 SQL 注入？ | 值参数化 + 标识符白名单正则 + 危险语句黑名单 + 单语句限制 + 租户 Schema 隔离，多层缓解。 |
| 为什么用 Drizzle 而不是 Prisma？ | Drizzle 更贴近 SQL、支持 `sql.identifier()` 参数化、原生 `execute` 执行任意 SQL，适合「动态表结构」的 BaaS 场景。 |
| 双 Token 如何做到无感刷新？ | 401 拦截 → 用 refreshToken 换新 accessToken → 重放原请求；refresh 也失效才跳登录。 |
| 前端如何避免竞态？ | 请求代际计数器（gen 比对）丢弃过期响应；Socket 重连用 ref 快照重放订阅。 |
| 项目最大的技术难点？ | Realtime 在 Serverless Postgres 上的长连接可靠性治理（挂起断连、连接复用、进程稳定性）。 |

## 五、可继续打磨的方向（体现技术判断力）

- Realtime 多实例扇出（Redis/Kafka 桥接）与断线补偿（增量拉取补齐）。
