# 越界访问

>  Schema-per-Project 实现多租户隔离，并通过设置 `search_path` 执行用户 SQL。
>  一次 SQL 请求到达服务端后，具体如何确保它只能访问当前项目的 Schema？

一个 `Project` 一个 `Schema` 一个 `Role`

``` SQL
-- 1. 建 schema（所有者是 provisioner，不交给项目角色）
CREATE SCHEMA IF NOT EXISTS "proj_xxx";

-- 2. 建角色（不存在才建），NOLOGIN 禁止登录
CREATE ROLE "proj_xxx_usr" NOLOGIN;

-- 3. 项目角色只能进/建自己的 schema
GRANT USAGE, CREATE ON SCHEMA "proj_xxx" TO "proj_xxx_usr";

-- 4. 存量表、序列全权授予
GRANT ALL ON ALL TABLES   IN SCHEMA "proj_xxx" TO "proj_xxx_usr";
GRANT ALL ON ALL SEQUENCES IN SCHEMA "proj_xxx" TO "proj_xxx_usr";

-- 5. 以后新建的表自动授权，不用每张表补 GRANT
ALTER DEFAULT PRIVILEGES IN SCHEMA "proj_xxx"
  GRANT ALL ON TABLES, SEQUENCES TO "proj_xxx_usr";

-- 6. 关键：让 API 连接身份能 SET LOCAL ROLE 切进这个角色
GRANT "proj_xxx_usr" TO CURRENT_USER;
```

**执行环节：**

``` ts
const results = await neonSql.transaction((txn) => [
  // 第一层（唯一可靠的一层）：整个事务以项目角色身份执行，数据库内核拦截越界访问
  txn`SET LOCAL ROLE ${txn.unsafe(quoteIdentifier(projectRole))}`,
  // 第二层：只是名字解析顺序，让用户可省略 schema 前缀
  txn`SET LOCAL search_path TO ${txn.unsafe(quoteIdentifier(project.dbSchema))}`,
  // 执行用户输入的任意 SQL
  txn`${txn.unsafe(statement)}`,
]);
```

首先切换执行角色，本事务 SQL 以该**角色**执行对应语句；因为角色只能访问对应的schema

这就是能拦截住的原因，越权访问在数据库内核就被拒了，应用层无法伪造或绕过

## 如何确保无法读取 `public` Schema 中的数据？

> 若用户提交 `SELECT * FROM public.users`，数据库权限层如何确保该角色无法读取 `public` Schema 中的数据？

PostgreSQL 默认给 `PUBLIC`（所有角色的集合）授予 `public` schema 的 `USAGE`，这意味着任何角色都能看到 public 里的表

``` sql
REVOKE ALL ON SCHEMA public FROM PUBLIC;
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM PUBLIC;
REVOKE ALL ON ALL SEQUENCES IN SCHEMA public FROM PUBLIC;
```
****`provisionProjectRole`** 只给项目角色授予**它自己 schema** 的权限：

``` sql
GRANT USAGE, CREATE ON SCHEMA "proj_9f3a1c02" TO "proj_9f3a1c02_usr";
```

# 断线重连

断线自动重连其实是 Socket.io-client 实现的，我只需要补充订阅关系即可

对于断线重连后的数据补偿

> **核心：**

事件先**落盘**分配**递增 seq**，客户端记住自己收到哪一条（cursor）

断线期间的事件继续累积在 outbox，重连后从游标处重放补齐，靠 seq 判序去重做到不重不漏。

> **客户端知道该从哪补？**

用 `cursorRef` 为每张表维护 `lastSeq`，收到事件就 `updateCursor`，且**只允许单调递增**（防止乱序事件把游标推回去）

游标就是断线前的最后进度

> **怎么触发补发？**

`socket.on('connect')` 里对每个已订阅表 `emitSubscription(SUBSCRIBE, table, cursorRef.get(table))`

把游标作为 `since` 一起发到服务端，这就是 “补发请求” 本身。

> **兜底：**

全量快照，全部推送到客户端

# 身份认证

> **对于 OAuth 登录**，服务端如何校验回调请求确实对应用户发起的那次授权流程，并避免 CSRF 或登录会话被串换？

发起认证时，服务端随机生成一个state，拼接到授权url中，用户授权后，state带回回调地址，服务端只需要检验一下跟本机是否相同，不一致就拒绝

**流程：**

```
用户点击oauth进行登录

重定向到授权网页，用户授权后

请求打到本地的回调地址
```
