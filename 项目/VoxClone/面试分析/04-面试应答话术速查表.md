## 话术 1：浏览器录音 + 实时波形（考察：React Hooks 高级运用、资源管理、异步协调）

**面试官可能问**：「在你做的声音克隆项目中，录音功能有什么技术挑战吗？」

**建议回答框架**：
> 录音功能看起来简单，但在我们的场景中有一个特殊需求：**录制的同时要在 UI 上实时显示音频波形**。这里最大的挑战是 RecordRTC 和 WaveSurfer 需要**共享同一个麦克风流**。
>
> 我的做法是：先在 `startRecording` 中通过 `getUserMedia` 获取 `MediaStream` 并存储在 `useRef` 中，RecordRTC 直接消费这个流来录制 WAV 文件。然后通过一个 `useEffect`——当 `isRecording` 变为 true 且 container DOM 已挂载、stream 已就绪时——创建 WaveSurfer 实例并通过 `RecordPlugin.renderMicStream(streamRef.current)` 将**同一个流**绑定到波形插件上。
>
> 另一个重要设计是资源清理。这个 Hook 涉及 4 类资源：MediaStream 音轨、RecordRTC 实例、WaveSurfer 实例、以及一个 100ms 间隔的计时器。我把所有清理逻辑封装在一个 `cleanup` 函数中，在三种路径下复用：useEffect 的 return（组件卸载）、startRecording 的 catch 分支（权限拒绝）、以及 resetRecording（用户取消重录）。这样保证无论如何退出录音流程，麦克风都不会被泄漏占用。
>
> 还有一个细节：RecordRTC 是同步导入还是动态导入？我用了 `await import("recordrtc")` 动态导入，因为这个库只在用户点击录音时才需要，这样可以减少初始 Bundle 约 50KB。

**可能的追问**：「为什么不用 MediaRecorder API？」
> MediaRecorder 在不同的浏览器中输出的音频格式不一致（Safari 默认是 mp4，Chrome 是 webm）。我们需要统一的 WAV 格式，所以选了 RecordRTC 这个更底层的库来做精确控制。

## 话术 2：全栈类型安全（考察：架构设计、TypeScript 深度、API 层设计）

**面试官可能问**：「你们的 API 层是怎么保证类型安全的？」

**建议回答框架**：
> 我们使用 tRPC + Zod + SuperJSON 构建了全链路类型安全的 API 层。意思是：从数据库 Schema 到后端 Router，再到前端 React 组件，任何一个环节的字段名变更都会在**编译时**报错，而不是运行时才发现。
>
> 具体做法：后端用 Prisma 定义数据模型，tRPC Router 中写 query/mutation，输入用 Zod schema 校验。前端使用 `inferRouterOutputs<AppRouter>` 从后端路由**自动推导**出类型——比如语音列表的类型 `TTSVoiceItem` 就是通过 `inferRouterOutputs<AppRouter>["voices"]["getAll"]["custom"][number]` 推导出来的。后端改 Prisma schema → 前端如果引用了被删改的字段，TypeScript 直接编译报错。
>
> 另外，在 SSR 层面我们实现了"服务端预取 → 脱水 → 客户端水合"的完整链路。Server Component 中用 `prefetch(trpc.voices.getAll.queryOptions())` 触发预取，通过 `<HydrateClient>` 把序列化后的数据注入客户端。客户端组件使用 `useSuspenseQuery` 时直接命中缓存，用户看到页面时数据已就绪，不需要额外的 loading 状态和网络请求。
>
> 序列化方面，我们使用 SuperJSON 而非 JSON.stringify——因为 SuperJSON 支持 Date 对象的序列化/反序列化，不然 createdAt 等字段在脱水/水合过程中会丢失类型信息。

**可能的追问**：「为什么不直接用 REST + OpenAPI 生成类型？」
> tRPC 的优势在于类型推导是**编译时自动完成的**，不需要运行代码生成工具。每次修改后端代码，前端立刻感知类型变化。如果用 REST + 代码生成，需要额外维护一个 `sync-api` 步骤，容易因为忘记运行而导致类型不一致。不过项目中确实有一个外部 API（Chatterbox TTS 引擎）用了 OpenAPI 类型生成，这是 tRPC 覆盖不到的场景。

## 话术 3：表单状态管理与精准渲染（考察：React 性能优化、状态管理方案对比）

**面试官可能问**：「这个项目的表单是怎么做的？为什么不用 React Hook Form？」

**建议回答框架**：
> 我们用的是 TanStack React Form，主要原因有两个：一是它和项目里已有的 TanStack React Query 来自同一生态，二是它的 `useStore(store, selector)` 精准订阅模式在性能上优于 React Hook Form 的 `watch`。
>
> 具体来说，我们的 TTS 表单有 4 个独立子组件：文本输入区、语音选择器、参数滑块面板、生成按钮。它们共享同一个表单实例但关注不同的字段。如果用 `useState` 全局管理，任何一个字段变化都会导致全部 4 个组件重渲染。我们通过 `useStore(form.store, (s) => s.values.text)` 这种 selector 模式，让文本输入区只订阅 `text`，滑块面板只订阅对应的参数，生成按钮只订阅 `isSubmitting` 和 `isValid`，实现了字段级的渲染隔离。
>
> 类型安全方面也很有意思——我们用 `formOptions` 创建一个类型令牌对象，然后通过 `useTypedAppFormContext(ttsFormOptions)` 在任意深度的子组件中获取表单实例，同时获得完整的 TypeScript 类型推导。如果你修改了表单 schema，所有使用方会立即编译报错。
>
> 还有一个实时费用预估的功能：我们用 `text.length * COST_PER_UNIT` 这个纯计算表达式直接在 JSX 中渲染，而不是通过 `useEffect` 同步到 state。因为 `text` 本身就是通过 selector 订阅的，变化时自然触发重渲染并重新计算，不需要额外的状态同步逻辑。

**可能的追问**：「有没有遇到 selector 的闭包陷阱问题？」
> TanStack React Form 的 `useStore` 内部使用 `useSyncExternalStore`，本质上是订阅外部 store 的快照，不存在闭包陷阱问题。这和 Zustand 的 selector 模式是类似的思路。

## 话术 4：分布式事务与韧性设计（考察：后端思维、错误处理、系统设计）

**面试官可能问**：「你们的生成流程中，如果中间步骤失败了怎么处理？」

**建议回答框架**：
> 生成流程涉及三个外部依赖：AI 引擎、对象存储 R2、计费系统 Polar。我设计了一套"补偿事务 + Fire-and-Forget"的方案来保证数据一致性。
>
> 补偿事务的核心思路是：先创建数据库记录拿到 ID → 用这个 ID 构建存储路径上传音频 → 更新数据库记录的存储 key。这中间任何一步失败，catch 块会检查是否已创建了数据库记录——如果有，就执行删除操作回滚。虽然这不是真正的数据库事务（跨了 DB 和 R2 两个系统），但在业务层面达到了"不留孤儿数据"的效果。
>
> 计费系统我用了 Fire-and-Forget 模式：`polar.events.ingest(...).catch(() => {})`——在 try-catch 主流程**之外**调用，即使 Polar 宕机或网络超时，也不会阻断用户获得已生成的音频。失败时静默吞掉，因为计费数据可以通过对账来补偿。
>
> 音频的安全访问也有考虑：不直接暴露 R2 的 URL，而是通过一个 API Route 代理，先做身份验证和权限检查，然后用 SDK 签发 1 小时过期的预签名 URL，设置 `Cache-Control: private, max-age=3600`。

**可能的追问**：「为什么不直接用数据库事务？」
> 因为音频上传到 R2 和写入数据库是两个独立的系统，无法放在同一个数据库事务中。所以这里用的是应用层的补偿事务——本质上是一种 Saga 模式的简化版本。

## 话术 5：第三方库生命周期管理（考察：React 原理、内存管理、自定义 Hook 设计）

**面试官可能问**：「你们怎么处理 WaveSurfer 这种非 React 库的集成？」

**建议回答框架**：
> 集成非 React 的第三方库，最核心的问题就是生命周期同步。WaveSurfer 在切换音频 URL 时需要销毁旧实例再创建新实例，我用了一个 `destroyed` 标志位来解决竞态问题。
>
> 为什么需要这个标志位？因为 WaveSurfer 的 `load()` 是异步的。如果用户快速切换两条音频，第一个 `load()` 可能在第二个实例已经创建之后才完成，然后回调中的 `setState` 会在已卸载的实例上执行——在 React Strict Mode 下这会触发警告。所以我用 `let destroyed = false` 这个局部变量，在所有事件回调中检查 `if (destroyed) return`，在 `useEffect` 的 cleanup 中设置为 `true`。
>
> 类似的问题在 `useAudioRecorder` hook 中也存在——我需要在 `isRecording` 变为 true、DOM 挂载、stream 就绪三个条件都满足后才初始化 WaveSurfer。这里用了带条件守卫的 `useEffect`：`if (!isRecording || !containerRef.current || !streamRef.current) return`。
>
> 还有一个实用细节：seek 操作使用**比例**（`newTime / duration`）而非绝对秒数，因为某些音频的 duration 元数据可能不精确，比例的方式兼容性更好。同时对 seek 做了边界保护：`Math.min(newTime, duration)` 和 `Math.max(newTime, 0)` 防止超出范围。

**可能的追问**：「怎么处理浏览器自动播放限制？」
> `ws.play()` 返回一个 Promise，如果浏览器阻止了自动播放会抛出 NotAllowedError。我直接在 play 后 `.catch(() => {})` 静默处理。这样组件不会报未捕获的异常，用户点击播放按钮时依然可以正常播放。

## 其他可能的面试追问

**Q: 为什么用 Clerk 而不是 NextAuth？**
> 项目需要多租户（Organization）支持，Clerk 内置了 org 切换、成员管理、role 权限，而且有现成的 Next.js Middleware 集成。如果自己用 NextAuth 实现，需要额外的数据模型和大量的模板代码。

**Q: 项目的安全性你是怎么考虑的？**
> - 所有数据查询通过 `orgProcedure` 中间件强制注入 `orgId`，实现租户间的数据物理隔离
> - 音频文件路径 `voices/orgs/{orgId}/{voiceId}` 天然租户隔离
> - 音频不暴露原始存储 URL，通过签名 URL 代理访问
> - 环境变量通过 `@t3-oss/env-nextjs` 做服务端/客户端分离校验
> - Sentry 集成了 tRPC 中间件自动捕获 API 错误

**Q: 如果让你重新设计这个项目，你会改变什么？**
> - 考虑将 TTS 生成改为异步任务队列（如 Inngest/Temporal），避免长请求超时
> - 使用 Edge Runtime 做音频 API Route，降低冷启动延迟
> - 引入 `@tanstack/react-virtual` 对历史列表做虚拟滚动
> - 对 WaveSurfer 做更精细的 tree-shaking，只引入用到的插件模块
