## 一、全链路类型安全

### Q1: 你提到"全链路类型安全"，从数据库到前端组件的完整类型链路。请描述一下这个类型链路具体是怎么实现的？Prisma 生成的类型是如何流转到前端 tRPC 调用的？

**参考答案：**

类型链路分为三层：

**第一层：Prisma → 服务端**

```typescript
// Prisma schema 定义
model Voice {
  id          String   @id @default(cuid())
  name        String
  description String?
  category    VoiceCategory
  language    String   @default("en-US")
  variant     VoiceVariant
  r2ObjectKey String?
  createdAt   DateTime @default(now())
}

// Prisma Client 生成完整 TypeScript 类型
const voice = await prisma.voice.findUnique({ where: { id } })
// voice 的类型自动推导，包含所有字段
```

**第二层：tRPC Router → 前端调用**

```typescript
// 服务端 router 定义
const voicesRouter = router({
  getAll: procedure.query(async ({ ctx }) => {
    return prisma.voice.findMany({
      where: { OR: [{ orgId: ctx.orgId }, { variant: "SYSTEM" }] }
    })
  }),
})

// 前端调用时自动获得类型提示和返回值推导
const { data } = useSuspenseQuery(trpc.voices.getAll.queryOptions())
// data 类型自动推导，无需手动定义接口
```

**第三层：Zod Schema 共享验证**

```typescript
// shared/schema.ts - 前后端共享的验证 schema
export const voiceCreateSchema = z.object({
  name: z.string().min(1),
  category: z.string(),
  language: z.string(),
})

// 服务端 procedure input 验证
const createVoice = procedure
  .input(voiceCreateSchema)
  .mutation(({ input }) => { /* input 类型已验证 */ })

// 前端表单验证也使用同一个 schema
const form = useForm({ validators: { onSubmit: voiceCreateSchema } })
```

**关键机制：** Prisma 生成的类型通过 tRPC 的泛型推导，流转到前端调用时无需手动维护接口定义。

### Q2: tRPC 和 TanStack Query 都在做类型安全，它们各自的职责是什么？为什么需要两层类型检查，是否有冗余？

**参考答案：**

| 层面 | 职责 | 类型安全的作用点 |
|------|------|----------------|
| **tRPC** | 后端 API 路由定义、输入验证、服务端上下文注入 | procedure 的 input/output 类型检查 |
| **TanStack Query** | 前端异步状态管理、缓存、请求生命周期 | queryKey 对应的数据类型 |

**两者如何配合：**

```typescript
// tRPC 定义返回类型
const { data } = trpc.voices.getAll.queryOptions()
// data 类型由 tRPC 自动推导

// TanStack Query 管理缓存
const queryClient = new QueryClient()
// queryClient.getQueryData(['voices', 'getAll']) 返回正确类型
```

**是否冗余？**
- 不是冗余，是职责分离
- tRPC 负责"服务端到服务端的类型安全"
- TanStack Query 负责"前端状态管理的类型安全"
- tRPC 底层其实依赖 TanStack Query 做请求执行

### Q3: Zod schema 共享给前后端，如果后端修改了 schema 但忘记同步前端，会发生什么？怎么避免"类型漂移"？

**参考答案：**

**会发生的问题：**
- 后端接受了新格式的数据，但前端还在用旧 schema 验证
- 导致前端验证通过但后端返回意外结果
- 或者反过来，前端验证失败但后端实际可以处理

**预防措施：**
1. 将 Zod schema 放在共享包中（`src/lib/validations.ts`），前后端都从同一处导入
2. 使用 `z.infer<typeof schema>` 推导类型，避免重复定义
3. CI/CD 阶段可以加入 schema 一致性检查
4. 实际上这个风险需要靠团队规范来约束，没有技术手段能完全避免

**如果已经发生：**
- tRPC 的 `input` 验证会在服务端拦截不符合新 schema 的请求
- 前端会收到 400 错误，错误信息包含 Zod 验证失败的具体字段

### Q4: Prisma 的 `select` 字段控制返回的数据，怎么确保前端使用的字段确实被查询了？

**参考答案：**

**风险场景：**
```typescript
// 后端只查询了 name 和 id
const voice = await prisma.voice.findUnique({
  where: { id },
  select: { id: true, name: true }
})

// 前端尝试访问 voice.description → undefined（不是报错！）
```

**项目中的实践：**

```typescript
// 在 tRPC router 中明确返回完整数据
const voice = await prisma.voice.findUnique({
  where: { id },
  select: {
    id: true,
    name: true,
    description: true,  // 明确列出
    category: true,
    language: true,
    variant: true,
    r2ObjectKey: true,
    createdAt: true,
  }
})

// 不使用 select 时，Prisma 返回完整对象
const voices = await prisma.voice.findMany()
// voices 是完整类型，包含所有字段
```

**前端使用时报错情况：**
```typescript
// 如果后端没返回该字段，TypeScript 编译时不报错
// 但运行时访问时是 undefined

// 所以需要前端自己做防护
const desc = voice.description ?? "无描述"
```

**最佳实践：** 在 tRPC 层明确规定返回的 shape，前端不应该访问未声明的字段。

## 二、多组织数据隔离

### Q5: Clerk Organizations 多组织架构与数据库的关联？一个用户能否同时属于多个组织？切换组织时怎么处理？

**参考答案：**

**数据库关联：**
```prisma
model Voice {
  id        String   @id @default(cuid())
  orgId     String?  // Clerk orgId，外键关联
  name      String
  // ...
}

// 通过 orgId 字段实现数据归属
```

**一个用户可以同时属于多个组织：**
- Clerk 允许一个 user 属于多个 organization
- 用户在 `orgId` 字段存储当前会话的 orgId

**切换组织的处理：**
```typescript
// 中间件获取 orgId
const { userId, orgId } = await auth()
// orgId 来自当前会话，不从请求参数获取

// 每次请求都会重新从 Clerk 获取当前 orgId
// 切换组织后，下一次请求的 orgId 就变了
```

**数据隔离保证：**
```typescript
// 所有 CUSTOM 语音查询都带 orgId 条件
prisma.voice.findMany({
  where: {
    OR: [
      { orgId: ctx.orgId },      // 当前组织的自定义语音
      { variant: "SYSTEM" }      // 系统语音（所有组织可见）
    ]
  }
})
```

### Q6: "通过 proxy 实现路由级别的认证拦截"，这个 proxy 怎么实现的？

**参考答案：**

**两层拦截：**

**1. Next.js Middleware（路由层面）：**
```typescript
// middleware.ts
export default clerkMiddleware(async (auth, req) => {
  const { userId, orgId } = await auth()

  // 公开路由不需要认证
  if (isPublicRoute(req)) {
    return NextResponse.next()
  }

  // 需要认证的路由
  if (!userId) {
    return NextResponse.redirect(new URL('/sign-in', req.url))
  }

  // 需要组织的路由
  if (!orgId && requiresOrg(req)) {
    return NextResponse.redirect(new URL('/org-selection', req.url))
  }
})
```

**2. tRPC Procedure（业务层面）：**
```typescript
// src/trpc/routers/_app.ts
const orgProcedure = procedure.use(async ({ ctx, next }) => {
  const { userId, orgId } = await auth()
  if (!userId || !orgId) {
    throw new TRPCError({ code: 'UNAUTHORIZED' })
  }
  return next({ ctx: { userId, orgId } })
})

// 所有需要组织的 router 都用 orgProcedure
const voicesRouter = router({
  create: orgProcedure.mutation(/* ... */)
})
```

**为什么两层？**
- Middleware：更快，未登录用户直接重定向，不需要进入业务代码
- Procedure：业务逻辑执行前的最后一道检查，确保 ctx 中有 orgId

### Q7: 如果构造一个请求，orgId 填别人的，能查到别人的数据吗？

**参考答案：**

**查不到。原因：**

```typescript
// 服务端代码
const { userId, orgId } = await auth() // 从 Clerk 获取，不从请求体获取

// 查询时用的是 ctx.orgId，不是请求参数中的 orgId
```

**安全设计：**

2. orgId 来自 `auth()` 函数，从 Clerk 的 session token 中解析
3. 用户无法伪造 orgId，因为没有途径传入

**攻击场景验证：**
```bash
# 即使手动构造请求
curl -X POST http://api/voices -d '{"orgId": "attacker_org_id"}'

# 服务端也会忽略这个 orgId，使用 Clerk 认证后的真实 orgId
```

### Q8: CUSTOM 语音和 SYSTEM 语音的隔离怎么处理的？SYSTEM 语音 orgId 是 null 吗？

**参考答案：**

**隔离策略：**

```typescript
// SYSTEM 语音：variant = "SYSTEM"，orgId = null
// CUSTOM 语音：variant = "CUSTOM"，orgId = 有值

// 查询逻辑
prisma.voice.findMany({
  where: {
    OR: [
      { orgId: ctx.orgId, variant: "CUSTOM" },  // 本组织的自定义语音
      { variant: "SYSTEM" }                    // 所有组织可见的系统语音
    ]
  }
})
```

**数据库存储：**
```prisma
model Voice {

  variant   VoiceVariant // SYSTEM | CUSTOM
  // ...
}
```

**为什么这样设计：**
- SYSTEM 语音是平台预置的，所有组织都可以使用
- 每个组织只能看到和操作自己的 CUSTOM 语音
- 通过 `variant` + `orgId` 组合实现灵活的数据可见性控制

## 三、浏览器实时录音

### Q9: RecordRTC 录音时，音频格式是什么？为什么选择这个格式？

**参考答案：**

**使用的格式：** `audio/wav`（WAV 格式）

**为什么选择 WAV：**
```typescript
const recorder = new RecordRTC(stream, {
  type: "audio",
  mimeType: "audio/wav",  // 指定 WAV 格式
})
```

**WAV 优点：**
- **无损格式**：音频质量不受影响，适合作为语音克隆的参考音频
- **简单结构**：RIFF 容器，解析简单，不需要复杂的编解码
- **兼容性**：所有浏览器都支持 WAV 格式的 MediaRecorder

**缺点：**
- 文件体积大（未压缩）
- 但语音克隆需要高质量音频，质量比体积更重要

**其他格式对比：**
| 格式 | 压缩 | 质量 | 兼容性 |
|------|------|------|--------|
| WAV | 无 | 最高 | 100% |
| WebM/Opus | 有 | 高 | 较好 |
| MP3 | 有 | 中 | 需编码器 |

### Q10: WaveSurfer.js 的 RecordPlugin 是怎么和 RecordRTC 配合工作的？

**参考答案：**

**两者的职责分工：**

```
RecordRTC: 负责获取和保存音频数据
WaveSurfer.RecordPlugin: 负责可视化渲染
```

**实际实现流程：**

```typescript
// 1. 获取麦克风音频流
const stream = await navigator.mediaDevices.getUserMedia({ audio: true })

// 2. RecordRTC 录制音频
const recorder = new RecordRTC(stream, {
  type: "audio",
  mimeType: "audio/wav",
  timeSlice: 5000, // 每 5 秒触发一次回调
})

recorder.startRecording()

// 3. 录音过程中，使用 MediaStream 作为 WaveSurfer 的数据源
// WaveSurfer.RecordPlugin 接收同一个 stream
// 它会从这个 stream 读取数据并渲染波形
```

**RecordPlugin 的作用：**
```typescript
import { RecordPlugin } from 'wavesurver.js/dist/plugins/record.js'

const recordPlugin = RecordPlugin.create({
  scrollingWaveform: true,  // 实时滚动波形
  renderWaveform: (waveform) => { /* 渲染到 canvas */ }
})

// 将麦克风 stream 传给 RecordPlugin
recordPlugin.startRecording(stream)
```

**注意：** 根据项目代码，VoiceRecorder 组件使用的是 RecordRTC 录制 + 前端 UI 状态管理，波形可视化可能需要额外集成 WaveSurfer.RecordPlugin。

### Q11: 录音组件在移动端浏览器上能正常工作吗？遇到过兼容性问题吗？

**参考答案：**

**项目中的实践：**
```typescript
// 使用 RecordRTC 库处理兼容性问题

const recorder = new RecordRTC(stream, {
```

- 录音功能作为可选功能，移动端会显示提示引导用户使用桌面端
- 没有特殊区分移动端组件，但要求 HTTPS 环境

### Q12: `timeSlice: 5000` 这个参数的选择基于什么考虑？

**参考答案：**

**参数作用：**
```typescript
const recorder = new RecordRTC(stream, {
  timeSlice: 5000, // 每 5 秒保存一次数据块
})
```

**设计考虑：**
- **太短（如 1 秒）**：
  - 文件碎片多，磁盘 I/O 频繁
  - 对性能要求高
  - 适合需要实时传输的场景（如实时通话）

- **太长（如 30 秒）**：
  - 内存占用大（需要缓存整个录音）
  - 如果中途出错，丢失数据多
  - 用户等待感强

- **选择 5 秒的原因**：
  - 平衡性能和用户体验
  - 录音时长通常在 10-30 秒范围
  - 最后一帧会在 stopRecording 时自动保存
  - 足够小的数据块便于处理

```python
# Modal 部署的函数
@app.function(
```

- 首次 TTS 生成较慢（冷启动）
- 连续生成时速度较快
- 没有实现请求队列或预热机制

### Q15: Chatterbox API 返回 ArrayBuffer，前后的数据是怎么流转的？

**参考答案：**

**服务端调用：**
```typescript
// src/trpc/routers/generations.ts
const { data, error } = await chatterbox.POST("/generate", {
  body: {
    prompt: input.text,
    voice_key: voice.r2ObjectKey,
    temperature: input.temperature,
    // ...
  },
  parseAs: "arrayBuffer",  // 指定接收格式
})
```

**数据类型转换：**
```typescript
// data 是 ArrayBuffer
const arrayBuffer: ArrayBuffer = data

// 转为 Node.js Buffer 用于上传到 R2
const buffer = Buffer.from(arrayBuffer)

// 上传到 R2
await uploadAudio({ buffer, key: r2ObjectKey, contentType: "audio/wav" })
```

**完整流转：**
```
Chatterbox API                    服务端              R2 存储
     │                              │                  │
     │  ArrayBuffer (二进制)         │                  │
     ├─────────────────────────────>│                  │
     │                              │ Buffer.from()    │
     │                              ├─────────────────>│
     │                              │                  │
     │                              │    存储成功      │
```

**为什么用 ArrayBuffer：**
- 音频数据是二进制，不需要 JSON 序列化/反序列化
- 直接传输效率最高
- openapi-fetch 的 `parseAs: "arrayBuffer"` 选项专门处理这种场景

### Q16: TTS 生成失败时，错误处理怎么做？用户看到什么错误？

**参考答案：**

**服务端错误处理：**

```typescript
// src/trpc/routers/generations.ts
const { data, error } = await chatterbox.POST("/generate", {
  body: { /* ... */ },
  parseAs: "arrayBuffer",
})

if (error) {
  throw new TRPCError({
    code: "INTERNAL_SERVER_ERROR",
    message: "Failed to generate audio",
  })
}
```

**前端错误展示：**

```typescript
// text-to-speech-form.tsx
try {
  const data = await createMutation.mutateAsync({ /* ... */ })
  toast.success("Audio generated successfully!")
  router.push(`/text-to-speech/${data.id}`)
} catch (error) {
  const message = error instanceof Error ? error.message : "Failed to generate audio"

  if (message === "SUBSCRIPTION_REQUIRED") {
    toast.error("Subscription required", {
      action: { label: "Subscribe", onClick: () => checkout() },
    })
  } else {
    toast.error(message)  // 显示具体错误信息
  }
}
```

**错误类型汇总：**
| 错误场景 | HTTP 状态 | 用户看到的提示 |
|---------|-----------|---------------|
| 未登录 | 401 | 重定向到登录页 |
| 无订阅 | 403 | "请先订阅" + 订阅按钮 |
| 参数验证失败 | 400 | 具体字段错误 |
| 语音不存在 | 404 | "语音不存在" |
| TTS 生成失败 | 500 | "生成失败，请重试" |
| Modal 超时 | 500 | "生成超时，请重试" |

**没有降级策略**：当前是同步调用，失败了只能重试。如果需要降级，可以考虑：
- 实现异步任务队列
- 预留备用 TTS 服务商
- 添加重试机制（指数退避）

### Q17: Polar 订阅系统和用量事件是怎么配合的？如果 Polar 不可用会阻塞用户吗？

**参考答案：**

**订阅检查流程：**

```typescript
// src/trpc/routers/generations.ts
try {
  const customerState = await polar.customers.getStateExternal({
    externalId: ctx.orgId,
  })

  if ((customerState.activeSubscriptions ?? []).length === 0) {
    throw new TRPCError({
      code: "FORBIDDEN",

    })
  }
} catch (err) {
  // Polar 服务异常也拒绝访问
  if (err instanceof TRPCError) throw err
  throw new TRPCError({
    code: "FORBIDDEN",
    message: "SUBSCRIPTION_REQUIRED",
  })
}
```

**用量事件上报（异步）：**

```typescript
// 创建语音后上报
polar.events.ingest({
  events: [{
    name: "voice_creation",
    externalCustomerId: orgId,
    metadata: {},
    timestamp: new Date(),
  }],
}).catch(() => {})  // 失败静默处理，不阻塞
```

**Polar 不可用时：**
- 订阅检查会失败，用户无法使用服务
- 用量上报失败不影响主流程（用了 `.catch(() => {})`）
- 这是**同步阻塞 + 异步不阻塞**的设计

### Q18: 为什么选择 Modal 而不是其他 GPU 云服务？对比过哪些方案？

**参考答案：**

**Modal 的优势：**

| 特性 | Modal | GPU 云服务器 | Replicate | Vast.ai |
|------|-------|-------------|-----------|---------|
| 计费 | 按秒计费 | 包月/年 | 按调用 | 按秒 |
| 冷启动 | 秒级 | 无（常驻） | 较快 | 较快 |
| 无请求收费 | 无 | 有（包月） | 有 | 有 |
| Python 原生 | 是 | 需配置 | API | 需配置 |
| 存储挂载 | R2 原生支持 | 需手动 | 支持 | 需手动 |

**为什么项目选择 Modal：**
1. **按秒计费**：TTS 是间歇性请求，不需要常驻 GPU
2. **R2 挂载**：可以直接挂载 R2 桶作为模型权重和样本库
3. **Python 原生**：Chatterbox 是 Python 库，不需要额外适配
4. **简单部署**：`modal deploy` 即可，无需配置 Docker/K8s

**实际使用场景：**
- 用户点击"生成"后才调用 TTS API
- 请求间隔不确定，可能几天才一次
- Modal 的无请求不收费特性非常适合

### Q20: 文本很长（接近 5000 字符）时，怎么处理可能的超时问题？

**参考答案：**

**当前限制：**


**超时处理：**
```typescript
// Modal 函数超时配置
@app.function(
  gpu="A10G",
  timeout=300,  // 5 分钟超时

```

**没有实现的优化：**
1. **文本分片**：将长文本切分成多个短片段，分别生成后拼接
2. **流式生成**：使用 SSE 让前端先显示进度
3. **异步任务**：将 TTS 作为后台任务，返回 taskId，前端轮询状态

- 5 分钟超时足够生成约 2-3 分钟的音频
- 如果超时，客户端会收到 500 错误

```
├── 音频格式不支持 → 需转换
```
