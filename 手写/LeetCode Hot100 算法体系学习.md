## 第一章：时间复杂度、空间复杂度与算法分析

### 知识点 1：为什么需要复杂度分析？

在正式刷 LeetCode 之前，我们先不急着写代码。

因为算法面试真正考的不是“你会不会写一个能跑的程序”，而是：

> 当数据量变大时，你的程序还能不能跑得动？

这就是复杂度分析存在的原因。

---

## 1. 一个前端同学很熟悉的例子

假设你在前端页面里有一个用户列表：

```js
const users = [
  { id: 1, name: "Alice" },
  { id: 2, name: "Bob" },
  { id: 3, name: "Charlie" },
];
```

现在要根据 `id` 找用户。

最直接的写法是：

```js
function findUser(users, targetId) {
  for (const user of users) {
    if (user.id === targetId) {
      return user;
    }
  }

  return null;
}
```

这个代码当然能用。

但问题是：如果用户数量变成下面这样呢？

| 用户数量 | 查找一次最多要看多少个用户 |
|---:|---:|
| 10 | 10 |
| 1,000 | 1,000 |
| 1,000,000 | 1,000,000 |

如果目标用户刚好在最后，或者根本不存在，那么程序就必须从头扫到尾。

这说明：

> 代码能跑，不代表代码适合大数据量。

复杂度分析，就是用来提前判断这个问题的。

---

## 2. 为什么不能只看运行时间？

很多初学者会想：

> 我直接 `console.time()` 测一下不就行了吗？

可以测，但不能只靠测。

因为真实运行时间会被很多因素影响：

| 影响因素 | 说明 |
|---|---|
| 电脑性能 | M 系列芯片和普通笔记本速度不同 |
| 浏览器 / Node 版本 | JS 引擎优化不同 |
| 当前系统负载 | 后台程序会影响测试 |
| 数据分布 | 目标在开头和目标在结尾差很多 |
| 网络 / IO | 如果有请求、文件读写，时间更不稳定 |

所以我们需要一种更稳定的分析方式。

复杂度分析不关心“这台机器上跑了几毫秒”，而关心：

> 当输入规模 n 增长时，操作次数大概怎么增长？

这里的 `n` 可以理解为输入数据量。

比如：

```js
function findUser(users, targetId) {
  for (const user of users) {
    if (user.id === targetId) {
      return user;
    }
  }

  return null;
}
```

如果 `users.length = n`，最坏情况下要检查 `n` 个元素。

所以它的时间复杂度是：

```text
O(n)
```

先不要急着背 `O(n)` 是什么。

此刻你只需要先建立一个直觉：

> 输入越多，要做的事情也线性变多。

也就是：

```text
n 变成 10 倍，操作次数大约也变成 10 倍
```

---

## 3. 复杂度分析到底在分析什么？

复杂度主要分析两件事：

### 3.1 时间复杂度

时间复杂度关心：

> 随着输入规模变大，程序执行的基本操作次数如何增长？

例如遍历数组：

```js
function printAll(nums) {
  for (const num of nums) {
    console.log(num);
  }
}
```

如果数组长度是 `n`，就要打印 `n` 次。

所以时间增长趋势是：

```text
O(n)
```

### 3.2 空间复杂度

空间复杂度关心：

> 随着输入规模变大，程序额外占用的内存如何增长？

例如复制数组：

```js
function copyArray(nums) {
  const result = [];

  for (const num of nums) {
    result.push(num);
  }

  return result;
}
```

如果 `nums` 有 `n` 个元素，`result` 也会存 `n` 个元素。

所以额外空间是：

```text
O(n)
```

注意这里说的是“额外空间”。

输入数组 `nums` 本来就存在，通常不算进额外空间里。

## 4. 一个重要思想：复杂度看趋势，不看细节

比如下面两个函数：

```js
function fn1(nums) {
  for (const num of nums) {
    console.log(num);
  }
}
```

```js
function fn2(nums) {
  for (const num of nums) {
    console.log(num);
  }

  for (const num of nums) {
    console.log(num);
  }
}
```

`fn1` 遍历 1 次数组。

`fn2` 遍历 2 次数组。

如果数组长度是 `n`：

```text
fn1: n 次
fn2: 2n 次
```

但在复杂度里，它们都记作：

```text
O(n)
```

为什么？

因为复杂度看的是增长趋势。

当 `n` 非常大时，`n` 和 `2n` 都是“随着 n 线性增长”。

常数倍不会改变增长级别。

可以粗略理解为：

```text
O(n) 关心的是：是不是和 n 同步变大
而不是：具体是 1n、2n、还是 10n
```

---

## 5. 先建立第一层直觉

你现在只需要记住这几句话：

| 概念 | 直觉理解 |
|---|---|
| 输入规模 n | 数据量，比如数组长度 |
| 时间复杂度 | 数据变多时，操作次数怎么变 |
| 空间复杂度 | 数据变多时，额外内存怎么变 |
| O(n) | 输入变大多少，操作大致也变大多少 |
| 复杂度分析 | 不看某次运行几毫秒，而看增长趋势 |

---

## 6. 面试官为什么一定问复杂度？

因为大厂真实业务里，数据规模可能很大。

一个 `O(n)` 和一个 `O(n^2)` 的差距，在小数据下不明显。

但当 `n = 100,000` 时：

```text
O(n)   大约 100,000 次操作
O(n^2) 大约 10,000,000,000 次操作
```

这已经不是“慢一点”的问题，而是“可能根本跑不完”。

所以面试官问复杂度，本质是在问：

> 你有没有能力判断自己的代码在大规模输入下是否可靠？
