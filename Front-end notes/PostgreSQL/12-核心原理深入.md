# 12. PostgreSQL 核心原理深入

本章重点讲这些主题：

- 表
- 索引
- JOIN
- EXPLAIN
- 事务
- 锁
- MVCC
- 查询优化

它们不是孤立知识。真正的理解路径是：

```text
表如何存储数据
  -> 索引如何定位数据
  -> JOIN 如何组合数据
  -> EXPLAIN 如何暴露执行过程
  -> 事务如何定义一致性边界
  -> 锁如何处理并发冲突
  -> MVCC 如何让读写并发
  -> 查询优化器如何选择执行计划
```

## 1. 表：PostgreSQL 里数据到底怎么放

从 SQL 层看，表是行和列：

```sql
CREATE TABLE users (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

从存储层看，表不是“一个 Excel 文件”，而是由很多数据页组成。PostgreSQL 默认数据页大小是 8KB。表中的每一行是一个 tuple，也就是行版本。

### 行不是原地无限修改

PostgreSQL 使用 MVCC。执行 `UPDATE` 时，通常不是直接覆盖旧行，而是写入一个新行版本，并把旧版本标记为不再对新事务可见。

```sql
UPDATE users
SET name = 'Alice Zhang'
WHERE id = 1;
```

概念上会发生：

```text
旧行版本：name = Alice        对旧事务仍可能可见
新行版本：name = Alice Zhang  对新事务可见
```

所以 PostgreSQL 表会产生死元组，需要 `VACUUM` 清理。

### 表膨胀

频繁更新、删除后，表文件可能变大，因为旧行版本没有立刻消失。

查看死元组：

```sql
SELECT
  relname,
  n_live_tup,
  n_dead_tup,
  last_vacuum,
  last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

手动清理并更新统计信息：

```sql
VACUUM (ANALYZE) users;
```

### HOT Update

如果更新的列没有被索引引用，PostgreSQL 可能使用 HOT Update，减少索引维护成本。

例子：

```sql
CREATE TABLE articles (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title TEXT NOT NULL,
  view_count INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX idx_articles_title ON articles (title);
```

更新 `view_count`：

```sql
UPDATE articles
SET view_count = view_count + 1
WHERE id = 1;
```

因为 `view_count` 不在索引中，这类更新更可能触发 HOT Update。反过来，如果你给 `view_count` 建索引，每次更新都要维护索引。

结论：

- 表不是静态容器，而是会产生多个行版本。
- 更新频繁的列不要随便建索引。
- `VACUUM`、Autovacuum、统计信息是 PostgreSQL 的基本生存系统。

## 2. 索引：不是越多越好

索引的本质是额外的数据结构。它让读更快，但让写更慢，占用更多空间。

### B-tree 索引

默认索引类型，适合：

- `=`
- `< / <= / > / >=`
- `BETWEEN`
- `ORDER BY`
- 前缀匹配，例如 `LIKE 'abc%'`

```sql
CREATE INDEX idx_users_email ON users (email);

SELECT *
FROM users
WHERE email = 'alice@example.com';
```

### 组合索引

```sql
CREATE INDEX idx_orders_user_created
ON orders (user_id, created_at DESC);
```

适合：

```sql
SELECT *
FROM orders
WHERE user_id = 1
ORDER BY created_at DESC
LIMIT 20;
```

因为索引已经按 `user_id` 分组，并在每个用户下按 `created_at` 排好序。

不一定适合：

```sql
SELECT *
FROM orders
WHERE created_at >= now() - interval '1 day';
```

因为查询没有限制第一列 `user_id`。PostgreSQL 18 起多列 B-tree 有更多 skip scan 能力，但索引顺序仍然非常重要。

### 选择性

索引适合高选择性的条件，也就是能过滤掉大部分数据的条件。

适合索引：

```sql
WHERE email = 'alice@example.com'
```

不一定适合索引：

```sql
WHERE gender = 'male'
```

如果一半行都匹配，顺序扫描可能更快。

### 覆盖索引

```sql
CREATE INDEX idx_users_email_include_name
ON users (email)
INCLUDE (name);
```

查询：

```sql
SELECT name
FROM users
WHERE email = 'alice@example.com';
```

如果可见性条件满足，PostgreSQL 可能使用 `Index Only Scan`，只读索引，不读表。

### 部分索引

```sql
CREATE INDEX idx_orders_unpaid_created
ON orders (created_at DESC)
WHERE status = 'unpaid';
```

适合：

```sql
SELECT *
FROM orders
WHERE status = 'unpaid'
ORDER BY created_at DESC
LIMIT 20;
```

部分索引适合“只经常查某一小部分数据”的场景。

### 表达式索引

```sql
CREATE INDEX idx_users_lower_email
ON users (lower(email));
```

查询也要写表达式：

```sql
SELECT *
FROM users
WHERE lower(email) = lower('Alice@Example.com');
```

### GIN 索引

适合 JSONB、数组、全文搜索：

```sql
CREATE TABLE events (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  payload JSONB NOT NULL
);

CREATE INDEX idx_events_payload
ON events
USING gin (payload);

SELECT *
FROM events
WHERE payload @> '{"type": "signup"}';
```

### 索引设计口诀

先问这几个问题：

1. 这个查询是否频繁？
2. 这个查询是否足够慢？
3. WHERE 条件是什么？
4. JOIN 条件是什么？
5. ORDER BY / LIMIT 是什么？
6. 返回的数据比例高不高？
7. 这张表写入频率高不高？

不要因为“某列会被查询”就建索引。要因为“某个重要查询需要这个访问路径”而建索引。

## 3. JOIN：数据库如何把表连起来

业务数据通常分散在多张表里：

```sql
SELECT
  o.id,
  u.email,
  o.total_amount
FROM orders AS o
JOIN users AS u ON u.id = o.user_id
WHERE o.status = 'paid';
```

SQL 里你写的是“我要什么结果”，执行器要决定“怎么连接”。

### Nested Loop Join

适合外表结果少、内表有索引的情况。

概念：

```text
for each row in outer_table:
  use index to find matching rows in inner_table
```

典型场景：

```sql
SELECT *
FROM orders AS o
JOIN users AS u ON u.id = o.user_id
WHERE o.id = 100;
```

如果 `orders.id` 和 `users.id` 都有索引，这种连接很快。

### Hash Join

适合较大数据集的等值连接。

概念：

```text
先把较小输入构建 hash table
再扫描较大输入并查 hash table
```

例子：

```sql
SELECT *
FROM orders AS o
JOIN users AS u ON u.id = o.user_id;
```

如果需要连接大量行，Hash Join 很常见。

### Merge Join

适合两边都已经按 JOIN key 排序，或可以通过索引顺序读取。

概念：

```text
两个有序列表从头往后同步推进
```

适合大表有序连接。

### JOIN 优化重点

JOIN 慢通常不是 JOIN 本身慢，而是：

- JOIN 条件缺索引。
- 过滤条件没有尽早缩小数据量。
- 统计信息不准，导致优化器估算错误。
- 返回行数太多。
- JOIN 顺序不合适。
- work_mem 太小，Hash Join 溢出到磁盘。

外键列通常建议建索引：

```sql
CREATE INDEX idx_orders_user_id ON orders (user_id);
```

注意：创建外键不会自动给引用列建索引。

## 4. EXPLAIN：看懂数据库实际怎么跑

`EXPLAIN` 只显示计划，不真正执行：

```sql
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 1;
```

`EXPLAIN ANALYZE` 会真正执行，并显示实际耗时：

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE user_id = 1
ORDER BY created_at DESC
LIMIT 20;
```

### 重点字段

示意：

```text
Limit  (cost=0.42..10.50 rows=20 width=80)
  actual time=0.040..0.120 rows=20 loops=1
  Buffers: shared hit=15
  -> Index Scan using idx_orders_user_created on orders
       Index Cond: (user_id = 1)
```

解释：

- `cost`：优化器估算成本，不是毫秒。
- `rows`：估算返回行数。
- `actual time`：真实耗时。
- `actual rows`：真实返回行数。
- `loops`：节点执行次数。
- `Buffers shared hit`：从缓存读到。
- `Buffers shared read`：从磁盘读到。
- `Index Cond`：索引层过滤条件。
- `Filter`：取出行之后再过滤。

### 常见扫描节点

顺序扫描：

```text
Seq Scan on orders
```

不一定坏。表小、返回比例高时很正常。

索引扫描：

```text
Index Scan using idx_orders_user_created on orders
```

通过索引定位，再回表读取完整行。

只读索引：

```text
Index Only Scan using idx_users_email_include_name on users
```

可能更快，但依赖 visibility map。

位图扫描：

```text
Bitmap Heap Scan on orders
  -> Bitmap Index Scan on idx_orders_status
```

适合匹配行较多但又不是大部分表的场景。

### 判断问题的顺序

1. 估算行数和实际行数差距大不大？
2. 是否扫描了远超预期的行？
3. 是否出现大量 `Rows Removed by Filter`？
4. 是否出现磁盘读 `shared read` 很高？
5. 排序是否用了磁盘？
6. Hash 是否分批，是否溢出？
7. 是否因为 `loops` 导致内层节点执行很多次？

### 一个典型慢查询分析

慢查询：

```sql
SELECT *
FROM orders
WHERE user_id = 1
ORDER BY created_at DESC
LIMIT 20;
```

如果计划是：

```text
Seq Scan on orders
  Filter: (user_id = 1)
Sort
  Sort Key: created_at DESC
```

说明数据库扫描全表，再排序。可以加组合索引：

```sql
CREATE INDEX idx_orders_user_created
ON orders (user_id, created_at DESC);
```

理想计划：

```text
Index Scan using idx_orders_user_created on orders
  Index Cond: (user_id = 1)
```

数据库可以直接按用户和时间顺序取前 20 条。

## 5. 事务：一致性的边界

事务是数据库里一组操作的边界。

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;
```

如果中途失败：

```sql
ROLLBACK;
```

### ACID

- Atomicity：原子性，要么都成功，要么都失败。
- Consistency：一致性，约束不能被破坏。
- Isolation：隔离性，并发事务之间互不乱套。
- Durability：持久性，提交后不会因为普通故障丢失。

### 隔离级别

PostgreSQL 常用：

```sql
BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

默认级别。每条语句看到语句开始前已经提交的数据。

```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

同一个事务内看到固定快照。

```sql
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

最强隔离，数据库会阻止不可串行化的并发结果。应用要准备重试事务。

### 长事务的危害

```sql
BEGIN;
SELECT * FROM orders;
-- 长时间不 COMMIT / ROLLBACK
```

问题：

- 旧行版本不能清理。
- 表膨胀。
- 可能阻塞 DDL。
- 占用连接。

查看长事务：

```sql
SELECT
  pid,
  state,
  now() - xact_start AS xact_age,
  query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_age DESC;
```

## 6. 锁：并发修改时谁等谁

锁用来保护数据结构和数据一致性。PostgreSQL 有很多锁，入门先抓住两类：

- 表级锁
- 行级锁

### 行级锁

更新行时会锁住对应行：

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;
```

此时另一个事务如果也更新 `id = 1`，会等待。

显式行锁：

```sql
BEGIN;

SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;

COMMIT;
```

适合库存、余额、任务领取等场景。

### SKIP LOCKED

任务队列常用：

```sql
WITH picked AS (
  SELECT id
  FROM jobs
  WHERE status = 'pending'
  ORDER BY id
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE jobs
SET status = 'running'
WHERE id IN (SELECT id FROM picked)
RETURNING *;
```

多个 worker 可以并发领取任务，已经被锁的任务会跳过。

### 表级锁

DDL 通常需要更强的表锁：

```sql
ALTER TABLE users ADD COLUMN phone TEXT;
```

在高并发生产库里，DDL 要谨慎，尤其是大表。

### 查看锁等待

```sql
SELECT
  blocked.pid AS blocked_pid,
  blocked.query AS blocked_query,
  blocking.pid AS blocking_pid,
  blocking.query AS blocking_query
FROM pg_stat_activity AS blocked
JOIN pg_locks AS blocked_locks
  ON blocked_locks.pid = blocked.pid
JOIN pg_locks AS blocking_locks
  ON blocking_locks.locktype = blocked_locks.locktype
 AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
 AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
 AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
 AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
 AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
 AND blocking_locks.classid IS NOT DISTINCT FROM blocked_locks.classid
 AND blocking_locks.objid IS NOT DISTINCT FROM blocked_locks.objid
 AND blocking_locks.objsubid IS NOT DISTINCT FROM blocked_locks.objsubid
 AND blocking_locks.pid <> blocked_locks.pid
JOIN pg_stat_activity AS blocking
  ON blocking.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted
  AND blocking_locks.granted;
```

## 7. MVCC：为什么读写可以同时发生

MVCC 是 Multi-Version Concurrency Control，多版本并发控制。

核心思想：

```text
读不阻塞写
写不阻塞读
不同事务根据自己的快照看到不同版本
```

### 行版本可见性

每个行版本有创建它的事务信息和删除/更新它的事务信息。查询时，PostgreSQL 根据当前事务快照判断这个行版本是否可见。

示例：

事务 A：

```sql
BEGIN;
SELECT name FROM users WHERE id = 1;
```

事务 B：

```sql
BEGIN;
UPDATE users SET name = 'New Name' WHERE id = 1;
COMMIT;
```

事务 A 再查时，在不同隔离级别下结果可能不同：

- `READ COMMITTED`：第二次查询可能看到新值。
- `REPEATABLE READ`：仍看到事务开始时的旧值。

### MVCC 的代价

MVCC 很强，但不是免费：

- 更新会产生新行版本。
- 删除只是标记删除。
- 需要 VACUUM 清理旧版本。
- 长事务会阻止旧版本被清理。
- 索引可能指向多个行版本，需要可见性判断。

### 可见性地图和 Index Only Scan

`Index Only Scan` 并不是永远只读索引。PostgreSQL 需要知道表页上的行是否对所有事务可见。如果 visibility map 显示该页全可见，就可以避免回表。

所以 `VACUUM` 做得好，可能提升 `Index Only Scan` 效率。

## 8. 查询优化：从慢到快的真实流程

查询优化不是“看到慢就加索引”。更稳的流程是：

```text
确认慢查询
  -> 复现 SQL 和参数
  -> EXPLAIN (ANALYZE, BUFFERS)
  -> 判断瓶颈
  -> 调整索引 / SQL / 数据模型 / 配置
  -> 再次验证
```

### 第一步：确认业务目标

先问：

- 这个查询是否必须实时？
- 返回多少行？
- 是否可以分页？
- 是否可以预聚合？
- 是否允许缓存？

很多性能问题不是数据库问题，而是产品需求没有边界。

### 第二步：看执行计划

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
  u.email,
  count(o.id) AS order_count,
  sum(o.total_amount) AS total_spent
FROM users AS u
JOIN orders AS o ON o.user_id = u.id
WHERE o.created_at >= now() - interval '30 days'
GROUP BY u.email
ORDER BY total_spent DESC
LIMIT 10;
```

可能需要索引：

```sql
CREATE INDEX idx_orders_created_user
ON orders (created_at, user_id);
```

也可能更适合：

```sql
CREATE INDEX idx_orders_user_created
ON orders (user_id, created_at);
```

哪个更好取决于查询形态：

- 先按时间过滤大量订单，再聚合用户：`(created_at, user_id)` 可能更好。
- 经常查某个用户最近订单：`(user_id, created_at)` 更好。

### 第三步：减少读取的数据

差：

```sql
SELECT *
FROM orders
WHERE user_id = 1;
```

好：

```sql
SELECT id, total_amount, status, created_at
FROM orders
WHERE user_id = 1
ORDER BY created_at DESC
LIMIT 20;
```

少取列、加分页、让索引匹配排序，通常收益很大。

### 第四步：避免深分页

差：

```sql
SELECT *
FROM orders
ORDER BY created_at DESC
LIMIT 20 OFFSET 100000;
```

数据库仍要跳过前 100000 行。

好：

```sql
SELECT *
FROM orders
WHERE (created_at, id) < ('2026-05-01 10:00:00+08', 12345)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

配套索引：

```sql
CREATE INDEX idx_orders_created_id
ON orders (created_at DESC, id DESC);
```

### 第五步：让统计信息准确

```sql
ANALYZE orders;
```

如果某些列分布很偏，可以提高统计目标：

```sql
ALTER TABLE orders
ALTER COLUMN status SET STATISTICS 1000;

ANALYZE orders;
```

### 第六步：重写 SQL

有时先聚合再 JOIN 更快。

原始写法：

```sql
SELECT u.email, count(o.id)
FROM users AS u
JOIN orders AS o ON o.user_id = u.id
GROUP BY u.email;
```

改写：

```sql
WITH order_counts AS (
  SELECT user_id, count(*) AS order_count
  FROM orders
  GROUP BY user_id
)
SELECT u.email, c.order_count
FROM order_counts AS c
JOIN users AS u ON u.id = c.user_id;
```

如果 `orders` 很大但用户表也很大，两者效果要用 `EXPLAIN ANALYZE` 验证。

### 第七步：考虑预计算

实时聚合太慢时，可以维护汇总表：

```sql
CREATE TABLE user_order_stats (
  user_id BIGINT PRIMARY KEY REFERENCES users(id),
  order_count BIGINT NOT NULL DEFAULT 0,
  total_spent NUMERIC(14, 2) NOT NULL DEFAULT 0,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

写订单后更新统计：

```sql
INSERT INTO user_order_stats (user_id, order_count, total_spent)
VALUES (1, 1, 99.00)
ON CONFLICT (user_id)
DO UPDATE SET
  order_count = user_order_stats.order_count + 1,
  total_spent = user_order_stats.total_spent + EXCLUDED.total_spent,
  updated_at = now();
```

## 9. 综合案例：订单列表优化

需求：

```text
查询某个用户最近 20 个已支付订单
```

初始 SQL：

```sql
SELECT *
FROM orders
WHERE user_id = 1
  AND status = 'paid'
ORDER BY created_at DESC
LIMIT 20;
```

可能的坏计划：

```text
Seq Scan on orders
  Filter: ((user_id = 1) AND (status = 'paid'))
Sort
  Sort Key: created_at DESC
```

推荐索引：

```sql
CREATE INDEX idx_orders_user_status_created
ON orders (user_id, status, created_at DESC);
```

如果 `status = 'paid'` 是最常见的核心查询，也可以用部分索引：

```sql
CREATE INDEX idx_orders_paid_user_created
ON orders (user_id, created_at DESC)
WHERE status = 'paid';
```

再次验证：

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, total_amount, created_at
FROM orders
WHERE user_id = 1
  AND status = 'paid'
ORDER BY created_at DESC
LIMIT 20;
```

理想方向：

```text
Index Scan using idx_orders_paid_user_created on orders
  Index Cond: (user_id = 1)
```

进一步优化为覆盖索引：

```sql
CREATE INDEX idx_orders_paid_user_created_cover
ON orders (user_id, created_at DESC)
INCLUDE (total_amount)
WHERE status = 'paid';
```

对应查询：

```sql
SELECT id, total_amount, created_at
FROM orders
WHERE user_id = 1
  AND status = 'paid'
ORDER BY created_at DESC
LIMIT 20;
```

是否能 `Index Only Scan`，取决于查询列、索引覆盖情况和可见性地图。

## 10. 综合案例：库存扣减

错误写法：

```sql
SELECT stock FROM products WHERE id = 1;

-- 应用判断 stock > 0

UPDATE products
SET stock = stock - 1
WHERE id = 1;
```

并发下可能超卖。

推荐写法一：单条原子 UPDATE。

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 1
  AND stock > 0
RETURNING id, stock;
```

如果返回 0 行，说明库存不足。

推荐写法二：显式锁。

```sql
BEGIN;

SELECT stock
FROM products
WHERE id = 1
FOR UPDATE;

UPDATE products
SET stock = stock - 1
WHERE id = 1
  AND stock > 0;

COMMIT;
```

优先选择单条原子 UPDATE，因为更短、更清晰、锁持有时间更短。

## 11. 必会排查 SQL

查看活动连接：

```sql
SELECT
  pid,
  usename,
  state,
  wait_event_type,
  wait_event,
  now() - query_start AS query_age,
  query
FROM pg_stat_activity
ORDER BY query_start;
```

查看长事务：

```sql
SELECT
  pid,
  state,
  now() - xact_start AS xact_age,
  query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_age DESC;
```

查看表统计：

```sql
SELECT
  relname,
  seq_scan,
  idx_scan,
  n_live_tup,
  n_dead_tup,
  last_analyze,
  last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

查看索引使用情况：

```sql
SELECT
  relname AS table_name,
  indexrelname AS index_name,
  idx_scan,
  idx_tup_read,
  idx_tup_fetch
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC;
```

查看慢 SQL 统计，需要 `pg_stat_statements`：

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT
  query,
  calls,
  total_exec_time,
  mean_exec_time,
  rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

### 练习一：观察 MVCC

开两个终端连接同一个数据库。

终端 A：

```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM users WHERE id = 1;
```

终端 B：

```sql
UPDATE users
SET name = 'Changed'
WHERE id = 1;
COMMIT;
```

终端 A：

```sql
SELECT * FROM users WHERE id = 1;
COMMIT;
SELECT * FROM users WHERE id = 1;
```

观察事务内外看到的数据是否不同。

### 练习二：观察锁等待

```sql
BEGIN;
```

终端 B：

终端 C：

```sql
SELECT
  pid,
```

然后在终端 A 执行：


观察终端 B 是否继续执行。

### 练习三：对比索引前后

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM transactions
WHERE user_id = 1
ORDER BY occurred_at DESC, id DESC
LIMIT 20;
```

删除索引后观察计划：

```sql
DROP INDEX IF EXISTS idx_transactions_user_time;
```

重新创建：

```sql
CREATE INDEX idx_transactions_user_time
ON transactions (user_id, occurred_at DESC, id DESC);
```

再次执行 `EXPLAIN (ANALYZE, BUFFERS)`，比较：

- 执行时间
- 扫描方式
- buffer 数量
- 是否需要排序

## 13. 最重要的心智模型

表：

```text
表是很多数据页，更新会产生行版本，不是简单覆盖。
```

索引：

```text
索引是为查询准备的访问路径，不是给字段贴标签。
```

JOIN：

```text
JOIN 的性能取决于输入规模、连接算法、索引和统计信息。
```

EXPLAIN：

```text
不要猜数据库怎么跑，要看执行计划。
```

事务：

```text
事务定义一致性边界，越短越好。
```

锁：

```text
锁不是坏事，等待太久才是问题。
```

MVCC：

```text
MVCC 用多版本换并发能力，也带来 VACUUM 和表膨胀问题。
```

查询优化：

```text
先减少数据，再选择访问路径，最后才考虑配置和硬件。
```
