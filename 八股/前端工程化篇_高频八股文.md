## 1. 基础概念与模块化 

### 1.1 什么是前端工程化？

**考点**：工程化核心理念

**定义**：将软件工程的方法和思想应用到前端开发中，通过工具化、自动化、规范化来提升开发效率、代码质量和可维护性。

**前端工程化的四大要素**：

| 要素 | 说明 | 工具示例 |
|-----|------|---------|
| **模块化** | 将代码拆分为独立、可复用的模块 | ES Module、CommonJS |
| **组件化** | 将UI拆分为独立可复用的组件 | React、Vue组件 |
| **规范化** | 制定并执行开发规范 | ESLint、Prettier |
| **自动化** | 自动化重复性工作 | 构建工具、CI/CD |

**为什么需要工程化**：

- 提升开发效率（热更新、自动化构建）
- 保证代码质量（lint、类型检查、测试）
- 优化产物性能（压缩、合并、Tree-shaking）
- 团队协作规范化

---

### 1.2 模块化、组件化、模块组件化的区别？

**考点**：核心概念辨析

**模块化**：侧重于**代码逻辑**的拆分，将一段复杂的逻辑拆分为多个独立文件

- JS模块：`export/import`
- CSS模块：`@import`
- 功能独立、可复用

**组件化**：侧重于**UI界面**的拆分，将页面拆分为独立的UI部件

- 包含HTML、CSS、JS的完整结构
- 有自己的状态和生命周期
- 可复用、可组合

**模块组件化**：将模块化的思想应用到组件开发中

```typescript
// 模块：纯逻辑，无UI
export function formatDate(date: Date): string { }

// 组件：逻辑 + UI
export function DatePicker({ value, onChange }) { }

// 模块组件化：组件内部也采用模块化思想
// DatePicker/index.tsx      - 组件入口
// DatePicker/Picker.tsx     - 主组件
// DatePicker/Calendar.tsx   - 日历模块
// DatePicker/Input.tsx      - 输入模块
```

### 1.3 CommonJS、AMD、CMD、ES Module的区别？

**考点**：模块系统演进

| 规范 | 加载方式 | 代表框架 | 特点 |
|-----|---------|---------|------|
| **CommonJS** | 同步 | Node.js | `module.exports` / `require()` |
| **AMD** | 异步 | RequireJS | 提前声明依赖 |
| **CMD** | 异步 | SeaJS | 懒加载依赖 |
| **ES Module** | 同步/异步 | 现代浏览器 | `import` / `export` |

**CommonJS**：

```javascript
// 导出
module.exports = { name: 'foo' }
// 或
exports.name = 'foo'

// 导入
const foo = require('./foo')
```

**AMD (Asynchronous Module Definition)**：

```javascript
define(['./a', './b'], function(a, b) {
  return { result: a.value + b.value }
})
require(['./app'], function(app) {
  app.init()
})
```

**CMD (Common Module Definition)**：

```javascript
define(function(require, exports, module) {
  var a = require('./a')
  var b = require('./b') // 懒加载
  module.exports = { result: a.value + b.value }
})
```

**ES Module**：

```typescript
// 命名导出
export const name = 'foo'
export function greet() { }

// 默认导出
export default function() { }

// 导入
import { name, greet } from './foo'
import MyFunc from './foo'
import * as all from './foo'
```

**关键区别**：

- **CommonJS**：运行时同步加载，导出的是值的拷贝
- **ES Module**：编译时静态分析，导出的是值的引用（只读绑定）
- ES Module 可以实现 **Tree Shaking**，CommonJS 不行

### 1.4 Tree Shaking是什么？它是如何工作的？

**考点**：构建优化

**定义**：移除JavaScript中未使用的代码（dead code）

**原理**：

1. **静态分析**：ES Module在编译时就能确定导入导出关系
2. **依赖图构建**：构建模块依赖图
3. **标记未使用**：从入口开始，标记所有被使用的导出
4. **移除**：删除未被标记的代码

**条件**：

- 必须使用 ES Module（CommonJS 不支持）
- 构建工具需要支持（Webpack Rollup Vite）
- 需要开启 `sideEffects` 配置

**示例**：

```typescript
// math.js
export function add(a, b) { return a + b }
export function multiply(a, b) { return a * b } // 未使用

// main.js
import { add } from './math'
console.log(add(1, 2))
// 构建时 multiply 会被移除
```

**sideEffects配置**：

```json
// package.json
{
  "sideEffects": [
    "*.css",
    "./src/polyfill.js"
  ]
}
```

### 1.5 前端模块化的演进历程？

**考点**：历史理解

**阶段一：混沌期**
- 所有代码写在一个文件
- 命名空间约定（如 `App.Utils`）

**阶段二：文件级模块化**
- CommonJS（Node.js 2009）
- 同步加载，适合服务端

**阶段三：前端模块化**
- AMD/CMD（ RequireJS、SeaJS）
- 异步加载，适合浏览器

**阶段四：统一模块化**
- ES Module（ES6 2015）
- 语言层面支持，统一浏览器和服务端

**阶段五：构建工具时代**
- Webpack、Rollup、Vite
- 模块化 + 打包 + 优化

## 2. 构建工具 

### 2.1 Webpack的工作原理？

**考点**：核心原理

**核心概念**：

| 概念 | 说明 |
|-----|------|
| **Entry** | 入口文件，Webpack从这里开始构建依赖图 |
| **Output** | 输出目录和文件名配置 |
| **Loader** | 处理非JS文件，转换为有效模块 |
| **Plugin** | 扩展Webpack功能，执行更广的任务 |
| **Chunk** | 代码块，优化分割输出 |
| **Module** | 模块，所有被处理的资源 |

**构建流程**：

```
1. 初始化 (Initialization)
   └─ 读取配置，初始化compiler

2. 编译 (Compilation)
   ├─ 从Entry开始递归分析依赖
   ├─ 使用Loader处理各类文件
   └─ 构建模块依赖图

3. 生成 (Emission)
   ├─ 使用Plugin优化和修改
   ├─ 生成chunk
   └─ 输出到文件系统
```

**Webpack 5的变化**：

- 持久化缓存（提升二次构建速度）
- 模块联邦（Module Federation）
- 更好的Tree Shaking
- 内置Asset Module

### 2.2 Webpack的Loader和Plugin有什么区别？

**考点**：核心机制对比

| 特性 | Loader | Plugin |
|-----|-------|-------|
| **作用时机** | 转换特定类型文件 | 贯穿整个构建生命周期 |
| **处理方式** | 单一文件转换 | 操作webpack内部实例 |
| **执行顺序** | 链式调用（从右到左） | 按注册顺序执行 |
| **配置方式** | module.rules | plugins数组 |
| **返回值** | 返回转换后的模块 | 一般无返回值 |

**常见Loader**：

```javascript
module.exports = {
  module: {
    rules: [
      {
        test: /\.css$/,
        use: ['style-loader', 'css-loader']
        // 执行顺序：css-loader → style-loader（从右到左）
      },
      {
        test: /\.ts$/,
        use: 'ts-loader'
      },
      {
        test: /\.(png|jpg)$/,
        type: 'asset/resource'
      }
    ]
  }
}
```

**常见Plugin**：

```javascript
const HtmlWebpackPlugin = require('html-webpack-plugin')
const MiniCssExtractPlugin = require('mini-css-extract-plugin')

module.exports = {
  plugins: [
    new HtmlWebpackPlugin({ template: './src/index.html' }),
    new MiniCssExtractPlugin({ filename: 'css/[name].css' }),
    new webpack.DefinePlugin({ 'process.env.NODE_ENV': JSON.stringify('production') })
  ]
}
```

**自定义Plugin结构**：

```javascript
class MyPlugin {
  apply(compiler) {
    compiler.hooks.emit.tap('MyPlugin', (compilation) => {
      // 在emit阶段做些什么
    })
  }
}
```

### 2.3 Webpack如何实现代码分割（Code Splitting）？

**考点**：优化策略

**方式一：Entry Points（入口分割）**

```javascript
module.exports = {
  entry: {
    main: './src/index.js',
    vendor: './src/vendor.js'
  }
}
```

**方式二：SplitChunks（提取公共代码）**

```javascript
module.exports = {
  optimization: {
    splitChunks: {
      chunks: 'all',
      cacheGroups: {
        vendors: {
          test: /[\\/]node_modules[\\/]/,
          name: 'vendors',
          priority: -10
        },
        common: {
          minChunks: 2,
          priority: -20,
          reuseExistingChunk: true
        }
      }
    }
  }
}
```

**方式三：动态导入（Dynamic Import）**

```typescript
// 路由懒加载
const Login = () => import('./Login')

// 组件懒加载
const BigChart = () => import(/* webpackChunkName: "chart" */ './BigChart')

// 条件加载
if (condition) {
  const module = await import('./heavy.js')
}
```

**方式四：内联Chunk**

```javascript
module.exports = {
  optimization: {
    runtimeChunk: 'single',
    splitChunks: {
      cacheGroups: {
        vendor: {
          test: /[\\/]node_modules[\\/]/,
          name: 'vendors',
          chunks: 'all'
        }
      }
    }
  }
}
```

### 2.4 Webpack的热更新（HMR）原理？

**考点**：开发体验优化

**原理图**：

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   Browser   │◄───►│   Webpack   │◄───►│    Files    │
│             │     │   Dev Server │     │             │
└─────────────┘     └─────────────┘     └─────────────┘
       │                   │
       │    WebSocket       │
       │◄──────────────────►│
       │                    │
   HMR Runtime         HMR Server
```

**流程**：

1. **文件变化**：代码文件发生变化
2. **重新编译**：Webpack监听到变化，重新编译
3. **发送补丁**：通过WebSocket发送更新的模块
4. **HMR Runtime**：JavaScript运行时替换对应模块
5. **局部更新**：页面局部刷新，保留状态

**开启方式**：

```javascript
// webpack.config.js
const webpack = require('webpack')
module.exports = {
  devServer: {
    hot: true
  },
  plugins: [
    new webpack.HotModuleReplacementPlugin()
  ]
}
```

**注意**：
- CSS更新：直接替换，无缝衔接
- JS更新：需要业务代码配合 `module.hot.accept()`

### 2.5 Vite和Webpack的区别？

**考点**：构建工具对比

| 特性 | Webpack | Vite |
|-----|--------|------|
| **开发服务器** | DevServer + Webpack-dev-middleware | 原生ESM + Koa |
| **构建方式** | 先打包，再启动 | 按需编译，立即启动 |
| **热更新** | 全部重新编译 | 按需更新（毫秒级） |
| **生产构建** | Bundler打包 | Rollup打包 |
| **依赖预购** | 需要单独配置 | 内置 `@vitejs/plugin-legacy` |
| **生态** | 成熟、插件丰富 | 快速崛起 |

**Webpack构建流程**：

```
启动 → 读取配置 → 编译所有模块 → 生成bundle → 启动服务器
              ↑ 这步很慢
```

**Vite构建流程**：

```
启动 → 启动服务器 → 按需编译请求的文件 → 响应
        ↑
     毫秒级
```

**Vite为什么快**：

1. **利用ESM**：现代浏览器原生支持ES Module，直接请求文件
2. **按需编译**：只编译当前请求的文件
3. **预构建依赖**：使用 `esbuild` 预构建依赖（Go编写，速度极快）
4. **跳过打包**：开发环境不打包，利用浏览器按需加载

### 2.6 Rollup是什么？它和Webpack有什么不同？

**考点**：打包工具对比

**Rollup特点**：

| 特性 | 说明 |
|-----|------|
| **设计目标** | 库和框架的打包 |
| **Tree Shaking** | 极致优化 |
| **输出格式** | ES、CommonJS、UMD、IIFE |
| **代码简洁** | 打包结果干净 |

**Rollup示例**：

```javascript
// rollup.config.js
export default {
  input: 'src/index.js',
  output: {
    file: 'dist/bundle.js',
    format: 'es',
    sourcemap: true
  }
}
```

**Webpack vs Rollup 使用场景**：

| 场景 | 推荐工具 | 原因 |
|-----|---------|------|
| 应用开发 | Webpack | 功能丰富、生态完善 |
| 库/组件开发 | Rollup | 输出干净、Tree Shaking好 |
| 框架开发 | Rollup + 自定义 | 需要极致的输出控制 |

**注意**：Vite生产构建使用Rollup，所以Vite项目实际是结合了两者优点。

### 2.7 Babel是什么？它是如何工作的？

**考点**：JavaScript编译器

**定义**：将新版本JavaScript代码转换为向后兼容的旧版本代码

**核心概念**：

| 概念 | 说明 |
|-----|------|
| **Babel CLI** | 命令行工具 |
| **Babel Core** | 核心API |
| **Presets** | 预设（一组插件集合） |
| **Plugin** | 具体转换规则 |
| **Polyfill** | 填补浏览器缺失的功能 |

**配置示例**：

```javascript
// .babelrc 或 babel.config.js
{
  "presets": [
    ["@babel/preset-env", {
      targets: {
        chrome: "80",
        ie: "11"
      },
      useBuiltIns: "usage",
      corejs: 3
    }],
    "@babel/preset-react",
    "@babel/preset-typescript"
  ],
  "plugins": [
    "@babel/plugin-proposal-class-properties",
    ["@babel/plugin-transform-runtime", { "regenerator": false }]
  ]
}
```

**Babel工作流程**：

```
代码 → 解析（Parser）→ AST → 转换（Transform）→ AST → 生成（Generator）→ 代码
```

**与TypeScript的区别**：

| 工具 | 作用 | 类型检查 |
|-----|------|---------|
| Babel | 转译代码 | ❌ |
| TypeScript | 类型检查 + 转译 | ✅ |

## 3. 包管理器 

### 3.1 npm、yarn、pnpm的区别？

**考点**：包管理器对比

| 特性 | npm | yarn | pnpm |
|-----|-----|------|------|
| **诞生时间** | 2010 | 2016 | 2017 |
| **作者** | npm公司 | Facebook | npm前员工 |
| **安装速度** | 较慢 | 快 | 极快 |
| **磁盘空间** | 大 | 大 | 小（内容寻址） |
| **依赖结构** | 扁平 | 扁平 | 非扁平（store） |
| **lock文件** | package-lock.json | yarn.lock | pnpm-lock.yaml |
| **幽灵依赖** | 有 | 有 | 无 |

**npm安装机制**：

```
node_modules/
├── foo/
│   └── node_modules/
│       └── bar/     # 嵌套依赖
└── baz/
```

**pnpm安装机制**：

```
node_modules/
├── .pnpm/
│   ├── foo/
│   └── bar/
└── foo  → .pnpm/foo
└── baz  → .pnpm/baz
```

**pnpm优势**：

1. **节省磁盘空间**：依赖只存储一份
2. **避免幽灵依赖**：无法访问未声明的依赖
3. **安装速度快**：复用同一份依赖

**命令对比**：

| 功能 | npm | yarn | pnpm |
|-----|-----|------|------|
| 安装 | `npm install` | `yarn` | `pnpm install` |
| 添加依赖 | `npm install pkg` | `yarn add pkg` | `pnpm add pkg` |
| 删除依赖 | `npm uninstall pkg` | `yarn remove pkg` | `pnpm remove pkg` |
| 全局安装 | `npm install -g pkg` | `yarn global add pkg` | `pnpm add -g pkg` |
| 清理缓存 | `npm cache clean` | `yarn cache clean` | `pnpm store prune` |

### 3.2 什么是Peer Dependencies？为什么需要它？

**考点**：依赖管理

**问题场景**：

```json
// my-ui-lib/package.json
{
  "dependencies": {
    "react": "^18.0.0"
  }
}

// consumer-app/node_modules/my-ui-lib/node_modules/react  ← npm3开始会提升
```

**Peer Dependencies定义**：

声明依赖包需要的**对等依赖**，由使用者提供

```json
// my-ui-lib/package.json
{
  "peerDependencies": {
    "react": ">=17.0.0",
    "react-dom": ">=17.0.0"
  }
}
```

**作用**：

1. **避免重复安装**：插件复用宿主应用的依赖
2. **版本对齐**：确保插件和宿主使用相同版本的依赖
3. **警告机制**：未安装对等依赖时发出警告

**常见使用场景**：

- UI组件库（需要React/Vue）
- Babel插件（需要@babel/core）
- ESLint插件（需要ESLint）

### 3.3 什么是Monorepo？有什么工具可以支持？

**考点**：项目结构管理

**定义**：在一个仓库中管理多个包/项目

**解决的问题**：

- 代码复用困难
- 版本管理混乱

**Monorepo工具对比**：

| 工具 | 特点 | 代表项目 |
|-----|------|---------|
| **Lerna** | 老牌、功能完善 | create-react-app |
| **Yarn Workspaces** | 简单、与yarn集成 | React Native |
| **PNPM Workspaces** | 性能好、与pnpm集成 | Vite |
| **Nx** | 强大、增量构建 | - |
| **Turborepo** | Vercel出品、缓存强大 | - |

**pnpm workspaces示例**：

```yaml
# pnpm-workspace.yaml
packages:
  - 'packages/*'
  - 'apps/*'
```

```json
// packages/ui/package.json
{
  "name": "@myorg/ui",
  "version": "1.0.0",
  "dependencies": {
    "@myorg/utils": "workspace:*"
  }
}
```

**安装命令**：

```bash
pnpm install   # 自动安装所有workspace
pnpm add react --filter @myorg/ui  # 只给特定包安装
```

## 4. 代码质量与规范 

### 4.1 ESLint是什么？如何配置？

**考点**：代码质量工具

**定义**：可配置的JavaScript代码检查工具，发现并修复问题

**核心概念**：

| 概念 | 说明 |
|-----|------|
| **Parser** | 解析器（默认Espree） |
| **Rules** | 规则 |
| **Plugins** | 插件（一组预设好的规则） |
| **Configs/Presets** | 预设配置 |
| **Processor** | 处理器 |

**配置方式**：

```javascript
// .eslintrc.js
module.exports = {
  parser: '@typescript-eslint/parser',
  extends: [
    'eslint:recommended',
    'plugin:@typescript-eslint/recommended',
    'plugin:react/recommended',
    'plugin:react-hooks/recommended',
    'prettier' // 最后关闭冲突规则
  ],
  plugins: ['@typescript-eslint', 'react', 'react-hooks'],
  rules: {
    'no-console': 'warn',
```

### 5.3 如何测试React/Vue组件？

**考点**：组件测试

**React Testing Library（推荐）**：

```typescript
import { render, screen, fireEvent } from '@testing-library/react'
import { describe, it, expect } from 'vitest'
import { LoginForm } from './LoginForm'

describe('LoginForm', () => {
  it('should render login form', () => {
    render(<LoginForm onSubmit={vi.fn()} />)
    expect(screen.getByLabelText('Username')).toBeInTheDocument()
    expect(screen.getByLabelText('Password')).toBeInTheDocument()
  })

  it('should call onSubmit with values', async () => {
    const onSubmit = vi.fn()
    render(<LoginForm onSubmit={onSubmit} />)

    fireEvent.change(screen.getByLabelText('Username'), {
      target: { value: 'test' }
    })
    fireEvent.change(screen.getByLabelText('Password'), {
      target: { value: '123456' }
    })
    fireEvent.click(screen.getByRole('button', { name: 'Login' }))

    expect(onSubmit).toHaveBeenCalledWith({
      username: 'test',
      password: '123456'
    })
  })
})
```

**Vue Test Utils**：

```typescript
import { mount } from '@vue/test-utils'
import { describe, it, expect } from 'vitest'
import { LoginForm } from './LoginForm.vue'

describe('LoginForm', () => {
  it('renders login form', () => {
    const wrapper = mount(LoginForm, {
      props: { onSubmit: vi.fn() }
    })
    expect(wrapper.find('input[type="text"]').exists()).toBe(true)
  })

  it('emits submit event', async () => {
    const wrapper = mount(LoginForm)
    await wrapper.find('input[type="text"]').setValue('test')
    await wrapper.find('form').trigger('submit')
    expect(wrapper.emitted('submit')).toBeTruthy()
  })
})
```

**测试最佳实践**：

1. 测试行为而非实现细节
2. 使用 `userEvent` 代替 `fireEvent`（更接近真实用户）
3. 避免测试内部状态
4. 使用语义化查询（`getByRole`、`getByLabelText`）

### 5.4 什么是Mock？如何进行模块Mock？

**考点**：测试隔离

**Jest Mock**：

```typescript

  fetchUser: vi.fn().mockResolvedValue({ id: 1, name: 'Tom' })

it('should call callback after 1s', async () => {
  vi.useFakeTimers()

  vi.useRealTimers()
})
```

### 6.1 什么是CI/CD？

**考点**：DevOps基础概念

**CI (Continuous Integration)**：持续集成

### 8.3 前端如何做权限控制？

**考点**：安全与架构

**权限类型**：

| 类型 | 说明 | 实现方式 |
|-----|------|---------|
| **路由权限** | 页面访问控制 | 路由守卫 |
| **按钮权限** | 操作权限控制 | 自定义指令 |
| **接口权限** | 数据访问控制 | 请求拦截 |
| **数据权限** | 字段级控制 | 后端过滤 |

**路由权限实现**：

```typescript
// 路由守卫
router.beforeEach(async (to, from, next) => {
  const token = localStorage.getItem('token')
  const userRole = store.state.user.role

  if (to.meta.requiresAuth && !token) {
    next('/login')
  } else if (to.meta.role && !to.meta.role.includes(userRole)) {
    next('/403')
  } else {
    next()
  }
})

// 路由配置
const routes = [
  {
    path: '/admin',
    component: Admin,
    meta: { requiresAuth: true, role: ['admin'] }
  }
]
```

**按钮权限实现**：

```typescript
// 权限指令
const permission = {
  mounted(el, binding) {
    const { value } = binding
    const userPermissions = store.state.user.permissions

    if (value && !userPermissions.includes(value)) {
      el.parentNode?.removeChild(el)
    }
  }
}

// 使用
<el-button v-permission="'user:delete'">删除</el-button>
```

**接口权限实现**：

```typescript
// 请求拦截
axios.interceptors.request.use((config) => {
  const token = localStorage.getItem('token')
  if (token) {
    config.headers.Authorization = `Bearer ${token}`
  }
  return config
})

// 响应拦截
axios.interceptors.response.use(
  (response) => response,
  (error) => {
    if (error.response?.status === 401) {
      // token过期，跳转登录
      router.push('/login')
    } else if (error.response?.status === 403) {
      // 无权限
      router.push('/403')
    }
    return Promise.reject(error)
  }
)
```

### 8.4 前端如何做国际化（i18n）？

**考点**：多语言支持

**主流方案对比**：

| 方案 | 特点 | 生态 |
|-----|------|------|
| **react-intl** | FormatJS核心，功能强 | React |
| **react-i18next** | i18next生态系统 | 通用 |
| **vue-i18n** | Vue官方 | Vue |
| **vue3-i18n** | Vue3版本 | Vue3 |

**react-i18next示例**：

```typescript
// i18n/index.ts
import i18n from 'i18next'
import { initReactI18next } from 'react-i18next'
import zhCN from './locales/zh-CN.json'
import enUS from './locales/en-US.json'

i18n.use(initReactI18next).init({
  resources: {
    'zh-CN': { translation: zhCN },
    'en-US': { translation: enUS }
  },
  lng: 'zh-CN',
  fallbackLng: 'zh-CN',
  interpolation: { escapeValue: false }
})

export default i18n
```

```json
// locales/zh-CN.json
{
  "nav": {
    "home": "首页",
    "about": "关于"
  },
  "user": {
    "greeting": "你好，{{name}}"
  }
}
```

```typescript
// 使用
import { useTranslation } from 'react-i18next'

function Nav() {
  const { t, i18n } = useTranslation()

  return (
    <nav>
      <a>{t('nav.home')}</a>
      <button onClick={() => i18n.changeLanguage('en-US')}>EN</button>
    </nav>
  )
}
```

**动态加载语言包**：

```typescript
const loadLanguage = async (lang: string) => {
  const module = await import(`./locales/${lang}.json`)
  i18n.addResourceBundle(lang, 'translation', module.default, true, true)
}
```

## 附录：常见面试问题

### 1. Webpack构建流程？

1. 初始化：读取配置，初始化compiler
2. 编译：从entry开始递归分析依赖
3. 使用loader处理各类文件
4. 生成chunk和输出文件

### 2. Webpack如何做性能优化？

- 代码分割（splitChunks）
- Tree Shaking
- 懒加载
- 压缩混淆
- 依赖预构建
- 缓存优化（contenthash）

### 3. Vite为什么比Webpack快？

- 利用ESM，按需编译
- esbuild预构建依赖
- 无需打包，开发环境直接请求文件

### 4. 前端工程化的核心目标？

- 自动化：减少人工操作
- 规范化：统一开发标准
- 模块化：提升代码复用
- 质量保障：确保代码质量
