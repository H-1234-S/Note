## 1. 浏览器基础架构

### 1.1 什么是同源策略？为什么要有同源策略？
**考点**：浏览器安全机制的核心概念

**同源定义**：协议、域名、端口号三者完全相同

- `http://example.com` 和 `https://example.com` ❌（协议不同）

- `http://example.com:80` 和 `http://example.com:8080` ❌（端口不同）

- `http://example.com` 和 `http://www.example.com` ❌（域名不同）

**为什么要同源策略**：

- 防止恶意网站读取其他网站的敏感数据

- 保护Cookie、LocalStorage等用户数据

- 防止CSRF攻击

---

### 1.2 浏览器的主要进程有哪些？
**考点**：浏览器的多进程架构

**Chromium浏览器的多进程模型**：

1. **浏览器进程（Browser Process）**

   - 控制主界面：地址栏、前进后退按钮

   - 管理其他进程的创建和销毁

   - 处理文件存储、网络请求等

2. **渲染进程（Renderer Process）**

   - 每个标签页通常有独立的渲染进程（进程隔离）

   - 负责HTML解析、CSS样式计算、布局、绘制

   - 执行JavaScript代码

   - 管理DOM树、CSSOM树

3. **GPU进程（GPU Process）**

   - 专门处理3D绘制、图像解码等需要GPU加速的任务

   - 所有标签页共享同一个GPU进程

4. **网络进程（Network Process）**

   - 处理所有网络请求

   - 资源缓存、HTTP协议处理

5. **插件进程（Plugin Process）**

   - 每个插件运行在独立进程，崩溃不影响浏览器

**为什么采用多进程架构**：

- 安全性：进程隔离，恶意网站无法影响其他标签页

- 稳定性：单个标签页崩溃不会导致整个浏览器崩溃

- 性能：充分利用多核CPU

---

### 1.3 浏览器内核是什么？有哪些常见的浏览器内核？
**考点**：浏览器的核心渲染引擎

**浏览器内核** = 渲染引擎 + JavaScript引擎

**常见渲染引擎**：

- **Blink**（Chrome 28+、Edge、Opera、新版Safari部分采用）

- **WebKit**（Safari、老版Chrome、Opera）

- **Gecko**（Firefox）

- **Trident**（IE，已废弃）

- **EdgeHTML**（老版Edge，已改为Blink）

**常见JS引擎**：

- **V8**（Chrome、Node.js、Edge）

- **SpiderMonkey**（Firefox）

- **JavaScriptCore**（Safari）

- **Chakra**（老版Edge）

## 2. 页面加载过程

### 2.1 从输入URL到页面展示的完整流程
**考点**：浏览器工作原理的经典问题

**完整流程**：

1. **DNS解析**

   - 浏览器缓存 → 系统缓存 → 路由器缓存 → ISP DNS → 根域名服务器

   - 最终获取IP地址

2. **建立TCP连接**

   - 三次握手（SYN → SYN+ACK → ACK）

3. **发送HTTP请求**

   - 请求报文（请求行、请求头、空行、请求体）

4. **服务器处理并响应**

   - 服务器接收请求、处理、返回响应

   - 响应报文（状态行、响应头、空行、响应体）

5. **浏览器解析渲染**

   - 解析HTML构建DOM树

   - 解析CSS构建CSSOM树

   - 合并DOM和CSSOM生成渲染树（Render Tree）

   - 布局（Layout/Reflow）：计算元素位置和大小

   - 绘制（Paint）：生成像素数据

   - 合成（Composite）：合并图层并显示

6. **TCP连接释放**

   - 四次挥手（FIN → ACK → FIN → ACK）

**面试加分点**：

- 提到HTTPS的TLS握手过程

- 说清楚关键渲染路径（Critical Rendering Path）

- 了解浏览器预加载、预解析等优化机制

---

### 2.2 什么是关键渲染路径（Critical Rendering Path）？

**考点**：性能优化的核心概念

**定义**：浏览器从接收HTML、CSS、JS到渲染页面所经历的一系列步骤

**关键步骤**：

**关键步骤**：

1. 构建DOM树（HTML → DOM）

2. 构建CSSOM树（CSS → CSSOM）

3. 构建渲染树（DOM + CSSOM → Render Tree）

4. 布局（计算每个节点的几何信息）

5. 绘制（填充像素）

6. 合成（图层合成）

**优化关键**：

- 减少关键资源数量

- 缩短关键资源大小

- 优化关键路径长度（减少往返次数）

---

### 2.3 浏览器的缓存机制有哪些？

**考点**：性能优化、网络相关

**浏览器缓存分类**：

1. **强缓存**

   - 不向服务器发送请求，直接使用本地缓存

   - HTTP 1.0：`Expires`（绝对时间）

   - HTTP 1.1：`Cache-Control`（相对时间，优先级更高）

2. **协商缓存**

   - 向服务器发送请求，服务器决定是否使用缓存

   - `Last-Modified` / `If-Modified-Since`

   - `ETag` / `If-None-Match`（优先级更高）
     ```http
     // 首次请求
     ETag: "5d8c72a5edda8d6a:3232"

     // 再次请求
     If-None-Match: "5d8c72a5edda8d6a:3232"
     ```

**缓存优先级**：

强缓存 > 协商缓存 > 直接请求

**面试加分点**：

- 理解`Cache-Control`的各种指令

- 知道`ETag`比`Last-Modified`更精确

- 了解Service Worker缓存（PWA）

## 3. 渲染原理

### 3.1 浏览器渲染流程（重排重绘）

**考点**：性能优化的核心

**渲染五步曲**：
```
1. 解析HTML → DOM树
2. 解析CSS → CSSOM树
3. 合并 → 渲染树（Render Tree）
4. 布局（Layout/Reflow）→ 计算位置大小
5. 绘制（Paint）→ 生成像素
6. 合成（Composite）→ 图层合并
```

**浏览器渲染流程全解析**

1. 解析 HTML → DOM 树浏览器从上到下读取 HTML 文档。将 HTML 标签转换为一个个“节点”（Nodes），并连接成一颗DOM（Document Object Model）树。
   
    注意： 这个过程是渐进的，浏览器不需要等到 HTML 全部下载完，解析到多少就构建多少。

2. 解析 CSS → CSSOM 树

浏览器在解析 HTML 的过程中，如果遇到 link标签或 style 标签，就会开始解析 CSS。

• 动作： 将 CSS 代码转换为CSSOM（CSS Object Model）树。

• 特点： CSSOM 会计算出每个节点的具体样式（继承、层叠等规则在这里生效）。

3. 合并 → 渲染树 (Render Tree)

将 DOM 树和 CSSOM 树结合在一起。

• 动作： 遍历 DOM 树中的可见节点，并匹配对应的 CSS 样式。

• 关键点： 不可见节点（如 head、display: none 的元素）不会出现在渲染树中。但 visibility: hidden 的元素会出现在树里，因为它虽然看不见但占据空间。

4. 布局 (Layout/Reflow) → 计算位置大小

有了渲染树，浏览器需要知道每个节点在屏幕上的确切位置和大小。

• 动作： 浏览器根据屏幕视口（Viewport）的大小，计算出每个盒子（Box Model）的几何属性。

• 术语： 当这个过程重复发生时（比如你改了元素的宽度），就叫回流（Reflow）。

5. 绘制 (Paint) → 生成像素

将计算好的盒子转换为屏幕上的实际像素（颜色、背景、边框、阴影等）。

• 动作： 浏览器会将元素拆分成不同的“层”（Layers）进行绘制，就像 PS 里的图层一样。

• 术语： 当你只改变颜色、不改变位置大小时，会触发重绘（Repaint）。

6. 合成 (Composite) → 图层合并

这是最后一步。由于页面可能是分层绘制的，浏览器需要将这些层按照正确的顺序叠加在一起。

• 动作： GPU 将多个图层合成并最终显示在屏幕上。

• 优化： 使用 transform 或 opacity 等属性可以跳过前面的布局和绘制，直接在合成阶段处理，这就是常说的GPU 加速。

---

### 3.2 什么是重排（Reflow/回流）和重绘（Repaint）？

**考点**：性能优化必问

**重排（Reflow/回流）**：

- 当页面布局或几何属性改变时发生

- 重新计算元素位置、大小

- **触发条件**：

  - 添加/删除可见DOM元素

  - 元素位置、尺寸改变（width、height、padding、margin）

  - 内容改变（文字、图片）

  - 浏览器窗口大小改变

  - 获取某些属性（offsetTop、clientWidth、getComputedStyle等）

**重绘（Repaint）**：

- 当元素样式改变但不影响布局时发生

- **触发条件**：

  - 改变颜色（color、background-color）

  - 改变visibility

  - 改变outline、box-shadow

**关系**：

- 重排必定触发重绘

- 重绘不一定触发重排

**性能影响**：

- 重排 > 重绘（重排成本更高）

---

### 3.3 如何减少重排重绘？

**考点**：性能优化实践

**优化策略**：

1. **避免逐条修改样式**
   ```javascript
   // ❌ 不好
   el.style.width = '100px';
   el.style.height = '100px';
   el.style.color = 'red';

   // ✅ 好
   el.className = 'new-class';
   // 或
   el.style.cssText = 'width:100px;height:100px;color:red';
   ```

2. **使用DocumentFragment或innerHTML批量操作DOM**
   ```javascript
   // ❌ 不好
   for (let i = 0; i < 1000; i++) {
     ul.appendChild(document.createElement('li'));
   }

   // ✅ 好
   const fragment = document.createDocumentFragment();
   for (let i = 0; i < 1000; i++) {
     fragment.appendChild(document.createElement('li'));
   }
   ul.appendChild(fragment);
   ```

3. **使用CSS3硬件加速**
   ```css
   /* 使用transform、opacity等GPU加速属性 */
   .animate {
     transform: translateZ(0);  /* 触发GPU加速 */
     opacity: 0.5;
   }
   ```

4. **避免频繁读取会触发重排的属性**
   ```javascript
   // ❌ 不好 - 触发4次重排
   console.log(div.offsetTop);
   console.log(div.offsetLeft);
   console.log(div.offsetWidth);
   console.log(div.offsetHeight);

   // ✅ 好 - 只触发1次重排
   const rect = div.getBoundingClientRect();
   console.log(rect.top, rect.left, rect.width, rect.height);
   ```

5. **使用虚拟化列表**（长列表优化）

6. **使用防抖节流**（resize、scroll事件）

### 3.4 什么是图层（Layer）？如何触发图层？
**考点**：渲染优化进阶

**图层概念**：

- 浏览器为了提升渲染性能，将页面分成多个图层

- 某个图层的变化不会影响其他图层

**触发图层的条件**（提升为合成层）：

- 3D或透视变换（transform: translateZ(0), perspective）

- 使用加速视频解码的video元素

- 3D或混合插件（Flash）

- 对opacity、transform应用动画

- 拥有加速CSS过滤器（filter）

- 元素有包含复合层的后代节点

- 元素有z-index比它小且包含复合层的兄弟元素

**查看图层的方法**：

- Chrome DevTools → Layers面板

- `will-change: transform`（显式提升图层）

**注意**：图层过多会导致内存占用增加，需要权衡

### 3.5 什么是合成（Composite）？

**考点**：现代浏览器渲染优化

**定义**：将多个图层按照正确顺序合并成最终图像的过程

**合成优势**：

- 不触发重排和重绘

- 利用GPU加速，性能更高

- 动画更流畅

**合成属性**（不会触发重排重绘）：

- `transform`

- `opacity`


**最佳实践**：
``` css
/* 使用transform和opacity做动画 */
@keyframes slide {
  from { transform: translateX(0); opacity: 1; }
  to { transform: translateX(100px); opacity: 0.5; }
}
```

### 3.6 事件循环与渲染的关系
**考点**：JavaScript执行与渲染的时序

**关键点**：
1. **宏任务执行** → 渲染任务（如果需要）→ 下一个宏任务

2. 浏览器每帧（约16ms）最多执行一次渲染

3. `requestAnimationFrame` 在渲染前执行

4. `requestIdleCallback` 在空闲时执行

**执行顺序**：
```
宏任务 → 微任务 → 渲染（如果需要）→ 下一个宏任务
```

**代码示例**：
```javascript
setTimeout(() => {
  console.log('setTimeout');  // 宏任务
}, 0);

Promise.resolve().then(() => {
  console.log('Promise');  // 微任务
});

console.log('sync');  // 同步代码

// 输出顺序：sync → Promise → setTimeout
```

## 4. JavaScript引擎与执行

### 4.1 V8引擎的工作原理

**考点**：JavaScript执行机制

**V8引擎架构**：
```
1. Parse（解析） → AST（抽象语法树）
2. Ignition（解释器） → 字节码
3. TurboFan（编译器） → 优化后的机器码
```

**详解：**

1. Parse（解析） → AST（抽象语法树）
在引擎看代码之前，代码只是长长的字符串。**Parse** 的任务就是把这些字符串“读懂”并结构化。

 * **词法分析 (Lexical Analysis)**：把代码拆成一个个有意义的词（Tokens），比如 let, a, =, 10。

 * **语法分析 (Syntactic Analysis)**：根据语法规则，把这些词组成一棵树状结构，这就是 **AST (Abstract Syntax Tree)**。

> **为什么要变树？**
> 电脑没法直接理解一行行文本，但树状结构能清晰地表达逻辑嵌套关系（比如哪个函数属于哪个对象，哪个变量在哪个作用域）。


2. Ignition（解释器） → 字节码

- 有了 AST 后，**Ignition** 登场了。它不会直接把代码变成最底层的二进制机器码，而是先转换成 **Bytecode（字节码）**。

 * **字节码是什么？** 它是介于高级语言和机器码之间的一种“中间状态”。它比 JS 代码更接近底层，但又具有跨平台性。

 * **为什么要这样做？**

   - **启动快**：直接编译成优化后的机器码非常耗时，生成字节码则飞快。

   * **省内存**：字节码占用的空间比机器码小得多。

 3. TurboFan（编译器） → 优化后的机器码

- JavaScript 是动态类型的（比如一个变量一会儿是数字，一会儿又是字符串），这让运行效率很低。**TurboFan** 就是为了解决这个问题而存在的“性能加速器”。

 * **热点检测**：Ignition 在执行字节码时，会收集代码运行的信息（比如某个函数被调用了 1000 次，且每次传的都是整数）。

 * **JIT 编译 (Just-In-Time)**：如果某段代码是“热点代码”，TurboFan 就会把它的字节码直接编译成 **Optimized Machine Code（优化后的机器码）**。

 * **去优化 (Deoptimization)**：如果你突然改变了变量类型（比如给一直传整数的函数传了个字符串），TurboFan 会发现之前的优化失效了，于是把代码退回到字节码状态重新执行。

**优化策略**：

- **即时编译（JIT）**：解释执行 + 编译优化

- **内联缓存（Inline Cache）**：缓存属性访问

- **隐藏类（Hidden Class）**：优化对象属性访问

- **垃圾回收（GC）**：新生代（Scavenge）、老生代（Mark-Sweep + Mark-Compact）

**面试加分点**：

- 知道V8有Ignition解释器和TurboFan编译器

- 了解内联缓存和隐藏类的原理

- 知道垃圾回收的不同算法

### 4.2 什么是垃圾回收（GC）？V8的GC策略？
**考点**：内存管理

**GC算法**：

1. **标记清除（Mark-Sweep）**

   - 标记所有可达对象

   - 清除未标记对象

   - **缺点**：产生内存碎片

2. **标记整理（Mark-Compact）**

   - 标记后将存活对象移到一端

   - 避免内存碎片

3. **引用计数（Reference Counting）**

   - 统计对象引用次数

   - 引用为0时回收

   - **缺点**：无法解决循环引用

**V8的分代回收**：

- **新生代（New Space）**：Scavenge算法（From/To空间）

- **老生代（Old Space）**：Mark-Sweep + Mark-Compact

**V8内存限制**：

- 64位系统：约1.4GB

- 32位系统：约0.7GB

**避免内存泄漏的方法**：

- 及时清除定时器、事件监听

- 避免全局变量

- 使用WeakMap/WeakSet

- 大数据及时释放引用

---

### 4.3 什么是事件循环（Event Loop）？

**考点**：JavaScript核心机制

**浏览器环境的事件循环**：

**执行机制**：
```
1. 执行同步代码
2. 执行微任务队列（清空）
3. 执行渲染任务（如果需要）
4. 执行宏任务队列（取一个）
5. 回到步骤2
```

**宏任务（Macro Task）**：

- `setTimeout`、`setInterval`

- `requestAnimationFrame`

- I/O、UI交互事件

**微任务（Micro Task）**：

- `Promise.then/catch/finally`

- `MutationObserver`

- `queueMicrotask()`

- `process.nextTick()`（Node.js）

**代码示例**：
```javascript
console.log(1);

setTimeout(() => {
  console.log(2);
  Promise.resolve().then(() => {
    console.log(3);
  });
}, 0);

Promise.resolve().then(() => {
  console.log(4);
});

console.log(5);

// 输出：1 → 5 → 4 → 2 → 3
```

## 5. 存储机制

### 5.1 浏览器的存储方式有哪些？区别是什么？

**考点**：前端存储方案对比

| 存储方式 | 容量 | 生命周期 | 是否发送到服务器 | 作用域 |
|---------|------|---------|---------------|--------|
| **Cookie** | ~4KB | 可设置过期时间 | ✅ 每次请求自动发送 | 同源 |
| **LocalStorage** | ~5MB | 永久，除非手动清除 | ❌ | 同源 |
| **SessionStorage** | ~5MB | 会话级别，窗口关闭清除 | ❌ | 同源同窗口 |
| **IndexedDB** | 几百MB | 永久 | ❌ | 同源 |
| **Cache Storage** | 几百MB | 永久（需手动管理） | ❌ | 同源 |

**详细对比**：

**Cookie**：

- 用途：身份认证（Session ID）、个性化设置

- 缺点：容量小、每次请求都携带、安全性问题

- 注意：`HttpOnly`（防止XSS）、`Secure`（HTTPS）、`SameSite`（防CSRF）

**LocalStorage**：

- 用途：持久化存储（用户偏好、缓存数据）

- 特点：同步API、简单键值对

- 缺点：无法存储复杂数据结构（需JSON.stringify）

**SessionStorage**：

- 用途：临时数据（表单数据、页面状态）

- 特点：关闭窗口即清除、不同窗口数据独立

**IndexedDB**：

- 用途：大型数据存储（离线应用、PWA）

- 特点：异步API、支持索引、事务机制

- 缺点：API复杂

---

### 5.2 Cookie有哪些安全属性？

**考点**：Web安全

**安全属性**：

1. **HttpOnly**

   - JavaScript无法通过`document.cookie`访问

   - 防止XSS攻击窃取Cookie
   ```javascript
   Set-Cookie: sessionId=abc123; HttpOnly
   ```

2. **Secure**

   - 只在HTTPS连接下发送

   - 防止中间人攻击
   ```javascript
   Set-Cookie: sessionId=abc123; Secure
   ```

3. **SameSite**

   - 控制跨站发送行为

   - `Strict`：完全禁止跨站发送

   - `Lax`（默认）：允许GET请求跨站发送

   - `None`：允许跨站发送（必须配合Secure）
   ```javascript
   Set-Cookie: sessionId=abc123; SameSite=Strict
   ```

4. **Domain** / **Path**

   - 限制Cookie的作用范围

---

### 5.3 LocalStorage和SessionStorage的区别？

**考点**：存储机制细节

**核心区别**：

| 特性 | LocalStorage | SessionStorage |
|-----|-------------|---------------|
| **生命周期** | 永久存储 | 会话级别（窗口关闭即清除） |
| **共享性** | 同源页面共享 | 仅当前窗口/标签页 |
| **跨窗口** | ✅ | ❌ |
| **存储事件** | ✅（其他窗口会触发） | ✅（仅同窗口触发） |

**代码示例**：
```javascript
// LocalStorage - 关闭浏览器后仍然存在
localStorage.setItem('name', 'Alice');

// SessionStorage - 关闭标签页后清除
sessionStorage.setItem('token', 'abc123');
```

**注意**：iframe同源情况下，LocalStorage会共享，SessionStorage不会

## 6. 网络相关

### 6.1 浏览器如何处理跨域请求？

**考点**：CORS机制、跨域解决方案

**同源策略限制**：

- 无法读取非同源网页的Cookie、LocalStorage、IndexedDB

- 无法接触非同源DOM

- 无法向非同源地址发送AJAX请求

**跨域解决方案**：

1. **CORS（跨域资源共享）** ✅ 推荐

   - 服务器设置响应头

2. **JSONP**（仅GET，已淘汰）

   - 利用`<script>`标签不受同源限制

   - 只能发送GET请求

3. **代理服务器**

   - 开发环境：webpack-dev-server proxy

   - 生产环境：Nginx反向代理

4. **postMessage**（窗口通信）

   - 用于iframe、window.open跨域通信

5. **WebSocket**（不受同源限制）

6. **Nginx反向代理**

### 6.2 什么是预检请求（Preflight Request）？

**考点**：CORS进阶

**触发条件**（简单请求不会触发）：

- 使用`PUT`、`DELETE`等非简单方法

- 设置自定义请求头（如`Authorization`）

- Content-Type为`application/json`等非简单类型

**预检请求流程**：
```
1. 浏览器发送OPTIONS请求（预检）
2. 服务器返回允许的跨域配置
3. 如果通过，浏览器发送真实请求
```

**简单请求（不会触发预检）**：

- 方法：GET、POST、HEAD

- Content-Type：`application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain`

**代码示例**：
```javascript
// 会触发预检（非简单请求）
fetch('https://api.example.com/data', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Authorization': 'Bearer token'
  },
  body: JSON.stringify({ name: 'Alice' })
});
```

### 6.3 浏览器的并发请求限制是多少？

**考点**：网络性能优化

**并发限制**：

- **HTTP/1.1**：同一域名下最多**6个**并发连接

- **HTTP/2**：多路复用，理论上无限制（实际浏览器有限制）

**解决方案**：

1. **域名分片（Domain Sharding）**

   - 将资源分散到多个子域名

   - 如：`static1.example.com`、`static2.example.com`

1. **升级HTTP/2**

   - 多路复用，解决队头阻塞

1. **资源合并**

   - CSS/JS合并、雪碧图

1. **使用CDN**

---

### 6.4 什么是HTTP/2？相比HTTP/1.1有哪些优势？

**考点**：网络协议演进

**HTTP/2核心特性**：

1. **二进制协议**

   - 不再是纯文本，解析效率更高

1. **多路复用（Multiplexing）**

   - 一个TCP连接上并行发送多个请求

   - 解决HTTP/1.1队头阻塞问题

1. **头部压缩（HPACK）**

   - 使用Huffman编码压缩头部

   - 减少传输体积

1. **服务器推送（Server Push）**

   - 服务器主动推送资源到客户端缓存

   ```http
   Link: </style.css>; rel=preload
   ```

**性能提升**：

- 减少TCP连接数

- 降低延迟

- 提升页面加载速度

## 7. 安全机制

### 7.1 什么是XSS攻击？如何防范？

**考点**：Web安全核心

**XSS（跨站脚本攻击）类型**：

1. **存储型XSS**

   - 恶意脚本存储在服务器（如评论、文章）

   - 所有访问该页面的用户都会执行

2. **反射型XSS**

   - 恶意脚本在URL中，服务器反射回页面

   - 需要用户点击恶意链接

3. **DOM型XSS**

   - 恶意脚本通过DOM操作注入

   - 不经过服务器

**防御措施**：

1. **输入过滤和转义**

2. **CSP（内容安全策略）**

3. **使用HttpOnly Cookie**

4. **使用现代框架**

   - React、Vue默认对插入内容进行转义

---

### 7.2 什么是CSRF攻击？如何防范？

**考点**：Web安全核心

**CSRF（跨站请求伪造）**：

- 攻击者诱导用户在已登录的网站执行非本意操作

- 利用浏览器自动发送Cookie的特性

**攻击示例**：
```html
<!-- 恶意网站上的代码 -->
<img src="https://bank.com/transfer?to=attacker&amount=10000" />
```

**防御措施**：

1. **SameSite Cookie**
   ```javascript
   Set-Cookie: sessionId=abc; SameSite=Strict
   ```

2. **CSRF Token**
   - 服务器生成Token，表单提交时验证
   ```html
   <input type="hidden" name="csrf_token" value="random_token">
   ```

2. **双重Cookie验证**

   - 请求头携带Cookie中的Token

2. **验证Referer**

   - 检查请求来源

---

### 7.3 什么是CSP（内容安全策略）？

**考点**：Web安全进阶

**定义**：通过HTTP响应头或meta标签，限制页面可以加载的资源

**作用**：
- 防止XSS攻击

- 防止数据注入

- 控制资源加载来源

**配置方式**：
```html
<!-- meta标签 -->
<meta http-equiv="Content-Security-Policy" content="default-src 'self'; script-src 'self' https://cdn.example.com">

<!-- HTTP响应头 -->
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com
```

**常用指令**：

- `default-src`：默认策略

- `script-src`：JavaScript来源

- `style-src`：CSS来源

- `img-src`：图片来源

- `connect-src`：AJAX、WebSocket来源

**面试加分点**：

- 知道`report-uri`用于上报违规

- 理解`nonce`和`hash`的使用

---

### 7.4 浏览器的沙箱机制是什么？
**考点**：浏览器安全架构

**沙箱（Sandbox）定义**：
- 将不可信代码运行在隔离环境中

- 限制对系统资源的访问

**浏览器沙箱机制**：
- 每个渲染进程运行在独立沙箱中

- 无法直接访问文件系统、网络

- 通过IPC与浏览器进程通信

**沙箱级别**：
- **高**：完全隔离（如iframe的sandbox）

- **中**：部分限制

- **低**：较少限制

**iframe沙箱属性**：
```html
<iframe src="page.html" sandbox="allow-scripts allow-same-origin"></iframe>
```

**sandbox可选值**：
- `allow-scripts`：允许执行脚本

- `allow-same-origin`：允许同源访问

- `allow-forms`：允许表单提交

- `allow-top-navigation`：允许跳转顶层页面

### 8.2 什么是懒加载（Lazy Loading）？
**考点**：性能优化技术

**定义**：延迟加载非首屏资源，提升首屏加载速度

**实现方式**：

1. **图片懒加载**
   ```html
   <!-- 原生懒加载 -->
   <img src="image.jpg" loading="lazy" alt="...">

   <!-- Intersection Observer API -->
   <script>
   const images = document.querySelectorAll('img[data-src]');
   const observer = new IntersectionObserver((entries) => {
     entries.forEach(entry => {
       if (entry.isIntersecting) {
         entry.target.src = entry.target.dataset.src;
         observer.unobserve(entry.target);
       }
     });
   });

   images.forEach(img => observer.observe(img));
   </script>
   ```

2. **路由懒加载（Vue/React）**
   ```javascript
   // Vue
   const routes = [
     { path: '/about', component: () => import('./About.vue') }
   ];

   // React
   const About = React.lazy(() => import('./About'));
   ```

3. **组件懒加载**

### 8.3 什么是防抖（Debounce）和节流（Throttle）？

**考点**：性能优化经典问题

**防抖（Debounce）**：

- 多次触发只执行最后一次

- **适用场景**：搜索框输入、窗口resize、scroll事件

**节流（Throttle）**：

- 规定时间内只执行一次

- **适用场景**：按钮点击、鼠标移动、滚动加载

**代码实现**：

**防抖**：
```javascript
function debounce(fn, delay) {
  let timer = null;
  return function(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => {
      fn.apply(this, args);
    }, delay);
  };
}

// 使用
const search = debounce((keyword) => {
  console.log('搜索:', keyword);
}, 500);

input.addEventListener('input', (e) => search(e.target.value));
```

**节流**：
```javascript
function throttle(fn, delay) {
  let lastTime = 0;
  return function(...args) {
    const now = Date.now();
    if (now - lastTime >= delay) {
      lastTime = now;
      fn.apply(this, args);
    }
  };
}

// 使用
const scrollHandler = throttle(() => {
  console.log('滚动');
}, 1000);

window.addEventListener('scroll', scrollHandler);
```

### 8.4 如何监控页面性能？

**考点**：性能监控实践

**性能指标**：

1. **FP（First Paint）**：首次绘制

2. **FCP（First Contentful Paint）**：首次内容绘制

3. **LCP（Largest Contentful Paint）**：最大内容绘制

4. **FID（First Input Delay）**：首次输入延迟

5. **CLS（Cumulative Layout Shift）**：累计布局偏移

6. **TTI（Time to Interactive）**：可交互时间

**监控API**：

1. **Performance API**
   ```javascript
   // 获取页面加载性能
   const timing = performance.timing;
   console.log('DNS查询耗时:', timing.domainLookupEnd - timing.domainLookupStart);
   console.log('TCP连接耗时:', timing.connectEnd - timing.connectStart);
   console.log('请求耗时:', timing.responseEnd - timing.requestStart);
   ```

2. **PerformanceObserver**
   ```javascript
   // 监听LCP
   new PerformanceObserver((entryList) => {
     const entries = entryList.getEntries();
     const lastEntry = entries[entries.length - 1];
     console.log('LCP:', lastEntry.renderTime || lastEntry.loadTime);
   }).observe({ type: 'largest-contentful-paint', buffered: true });
   ```

3. **Web Vitals库**（Google官方）
   ```javascript
   import { getCLS, getFID, getLCP, getFCP, getTTFB } from 'web-vitals';

   getCLS(console.log);
   getFID(console.log);
   getLCP(console.log);
   ```

## 9. 进阶问题

### 9.1 什么是Service Worker？

**考点**：PWA、离线应用

**定义**：运行在浏览器后台的独立线程，可拦截网络请求

**特性**：
- 独立于页面运行

- 可离线工作

- 可拦截和处理网络请求

- 支持推送通知

- 支持后台同步

**典型应用**：

- 离线缓存（Cache API）

- 推送通知

- 后台同步

- 请求拦截和修改

**代码示例**：
```javascript
// 注册Service Worker
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js')
    .then(registration => console.log('SW注册成功'))
    .catch(error => console.log('SW注册失败:', error));
}

// sw.js
const CACHE_NAME = 'v1';
const urlsToCache = ['/index.html', '/style.css', '/app.js'];

// 安装时缓存资源
self.addEventListener('install', event => {
  event.waitUntil(
    caches.open(CACHE_NAME)
      .then(cache => cache.addAll(urlsToCache))
  );
});

// 拦截请求
self.addEventListener('fetch', event => {
  event.respondWith(
    caches.match(event.request)
      .then(response => response || fetch(event.request))
  );
});
```

---

### 9.2 什么是Web Worker？

**考点**：多线程编程

**定义**：在后台运行的独立线程，不阻塞UI

**特点**：

- 独立于主线程

- 无法访问DOM

- 通过`postMessage`通信

- 适用于计算密集型任务

**使用场景**：

- 复杂计算（数据处理、加密解密）

- 大文件处理

- 游戏逻辑

**代码示例**：
```javascript
// 主线程
const worker = new Worker('worker.js');

worker.postMessage({ data: [1, 2, 3, 4, 5] });

worker.onmessage = (e) => {
  console.log('Worker返回结果:', e.data);
};

// worker.js
self.onmessage = (e) => {
  const result = e.data.data.reduce((sum, num) => sum + num, 0);
  self.postMessage({ result });
};
```

### 9.3 什么是MutationObserver？

**考点**：DOM监听进阶

**定义**：异步监听DOM变化的API

**相比MutationEvents的优势**：

- 异步执行，不会阻塞主线程

- 性能更好

- 可以监听批量变化

**使用场景**：

- 监听DOM结构变化

- 实现虚拟DOM差异化更新

- 监控第三方库对DOM的修改

**代码示例**：
```javascript
const observer = new MutationObserver((mutations) => {
  mutations.forEach(mutation => {
    console.log('变化类型:', mutation.type);
    console.log('目标节点:', mutation.target);
    console.log('添加的节点:', mutation.addedNodes);
    console.log('删除的节点:', mutation.removedNodes);
  });
});

// 配置观察选项
const config = {
  childList: true,     // 子节点变化
  attributes: true,    // 属性变化
  subtree: true,       // 观察后代节点
  characterData: true  // 文本变化
};

observer.observe(document.body, config);

// 停止观察
// observer.disconnect();
```

### 9.4 浏览器的本地化存储方案有哪些？

**考点**：存储技术选型

**存储方案对比**：

| 方案 | 适用场景 | 优点 | 缺点 |
|-----|---------|------|------|
| **Cookie** | 身份认证 | 自动发送 | 容量小、性能差 |
| **LocalStorage** | 持久化配置 | 简单、容量大 | 同步、阻塞 |
| **SessionStorage** | 会话数据 | 简单、临时 | 窗口关闭即清除 |
| **IndexedDB** | 大型数据 | 容量大、异步 | API复杂 |
| **Cache Storage** | 资源缓存 | 配合SW使用 | 需要HTTPS |
| **Web SQL** | ❌ 已废弃 | - | - |

**选择建议**：

- 小量配置：LocalStorage

- 大量结构化数据：IndexedDB

- 离线资源：Cache Storage + Service Worker

- 临时数据：SessionStorage

- 身份认证：HttpOnly Cookie

### 9.5 什么是浏览器的预加载扫描器（Preload Scanner）？

**考点**：浏览器优化机制

**定义**：浏览器在解析HTML时，会提前扫描后续资源并开始下载

**工作原理**：

1. 主线程解析HTML构建DOM

2. 预加载扫描器并行扫描后续标签

3. 提前发现`<link>`、`<script>`、`<img>`等资源

4. 提前发起网络请求

**优化技巧**：
```html
<!-- 利用预加载 -->
<link rel="preload" href="critical.css" as="style">
<link rel="preload" href="font.woff2" as="font" crossorigin>

<!-- 使用dns-prefetch -->
<link rel="dns-prefetch" href="https://cdn.example.com">

<!-- 使用preconnect -->
<link rel="preconnect" href="https://api.example.com">
```

**面试加分点**：

- 知道预加载扫描器的存在

- 理解`preload`、`prefetch`、`preconnect`的区别

### 9.6 什么是回流（Reflow）优化中的"布局抖动"（Layout Thrashing）？

**考点**：性能优化陷阱

**定义**：连续读取和修改布局属性，导致浏览器反复重排

**错误示例**：
```javascript
// ❌ 布局抖动 - 每次循环都触发重排
for (let i = 0; i < 100; i++) {
  div.style.top = div.offsetTop + 10 + 'px';
  div.style.left = div.offsetLeft + 10 + 'px';
}
```

**优化方案**：
```javascript
// ✅ 批量读取、批量修改
const currentTop = div.offsetTop;
const currentLeft = div.offsetLeft;

for (let i = 0; i < 100; i++) {
  div.style.top = currentTop + (i * 10) + 'px';
  div.style.left = currentLeft + (i * 10) + 'px';
}
```

**工具检测**：

- Chrome DevTools → Performance → 查看重排次数
