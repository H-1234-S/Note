# 前端工程化面试八股整理：Webpack 与 Vite

> 适用：前端实习 / 校招；技术背景：React + TypeScript + Next.js。  
> 面试策略：先用“30 秒回答”给结论，再按“问题—机制—取舍—实践”展开。不要背 API，要讲清为什么这样设计。

## 一、Webpack

### 1. Webpack 是什么，解决什么问题？

**30 秒面试回答**

Webpack 是一个以模块为入口的静态资源打包工具。它从入口文件出发，递归分析 JS、TS、CSS、图片等依赖，借助 Loader 把非 JS 文件转换为模块，再通过 Plugin 介入构建生命周期，最后根据依赖关系输出浏览器可运行的一个或多个 Bundle。它主要解决浏览器原生模块能力不足、资源类型繁杂、模块之间依赖管理困难，以及上线时需要压缩、拆包、缓存等问题。

**深入解释**

- 早期浏览器无法直接处理 CommonJS、TypeScript、CSS Modules、图片导入等写法；即使使用原生 ESM，也缺少统一的压缩、兼容性转换和资源管理流程。
- Webpack 把“所有资源”抽象成模块：`import './style.css'`、`import logo from './logo.svg'` 都能进入同一张依赖图。
- 它的核心价值不是“把文件拼起来”，而是建立依赖图，并据此做转换、优化、分块和输出。
- React 项目中，JSX/TSX 经由 Babel 或 SWC 转换；CSS 经 Loader 链处理；动态 `import()` 可以形成异步 Chunk；生产构建再做压缩与长期缓存。

**常见追问**

- 为什么 Webpack 能处理图片？——不是原生能处理，而是资产模块或对应 Loader 把它转换成 URL / 文件资源模块。
- Webpack 和 Babel 的关系？——Babel 负责代码语法转换；Webpack 负责模块依赖、资源编排与最终输出，二者常配合。

### 2. 整体构建流程：Compiler、Compilation、Module、Chunk、Bundle

**30 秒面试回答**

Webpack 启动时先创建全局唯一的 Compiler，它读取配置并注册插件；每次构建产生一个 Compilation，Compilation 从 entry 开始解析模块、执行 Loader、收集依赖并形成模块图。模块按入口、动态导入和 SplitChunks 策略被组织成 Chunk，最后 Chunk 经过渲染和输出形成浏览器加载的 Bundle 文件。开发模式下文件变更会触发新的 Compilation。

**深入解释**

| 概念 | 面试中应怎么理解 |
| --- | --- |
| Compiler | Webpack 的总调度器，生命周期覆盖从启动到结束，通常一个 Webpack 实例一个 Compiler。 |
| Compilation | 一次构建的上下文与结果，包含模块、依赖、Chunk、资源和错误信息；监听模式下会多次创建。 |
| Module | 依赖图中的一个节点，不一定是 `.js`，也可以是 CSS、图片、JSON。 |
| Chunk | 为加载和优化而组合的一组 Module，是逻辑产物，可能来自 entry、动态导入或公共依赖提取。 |
| Bundle / Asset | 最终输出到磁盘的文件，如 `main.[contenthash].js`、`vendors.js`、CSS 文件。 |

流程可记为：`初始化配置 → 创建 Compiler → 注册 Plugin → 触发 run/watch → 创建 Compilation → 从入口建图 → 优化/分 Chunk → 生成 Assets → 写入输出目录`。

面试易错点：Chunk 不是最终文件；一个 Chunk 通常生成一个或多个文件，具体取决于 CSS 抽取、Source Map、运行时代码等配置。

### 3. Loader 原理和执行流程

**30 秒面试回答**

Loader 本质是一个函数转换器，输入是上一个 Loader 处理后的资源内容，输出是可继续被 Webpack 解析的内容或结果。Webpack 根据 `module.rules` 匹配资源，从右到左、从下到上执行 Loader 链，例如 `style-loader`、`css-loader`、`sass-loader` 中，Sass 先转 CSS，CSS 再转 CommonJS 模块，最后把样式注入页面。异步 Loader 通过 `this.async()` 或回调完成。

**深入解释**

- `test/include/exclude` 决定规则匹配范围；Loader 配置的 `use` 数组执行顺序是**从后往前**。
- Loader 通常将源文本转换为 JS 模块源码，Webpack 才能继续解析其中的 `import/export` 并加入依赖图。
- Loader 可以调用 `this.getOptions()` 读取配置，调用 `this.addDependency()` 声明额外文件依赖，调用 `this.emitFile()` 输出附加资源。
- 常见链路：`tsx → swc/babel-loader → JS 模块`；`scss → sass-loader → css-loader → style-loader`。生产环境通常以 `MiniCssExtractPlugin` 抽出 CSS，而非 `style-loader` 注入。

**常见追问**

- 为什么 loader 要右到左？——使转换呈管道嵌套关系；最右侧最接近原始文件，先执行。
- Loader 可以做 Tree Shaking 吗？——Loader 主要做单文件转换；跨模块可达性分析、Chunk 优化由 Webpack 的优化阶段完成。

### 4. Plugin 原理和生命周期

**30 秒面试回答**

Plugin 用于扩展 Webpack 在构建全流程中的能力。一个插件通常实现 `apply(compiler)`，在其中通过 Tapable 提供的钩子订阅 Compiler 或 Compilation 生命周期；到了对应时机再读取、修改 Compilation 中的模块、Chunk、资源或构建参数。Loader 聚焦文件转换，Plugin 更适合压缩、注入 HTML、定义环境变量、抽取 CSS 等全局能力。

**深入解释**

- Webpack 基于 Tapable 的同步、异步串行、异步并行钩子组织生命周期。
- 插件先在 `compiler.hooks` 订阅全局事件，再可在 `compilation` 阶段订阅本次构建事件，如模块构建、资源处理、优化、emit。
- 现代插件修改资源应优先使用 `compilation.emitAsset()`、`processAssets`，而不是直接操作废弃内部字段。
- 示例思路：`HtmlWebpackPlugin` 根据 Chunk 生成 script/link 标签；`DefinePlugin` 在编译期替换常量；压缩插件在资源优化阶段缩小代码。

**常见追问**

- 能否用 Loader 写 HTML 注入？——技术上可绕，但 HTML 注入依赖全局 Chunk 结果，属于 Plugin 的职责边界。
- Plugin 是否每次文件变化都重新实例化？——配置阶段实例化并注册一次；监听构建时会重复执行相关钩子，Compilation 会更新。

### 5. Loader 和 Plugin 的区别

| 维度 | Loader | Plugin |
| --- | --- | --- |
| 核心职责 | 转换某类资源内容 | 扩展构建流程和全局能力 |
| 工作粒度 | 单个模块/文件 | 一次 Compilation、所有模块与资源 |
| 入口 | `module.rules` | `plugins` |
| 典型能力 | TS、Sass、图片转模块 | 压缩、生成 HTML、提取 CSS、环境变量 |
| 形态 | 函数 | 带 `apply` 方法的对象/类 |

**一句话回答**：Loader 是“把某个文件变成模块”，Plugin 是“在正确的构建时机改变整个构建结果”。

### 6. 模块解析和依赖图构建

**30 秒面试回答**

Webpack 从 entry 解析 `import`、`require` 和动态 `import()`，按 `resolve` 规则定位真实文件：相对路径直接查找，包名从 `node_modules` 和 package.json 的入口字段解析，并尝试扩展名和别名。每个文件经过 Loader 转换后，Webpack 继续分析其中的依赖并递归建立 Module Graph；遇到已处理的模块会复用，从而处理共享依赖和循环依赖。

**深入解释**

- 解析优先受 `resolve.alias`、`extensions`、`mainFields`、`conditionNames`、`exports` 影响；现代包优先遵守 package `exports` 条件导出。
- `import()` 会在图中标记异步边界，后续形成独立异步 Chunk。
- 循环依赖通常不会无限递归，因为模块会被缓存；但运行时可能拿到未完成初始化的导出，因此应避免业务层强循环。
- 性能实践：缩小 `resolve.extensions`、为复杂路径配置 `alias`、限制 Loader 的 `include`，避免遍历整个 `node_modules`。

### 7. Tree Shaking 原理

**30 秒面试回答**

Tree Shaking 是基于 ES Module 静态结构的“未使用导出消除”。Webpack 先在构建阶段标记哪些导出被使用，再由压缩器在生产模式下删除不可达代码。它依赖 ESM 的 import/export 在编译时可分析；CommonJS 的动态 `require` 不利于精确分析。要避免副作用模块被误删，需要正确配置 `sideEffects`。

**深入解释**

- `usedExports` 做“标记”，Terser 等压缩器结合死代码消除做“删除”；因此仅打开某个开关不一定真的缩小产物。
- `sideEffects: false` 表示包内模块默认没有导入即执行的副作用；CSS、polyfill 等有副作用资源必须在数组中保留，例如 `sideEffects: ['*.css']`。
- `export *`、动态属性访问、CJS、带副作用的顶层代码都会降低效果。
- React 项目建议按需导入：`import { debounce } from 'lodash-es'` 比导入整个 CommonJS 库更利于优化；但“按需导入”不等于 Tree Shaking，本质仍取决于模块格式和副作用标记。

**追问：Tree Shaking 能删除什么？**

未被使用的导出及其可证明不可达的代码；不能安全删除模块顶层副作用、运行时动态访问可能用到的内容。

### 8. Code Splitting 原理

**30 秒面试回答**

Code Splitting 是把单个大 Bundle 按加载时机和依赖关系拆成多个 Chunk，减少首屏必须下载的代码。Webpack 常用三种方式：多入口、动态 `import()` 形成异步 Chunk、`SplitChunksPlugin` 抽取公共依赖。运行时通过 Webpack runtime 按需加载对应 JS 文件，并缓存已加载 Chunk。

**深入解释**

- **路由级拆分**最有收益：React 可用 `React.lazy` / `Suspense`，Next.js 可用 `next/dynamic`，使非首屏页面或重组件延迟下载。
- `splitChunks.cacheGroups` 会按复用次数、体积阈值等策略提取 vendor 或 shared Chunk，减少重复下载。
- `runtimeChunk: 'single'` 可把运行时代码稳定分离，配合 `[contenthash]` 提高长期缓存命中率。
- 不要机械拆得太碎：请求调度、缓存失效、HTTP/2/3 环境、用户路径都需权衡。目标是减少关键路径字节数，而非最大化文件数量。

### 9. HMR 原理

**30 秒面试回答**

HMR 是热模块替换：开发服务器与浏览器保持 WebSocket 连接，文件修改后 Webpack 只重新编译受影响模块并生成更新描述和 hot-update 文件；客户端收到消息后下载更新，从变更模块向上查找可接受更新的边界，调用 `module.hot.accept` 或框架运行时完成替换。找不到边界或更新不可接受时，才退化为整页刷新。

**深入解释**

1. 浏览器加载初始 Bundle 和 HMR runtime，并连接 dev server。
2. 文件变更触发增量 Compilation，服务端广播 hash / update 通知。
3. 客户端请求 manifest，获知哪些 Chunk 更新，再拉取对应 hot-update 文件。
4. 运行时 dispose 旧模块、替换模块工厂、重新执行并通知 accept 回调。
5. React Fast Refresh 在此基础上判断组件边界，尽可能保留 Hook state；不是所有编辑都能保留状态。

### 10. Webpack 性能优化

**30 秒面试回答**

我会先区分开发构建和生产产物。开发侧减少解析和转换范围，例如 Loader `include`、缩小 `resolve.extensions`、开启持久化缓存、用更快的转译器；生产侧重点是拆包、Tree Shaking、压缩、资源优化和内容哈希缓存。优化前后都用 SpeedMeasurePlugin、webpack-bundle-analyzer 或构建时间与产物体积数据验证，避免凭感觉改配置。

**深入解释：按瓶颈作答**

| 目标 | 具体手段 | 原理 |
| --- | --- | --- |
| 减少编译工作 | `include`、排除 `node_modules`、精确后缀、别名 | 少匹配、少解析、少执行 Loader。 |
| 加快重复构建 | `cache: { type: 'filesystem' }` | 复用模块解析和构建缓存。 |
| 加快 JS 转译 | SWC / esbuild loader（按项目验证） | 原生实现通常比纯 JS 转译快。 |
| 缩小首屏 | 动态导入、SplitChunks、按路由拆分 | 延后非关键代码。 |
| 缩小总产物 | Tree Shaking、压缩、图片字体优化 | 删除无用代码、降低传输字节。 |
| 提高缓存 | `[contenthash]`、稳定 module/chunk id、runtime 分离 | 未变 Chunk 名不变，可命中 CDN/浏览器缓存。 |

Next.js 项目一般不直接维护 Webpack 主配置，但理解这些原则仍有用：路由自动拆分、`next/dynamic`、分析 Bundle、避免把大客户端库放进 Client Component，都是同一套工程化思想。

## 二、Vite

### 11. Vite 出现背景，为什么开发更快？

**30 秒面试回答**

传统 Webpack 开发模式通常要先把整张依赖图打包，项目越大冷启动和更新等待越明显。Vite 在开发环境利用浏览器原生 ESM：启动时只预构建依赖，业务源码按浏览器请求即时转换和返回；修改文件时只让浏览器更新受影响模块，而不是重打整个 Bundle。因此它在大项目中通常具有更快的冷启动和更小的 HMR 更新范围。

**深入解释**

- “更快”主要指开发服务器，不等于所有生产构建都必然更快。
- 源码通常变化频繁且数量大，Vite 不预先打包它们；第三方依赖多为 CommonJS / 细碎 ESM，适合预构建合并和格式转换。
- 浏览器请求 `.tsx` 时，Vite 按需转换并重写模块路径；后续请求命中内存 / HTTP 缓存。

### 12. Vite 核心原理

**30 秒面试回答**

Vite 开发服务器以原生 ESM 为核心。浏览器请求入口后，Vite 对源码做按需转换、把裸模块导入改写成可访问路径，并维护模块图；依赖先由 esbuild 预构建。文件修改时，Vite 根据模块图精确找到受影响模块和 HMR 边界，通过 WebSocket 通知浏览器更新。生产环境则交给 Rollup 完成成熟的打包和优化。

**工作流程**

`浏览器请求入口 → Vite 转换 HTML / 注入客户端 → 浏览器请求 ESM 模块 → 按需 transform → 构建 Module Graph → 返回模块 → 文件变更 → 沿图传播 HMR 更新`。

注意：Vite 不是“完全不打包”。开发阶段主要不打包业务源码；依赖会预构建，生产阶段仍需要打包以做兼容、压缩和资源优化。

### 13. ESM 按需加载机制

**30 秒面试回答**

浏览器原生 ESM 会在解析模块中的静态 import 后，只请求当前页面依赖到的模块。Vite 利用这个能力，不在启动时预打包全部业务代码，而是在浏览器发起请求时再转换对应文件；路由懒加载模块也只有真正进入该路由时才请求。这就是“按需加载”，它把原来构建时的大量工作推迟并分散到实际访问路径上。

**深入解释**

- 这里的“按需”有两层：开发服务器按请求转换源码；业务通过动态 import 按用户路径加载代码。
- Vite 会将裸导入如 `react` 重写为预构建依赖路径，将 `/src/x.tsx` 等映射为可服务模块。
- 浏览器 ESM 请求多，因此 Vite 需要合理的 HTTP 缓存、依赖预构建和模块路径处理；现代 HTTP 协议降低了多请求成本，但不是零成本。

### 14. esbuild 依赖预构建

**30 秒面试回答**

Vite 用 esbuild 做依赖预构建，主要有两个目的：第一，把 CommonJS、UMD 等非原生 ESM 依赖转换成浏览器可用的 ESM；第二，把一个依赖及其大量内部模块合并或优化，避免浏览器开发时发出过多细碎请求。预构建结果会缓存，依赖或配置变化时才重新生成。

**深入解释**

- 扫描入口中裸模块依赖，输出到缓存目录；业务源码通常不在这一步整体打包。
- esbuild 以 Go 实现，转换非常快，适合开发时的依赖处理；但 Vite 的生产打包默认选择 Rollup，见后文。
- 可通过 `optimizeDeps.include/exclude` 处理扫描不到、动态引用或需要特殊优化的依赖，但应先确认问题，别把所有包都硬塞进去。

### 15. Vite HMR 原理

**30 秒面试回答**

Vite 启动时维护模块依赖图，并通过 WebSocket 与浏览器通信。文件变化后，它失效对应模块的 transform 缓存，从变更模块沿 importer 关系向上寻找 HMR 接受边界；若找到，就只发送该模块更新，客户端重新请求带时间戳的模块并执行回调；找不到边界则全页刷新。由于不需要生成整包 hot-update，更新链路通常更短。

**深入解释**

- Vite 客户端通过 `import.meta.hot.accept()` 注册接受边界；框架插件（如 React 插件）会注入 / 利用这一机制实现 Fast Refresh。
- CSS 常可替换样式而不刷新页面；React 的组件状态能否保留取决于 Fast Refresh 的边界判断。
- HMR 失败不一定是 Vite 慢，往往是模块有副作用、边界未接受，或框架插件无法判定安全替换。

### 16. Vite 插件机制

**30 秒面试回答**

Vite 插件以 Rollup 插件接口为基础，并增加面向开发服务器的钩子。通用构建转换可复用 Rollup 的 `resolveId`、`load`、`transform`、`generateBundle` 等钩子；需要开发能力时可使用 `configureServer`、`handleHotUpdate`。因此很多 Rollup 插件能在 Vite 中使用，但使用前要确认它是否依赖纯打包阶段语义。

**深入解释**

- `enforce: 'pre' | 'post'` 控制插件顺序；插件顺序会影响 JSX、宏转换、CSS 处理等结果。
- `apply: 'serve' | 'build'` 可限制只在开发或生产生效，避免不必要开销与行为差异。
- 面试里要强调：Vite 兼顾 dev server 与 build，插件不能只从“改代码字符串”理解；解析、虚拟模块、资源生成、HMR 都可扩展。

### 17. Vite 生产环境为什么使用 Rollup？

**30 秒面试回答**

因为生产构建更重视成熟的 Chunk 切分、Tree Shaking、输出格式、插件生态与产物可控性。Rollup 在库和应用构建的 ESM 静态分析、代码组织及插件体系上很成熟，适合生成高质量产物；esbuild 虽然很快，但早期在复杂打包优化和生态兼容上不如 Rollup 完整。Vite 因而采用“开发时 esbuild 加速、生产时 Rollup 优化”的分工。

**补充**：现在 Vite 的底层能力持续演进，回答重点不要绝对化为“esbuild 不能打包”，而是说明默认架构的设计取舍：开发体验与生产产物质量分别使用更合适的工具链。

### 18. Vite 性能优化

**30 秒面试回答**

Vite 优化要先区分启动慢、页面首次加载慢和 HMR 慢。启动慢重点排查依赖预构建与过多插件；页面慢看懒加载、产物体积和资源缓存；HMR 慢看模块依赖扇出、重型转换插件和不必要的 Client 端依赖。生产构建通过 visualizer 分析 Chunk，再有针对性地拆分或替换大依赖，而不是盲目配置 `manualChunks`。

**可执行清单**

- 依赖稳定时保留预构建缓存；避免频繁删除缓存目录。
- 插件设置 `apply`，避免开发与构建阶段都跑不必要逻辑。
- 大型编辑器、图表、富文本、地图等使用动态 import；React 中配合 `lazy` / `Suspense`。
- 使用 `rollup-plugin-visualizer` 或构建统计定位大包；优先替换不支持按需导入或体积异常的库。
- 合理配置 `build.sourcemap`；生产 Source Map 有排障价值，但会增加产物与发布成本，应按安全策略决定。
- Next.js 默认不使用 Vite 作为官方主构建链路；不要为了“Vite 快”强行迁移。对 Next.js 更重要的是 Server / Client Component 边界、动态加载和 Bundle Analyzer。

## 三、Webpack 与 Vite 核心区别

| 维度 | Webpack | Vite |
| --- | --- | --- |
| 开发核心 | 通常先构建 / 编译依赖图再服务 | 浏览器原生 ESM，源码按请求转换 |
| 冷启动 | 大项目可能较慢 | 通常更快，主要预构建依赖 |
| HMR | 生成并应用模块热更新产物 | 基于模块图精确更新，链路通常更短 |
| 依赖处理 | 与业务代码统一进入打包流程 | esbuild 预构建依赖，源码按需服务 |
| 生产构建 | Webpack 自身完成 | 默认 Rollup 完成 |
| 插件生态 | 历史悠久、覆盖面广 | Rollup 兼容 + Vite 开发钩子 |
| 适用判断 | 高度定制、存量 Webpack 生态、复杂兼容需求 | 新 SPA / 组件库、追求现代开发体验 |
| 本质差异 | 以“打包器”组织开发与生产 | 开发服务器和生产打包器分工 |

**面试结论**：不是 Vite 全面取代 Webpack。选型取决于项目存量、插件兼容、浏览器目标、团队构建链路和迁移成本；新项目优先评估 Vite，成熟 Webpack 项目优先评估收益是否覆盖迁移风险。

## 四、30 个高频工程化面试问题及参考回答

1. **Webpack 的核心是什么？**——从入口建立模块依赖图，转换模块、优化分块，再输出浏览器资源。
2. **Compiler 与 Compilation 区别？**——Compiler 是全局调度器；Compilation 是一次构建的上下文和结果。
3. **Module、Chunk、Bundle 区别？**——Module 是图节点，Chunk 是逻辑模块组，Bundle 是落盘文件。
4. **Loader 的执行顺序？**——`use` 中从右到左、从下到上；最右侧先处理原文件。
5. **Plugin 为什么能扩展 Webpack？**——通过 `apply` 注册 Tapable 生命周期钩子，读取或修改构建过程和产物。
6. **Loader 和 Plugin 如何选？**——文件内容转换选 Loader；跨文件、全局构建编排选 Plugin。
7. **Webpack 如何解析 npm 包？**——按 alias、package.json `exports/mainFields`、模块目录和扩展名规则定位入口。
8. **为什么要限制 Loader 的 include？**——避免无关目录特别是 node_modules 被重复转译，降低构建时间。
9. **Tree Shaking 为什么依赖 ESM？**——静态 import/export 可在编译期分析；CJS 的 require 更动态。
10. **`sideEffects` 配错会怎样？**——可能把 CSS、polyfill 等有副作用文件错误删除，造成线上样式或功能缺失。
11. **Tree Shaking 为什么有时不生效？**——导入 CJS、顶层副作用、未压缩、Babel 转成 CJS，或实际使用路径不静态。
12. **Code Splitting 有哪些方式？**——多入口、动态 import、SplitChunks 抽公共依赖。
13. **动态 import 为什么能拆包？**——它是异步依赖边界，Webpack 会将其依赖分配到可延后加载的 Chunk。
14. **拆包越多越好吗？**——不好；需要围绕关键路径、复用、缓存和请求成本做平衡。
15. **HMR 与刷新页面的区别？**——HMR 替换受影响模块并尝试保留应用状态；刷新会重新加载整个页面。
16. **React Fast Refresh 与 HMR 的关系？**——Fast Refresh 是 React 对 HMR 的高层适配，尽量保留组件 Hook state。
17. **长期缓存怎么做？**——使用 contenthash、稳定 id、runtime 分离，并避免不相关改动污染公共 Chunk。
18. **Webpack 构建慢如何排查？**——先量化构建耗时、Loader/Plugin 耗时和 Bundle 体积，再按瓶颈处理。
19. **Vite 为什么启动快？**——不预打包全部业务源码，依赖预构建后，源码由浏览器请求驱动按需转换。
20. **Vite 是不是不打包？**——不是；开发源码以 ESM 服务，依赖预构建；生产仍默认使用 Rollup 打包。
21. **Vite 为什么要依赖预构建？**——把 CJS/UMD 转 ESM，并减少第三方依赖带来的细碎模块请求。
22. **Vite HMR 为什么通常更快？**——能借助模块图直接失效和更新相关模块，通常不用重新生成完整 bundle 更新产物。
23. **Vite 中裸模块导入如何运行？**——开发服务器重写为可访问的预构建依赖路径。
24. **Vite 的模块图有什么用？**——记录导入和反向依赖关系，为缓存失效、HMR 边界查找服务。
25. **Vite 插件与 Rollup 插件关系？**——Vite 兼容大量 Rollup 构建钩子，并补充开发服务器和 HMR 钩子。
26. **为什么 Vite build 默认选 Rollup？**——生产更看重成熟 Tree Shaking、分块控制、输出能力和插件生态。
27. **Vite 项目 HMR 慢怎么查？**——检查变更模块的反向依赖扇出、转换插件耗时、重型组件依赖和文件监听问题。
28. **如何优化 React 项目首屏？**——路由/重组件懒加载、减少客户端大依赖、按需加载、压缩资源并建立缓存策略。
29. **Next.js 中工程化优化重点？**——Server/Client 边界、`next/dynamic`、图片字体优化、路由级加载和 Bundle 分析，而非盲改 Webpack。
30. **如何做选型回答？**——先说约束：项目类型、存量配置、浏览器兼容、生态依赖、团队经验；再说明 Vite 开发体验优势和 Webpack 的可定制/兼容价值。

## 五、面试表达模板

遇到原理题，推荐按以下顺序回答：

1. **定义**：它是什么，解决哪类工程问题。
2. **主链路**：输入从哪里来，经历哪些关键阶段，输出是什么。
3. **关键机制**：只挑 1—2 个设计点讲透，例如“ESM 静态分析”或“模块图 + HMR 边界”。
4. **边界与取舍**：它不适合什么；为什么不能绝对化。
5. **实践落点**：结合 React / Next.js 说一个你会怎样排查、配置或优化的例子。

例如被问“为什么 Vite 快”，不要只答“用了 esbuild”。更完整的回答是：**开发环境快的主要原因是原生 ESM 按请求转换业务源码，而不是先打完整包；esbuild 负责快速预构建依赖和部分转换；模块图又让 HMR 只更新受影响边界。生产构建则是另一套以 Rollup 优化产物的链路。**

## 六、复习优先级

校招优先把以下内容讲成闭环：

1. Webpack：依赖图、Loader / Plugin、Tree Shaking、Code Splitting、HMR。
2. Vite：原生 ESM、依赖预构建、模块图 HMR、为何生产用 Rollup。
3. 实战：能用“首屏慢 / 构建慢 / 更新慢”三类问题说出排查指标和优化手段。

> 最终目标不是背出所有配置项，而是让面试官确信：你能看懂构建链路，能根据性能指标定位瓶颈，也知道工程方案永远有约束和成本。
