## 0. 知识地图与推荐顺序

Redis 可以理解为一个**基于内存、支持多种数据结构、可持久化、可复制、可分片的网络数据库**。它既能做缓存，也能做计数器、排行榜、分布式锁、延迟队列和轻量消息流，但这些能力的可靠性边界不同，不能因为“都能用 Redis”就把 Redis 当成万能数据库。

```text
业务代码 / 缓存 / 计数 / 排行榜 / 锁 / 队列
                    │ RESP 请求
客户端连接 ── Redis 事件循环 ── 命令执行（主线程）
                    │
     Dict / SDS / listpack / quicklist / skiplist / intset
                    │
      内存分配器、过期字典、淘汰策略、复制缓冲区
                    │
       RDB / AOF / 主从复制 / Sentinel / Cluster
                    │
                   磁盘、网络、操作系统
```

推荐依赖顺序：

1. 先掌握五大类型以及各自的时间复杂度和典型场景。
2. 再理解 Redis 为什么快：内存、单线程命令执行、非阻塞网络、简单数据结构。
3. 接着理解持久化、复制和集群，回答“数据丢不丢、节点挂了怎么办、容量不够怎么办”。
4. 最后学习缓存问题、分布式锁和消息场景，因为这些才是业务面试中的追问重点。

面试时建议使用这条回答路径：**先给结论，再讲机制，再给示例，最后说明边界和故障场景**。例如被问“Redis 为什么快”，不要只回答“单线程”；应当说明内存访问、IO 多路复用、简单数据结构、避免线程切换分别贡献了什么，同时指出大 Key、慢命令和网络才是常见瓶颈。

## 1. Redis 全景：定位、模型与为什么快

### 1.0 学习前置：先理解“数据从哪里来、到哪里去”

学习 Redis 前，建议先具备三组基础知识：

1. **进程、线程与内存**：Redis 是一个进程，数据结构主要驻留在进程内存；线程决定命令如何串行执行，内存决定容量和访问速度。
2. **TCP 与网络 I/O**：Redis 不是函数库，而是网络服务。客户端和 Redis 之间有连接、协议、缓冲区和网络延迟。
3. **时间复杂度**：Redis 的快慢不是绝对的，`GET`、`HGET` 和 `ZRANGE` 的成本不同，返回 10 个元素与返回 100 万个元素也完全不同。

为什么先学这些？因为“Redis 很快”只是结果，不是原因。新人如果只记住“Redis 是内存数据库”，很容易忽略网络 RTT、序列化、大 Key 和慢命令；如果不理解进程和线程，也无法解释为什么一个 `KEYS *` 会影响所有请求。

建议先做一个最小实验：启动 Redis，使用一个客户端执行 `SET/GET`，再用两个客户端并发执行 `INCR`，最后执行一个大集合的范围读取。观察命令是如何通过网络进入 Redis、按顺序执行并返回的，再开始阅读高可用和缓存章节。

### 1.1 Redis 是什么

Redis（Remote Dictionary Server）是一个开源的内存数据结构服务。它把数据主要放在内存中，通过网络提供命令式访问，并支持 RDB 快照、AOF 日志、主从复制、哨兵和 Cluster。

它和普通关系型数据库的差异不在于“Redis 只能存内存、MySQL 只能存磁盘”，而在于核心抽象不同：

| 对比项 | Redis | 关系型数据库 |
| --- | --- | --- |
| 核心模型 | Key-Value + 原生数据结构 | 表、行、列、SQL |
| 典型访问 | 按 Key、按集合/分数/范围 | 条件查询、连接、聚合 |
| 主要优势 | 低延迟、高吞吐、丰富原子操作 | 持久化、复杂查询、事务约束 |
| 常见职责 | 缓存、计数、排行榜、锁、队列 | 权威数据、复杂查询、账务数据 |
| 一致性边界 | 取决于持久化、复制和业务策略 | 通常有更强的事务与约束能力 |

### 1.2 一次 Redis 请求发生了什么

以 `GET user:1` 为例：

1. 客户端通过 TCP 连接发送 RESP 命令。
2. Redis 读取 socket 中的数据，解析命令和参数。
3. 根据命令名找到命令实现，校验参数和数据类型。
4. 通过全局字典定位 `user:1`，读取 String 对象。
5. 将结果编码为 RESP 响应，写入客户端 socket 缓冲区。
6. 如果开启 AOF，写命令追加到 AOF 缓冲区；如果发生复制，命令还会写入复制缓冲区。

```text
Client ── TCP/RESP ──> Redis Event Loop
                         ├─ 解析命令
                         ├─ 查找 key
                         ├─ 执行原子命令
                         ├─ AOF / Replication buffer
                         └─ RESP response ──> Client
```

### 1.3 Redis 为什么快

常见原因有四层：

- **内存访问**：主数据通常在内存中，避免了每次请求都访问磁盘。
- **数据结构专用实现**：Hash、跳表、压缩列表等结构针对常见操作优化，不需要每次解析 SQL、生成执行计划。
- **命令执行串行**：传统 Redis 命令执行阶段主要由一个线程完成，一个命令执行期间不会被另一个命令打断，因此天然具备单命令原子性，也避免了共享数据加锁和大量线程切换。
- **IO 多路复用**：一个线程可以管理大量连接；网络等待不需要为每个连接占用一个阻塞线程。

但“Redis 单线程所以快”是不完整答案。影响延迟的因素还包括：命令复杂度、Key/Value 大小、网络 RTT、客户端连接池、fork 重写、内存碎片、慢查询和 CPU。`KEYS *`、大范围 `ZRANGE`、超大 Hash 的序列化都可能阻塞事件循环。

### 1.4 Redis 是单线程吗

更准确的说法是：**核心命令执行路径通常是单线程串行的，但 Redis 整体不是只有一个线程**。后台线程/进程可能处理 AOF fsync、懒删除、网络 IO 线程、RDB/AOF fork 子进程等，具体能力与版本和配置有关。

单线程带来的优势：

- 单条命令无需显式加锁，命令之间有明确顺序；
- 数据结构实现简单，避免并发读写竞态；
- 小命令延迟稳定。

单线程的限制：

- 一个慢命令会阻塞其他请求；
- CPU 密集型操作无法仅靠增加连接数扩展；
- 大 Key 删除、序列化、过期集中处理可能造成延迟尖刺。

### 1.5 为什么 Redis 不使用多线程执行所有命令

如果多个线程同时修改同一个 Hash、List 或跳表，需要更复杂的锁、内存可见性和调度协调；多数 Redis 命令很快，线程切换和锁竞争未必划算。Redis 的思路是把命令做短、把数据结构操作做高效，再用复制、分片和多实例扩展吞吐。

### 1.6 高频面试题

| 问题 | 标准回答思路 | 可能追问 |
| --- | --- | --- |
| Redis 为什么快？ | 内存、简单数据结构、单线程命令执行、IO 多路复用；同时受命令复杂度、网络和大 Key 影响。 | 单线程为什么还能支持高并发？ |
| Redis 是单线程吗？ | 核心命令执行以串行模型为主，但后台线程/子进程和 IO 线程可能参与其他工作。 | `UNLINK` 为什么能降低删除阻塞？ |
| Redis 适合做数据库吗？ | 适合低延迟数据结构服务；是否能做主库取决于持久化、复制、备份和可接受的数据丢失窗口。 | 订单、余额能否只存 Redis？ |
| Redis 和 Memcached 区别？ | Redis 支持丰富数据结构、持久化、复制、事务脚本；Memcached 模型更简单，通常只做缓存。 | Redis 什么时候反而更不合适？ |

## 2. 五大基础数据类型与底层编码

### 2.0 学习前置：从“业务数据模型”映射到 Redis 类型

本章前置不是背命令，而是先会把业务对象拆成三类问题：

- **单值问题**：一个 Key 对应一个值，例如用户详情、配置、Token，通常用 String；
- **字段问题**：一个对象有多个可独立读写的字段，通常用 Hash；
- **关系问题**：关注关系、标签、排名、时间顺序，本质上是集合、排序或队列，分别考虑 Set、ZSet、List/Stream。

为什么要先做建模？Redis 的数据类型不是装饰性的 API，它直接决定原子操作、时间复杂度、内存占用和集群路由。例如“用户标签”如果存成 JSON String，去重和增删都要读改写整个对象；存成 Set 后，`SADD` 天然保证唯一性。新人选型时先问“我需要哪些操作”，再问“哪种类型能以最少步骤完成”。

每种类型都建议按四步学习：**语义是什么、底层如何支持、常见操作复杂度、超大规模时如何退化**。这样才能从“会用命令”进阶到“能设计 Key”。

### 2.1 Redis 对象模型

Redis 中每个 Key 和 Value 都是对象。对象除了保存类型，还可能保存编码方式、LRU/LFU 信息、引用计数等。面试不必死记每个版本的阈值，但要知道：**同一种逻辑类型可能根据数据规模选择不同底层编码，小数据偏向节省内存，大数据偏向操作效率**。

| 逻辑类型 | 常见底层结构 | 典型操作复杂度 |
| --- | --- | --- |
| String | SDS、整数编码 | `GET/SET` 近似 O(1)，按长度传输 |
| List | quicklist，节点内常用 listpack | 两端 O(1)，按下标中间访问可能 O(N) |
| Hash | listpack 或 hashtable | 平均 O(1)，遍历 O(N) |
| Set | intset 或 hashtable | `SADD/SISMEMBER` 平均 O(1) |
| ZSet | listpack 或 dict + skiplist | 增删查分数平均 O(log N)，范围 O(log N + M) |

不同版本会调整内部结构和配置阈值，因此回答底层编码时，应该以“常见实现 + 版本差异”表达，不要把一个版本的源码细节当成永久不变的协议。

### 2.2 String

String 是 Redis 最基础的类型，Value 可以是文本、整数或二进制数据，最大值上限受 Redis 版本和协议实现约束，业务上更应关注内存和网络大小。

```redis
SET user:1:name "Alice"
GET user:1:name
SET user:1:login_count 0
INCR user:1:login_count
SET session:abc '{"userId":1,"role":"admin"}' EX 1800 NX
```

常见用途：

- 对象缓存：`user:1 -> JSON`；
- 计数器：浏览量、点赞数、限流令牌；
- 分布式 ID 的序列号；
- 二进制数据或短文本；
- 简单锁值：`SET lock:order:1 token NX EX 30`。

注意：`INCR` 对整数是原子操作，但“先 GET 再计算再 SET”不是原子操作；对象字段频繁局部更新时，String JSON 会带来整对象读写和并发覆盖问题，此时可以考虑 Hash 或 Lua。

### 2.3 Hash

Hash 适合存储一个对象的多个字段：

```redis
HSET user:1 id 1 name Alice vip 1 login_count 10
HGET user:1 name
HINCRBY user:1 login_count 1
HGETALL user:1
```

Hash 比“每个字段一个 String Key”更节省 Key 元数据和网络往返，但也有边界：

- `HGETALL` 会返回整个 Hash，字段多时可能成为慢命令；
- 一个极大的 Hash 会造成大 Key、迁移和删除压力；
- Hash 的 TTL 作用在整个 Key 上，不能给单个 field 单独设置过期时间；
- 不同字段有不同生命周期时，拆成多个 Key 更清晰。

对象更新示例：

```ts
await redis.hSet('user:1', { name: 'Alice', vip: '1' });
await redis.hIncrBy('user:1', 'login_count', 1);
await redis.expire('user:1', 3600);
```

### 2.4 List

List 是有序字符串集合，适合两端进出：

```redis
LPUSH queue:email job-3 job-2 job-1
RPOP queue:email
BLPOP queue:email 10
LRANGE recent:orders 0 19
```

常见用途：简单队列、最新消息列表、时间线。`LPUSH + LTRIM recent:orders 0 99` 可以维护最近 100 条记录。

不要把 List 当作高可靠消息队列的完整替代品：消费者 `RPOP` 后进程崩溃，消息可能已经丢失。若要可靠消费，可以用 `BRPOPLPUSH`/`BLMOVE` 形成处理中队列，或优先考虑 Stream 的消费组。

### 2.5 Set

Set 无序且元素唯一，适合集合关系：

```redis
SADD article:1:tags redis database cache
SISMEMBER article:1:tags redis
SINTER user:1:followings user:2:followings
SUNIONSTORE group:all user:1:followings user:2:followings
```

场景：标签去重、共同关注、抽奖去重、在线用户集合、权限集合。集合运算可能扫描大量元素，要关注规模；生产上不应对超大 Set 随意 `SMEMBERS`。

### 2.6 Sorted Set（ZSet）

ZSet 每个 member 关联一个 score，并按 score 排序；score 相同时通常按 member 的字典序处理。

```redis
ZADD leaderboard 98 user:1 95 user:2 98 user:3
ZREVRANGE leaderboard 0 9 WITHSCORES
ZINCRBY leaderboard 5 user:2
ZRANGEBYSCORE leaderboard 100 200 WITHSCORES
```

典型场景：排行榜、定时任务、延迟队列、按时间排序的 Feed。时间轮/延迟队列示例：

```redis
ZADD delay:jobs 1760956800 job:1001
ZRANGEBYSCORE delay:jobs -inf 1760956800 LIMIT 0 100
ZREM delay:jobs job:1001
```

仅靠 `ZRANGEBYSCORE` 再 `ZREM` 可能有并发重复消费，需要用 Lua 把“取出并删除”封装为原子操作，或者用 Stream/专业消息系统。

### 2.7 类型错误与键设计

如果 `user:1` 原来是 String，又执行 `HSET user:1 name Alice`，会得到 `WRONGTYPE`。生产中应通过命名空间区分用途：

```text
user:1:profile     Hash
user:1:session      String
user:1:followers    Set
user:1:timeline     List
```

键名建议包含业务域、对象标识和用途，避免过长但不能牺牲可读性。可以统一约定 `业务:对象:ID:属性`，并控制单个 Key 的 Value 大小。

## 3. String 的使用边界：缓存、计数器、分布式 ID

### 3.0 学习前置：序列化、幂等和数值原子操作

String 看起来最简单，但它往往是缓存系统的入口，因此要先理解三个概念：

- **序列化**：对象进入 Redis 前要变成字符串或二进制；JSON 可读性好，但会产生体积、兼容和整对象更新问题。
- **幂等性**：同一个写请求重复执行，结果是否相同。网络超时后客户端无法确定服务端是否执行成功，写操作能否安全重试非常关键。
- **原子数值操作**：`INCR` 是服务端完成的读改写，避免了客户端并发竞争；而“GET 后在业务代码里加一再 SET”是两个请求之间可被插入的非原子流程。

为什么要补这些前置知识？因为 String 最常见的生产事故不是 `SET` 写错，而是缓存 JSON 覆盖了并发更新、计数重试造成重复累加、锁没有 TTL，或者序列化版本升级后旧缓存无法解析。学习命令时要同时记录“它的失败方式”。

### 3.1 String 做对象缓存

```ts
const key = `user:${id}`;
const cached = await redis.get(key);
if (cached) return JSON.parse(cached);

const user = await db.user.findById(id);
if (user) {
  await redis.set(key, JSON.stringify(user), { EX: 300 });
}
return user;
```

这里有三个常见追问：

1. 查不到的数据要不要缓存？可以缓存短 TTL 的空值，防止穿透。
2. `GET` 后数据库查询期间大量请求怎么办？使用互斥锁、singleflight 或逻辑过期。
3. 数据更新后缓存怎么处理？通常先更新数据库，再删除缓存；若要求更强一致性，需要消息补偿、重试和版本控制。

### 3.2 计数器为什么适合 Redis

`INCR` 在 Redis 命令执行层是原子的：

```redis
INCR article:100:views
INCRBY user:1:points 10
```

但如果计数必须永久准确，不能只依赖 Redis。常见方案是 Redis 负责高并发累加，异步批量落库；同时需要处理重复消费、服务重启、落库失败和最终对账。

### 3.3 自增 ID 的限制

`INCR global:order:id` 可以生成单实例递增序列，但在多业务、多机房、跨环境和故障恢复场景下可能需要前缀、时间戳、机器号或 Snowflake。Redis 自增 ID 适合简单序列，不天然保证全局有序、跨机房不重复和永久不回退。

### 3.4 GETSET、SET NX EX 与安全更新

现代 Redis 中推荐使用带选项的 `SET`：

```redis
SET lock:payment:1001 6b9... NX EX 30
```

`NX` 表示不存在才设置，`EX` 设置秒级 TTL。不要把 `SETNX` 和 `EXPIRE` 分成两个独立命令，因为进程可能在两条命令之间崩溃，留下永不过期的锁。若需要毫秒级可以使用 `PX`。

## 4. List、Hash、Set、Sorted Set 的场景选择

### 4.0 学习前置：集合、队列与索引的区别

新人常把 List、Set、ZSet 都理解成“Redis 里的数组”。更准确的理解是：

- List 关注**顺序和两端进出**，像一个可持久化的链表/队列；
- Set 关注**成员是否存在以及集合关系**，不保证业务顺序；
- ZSet 关注**成员与分数的排序关系**，不是普通数组下标；
- Hash 关注**一个对象内部的字段映射**，不是多个对象的集合。

设计前先写出业务操作，例如“判断是否关注”“获取前 100 名”“取最新 20 条”“更新用户昵称”。然后比较哪个类型能用一条命令完成，而不是先选一个类型再强行改造业务。这样做的原因是：Redis 的性能优势来自数据结构与操作匹配，类型选错后，通常只能通过全量读取、客户端计算和重复写回补救。

### 4.1 场景选择表

| 业务需求 | 首选类型 | 原因 | 常见坑 |
| --- | --- | --- | --- |
| 对象整体缓存 | String | 序列化和读取简单 | 局部更新成本高 |
| 对象字段局部更新 | Hash | 字段级原子操作 | 无字段级 TTL，不能无脑 HGETALL |
| 去重 / 关系集合 | Set | 唯一性和集合运算 | 大集合遍历会阻塞 |
| 排名 / 范围查询 | ZSet | score 排序和范围操作 | 分数相同排序、热点写入 |
| 两端队列 | List | LPUSH/RPOP 简单 | 消费可靠性不足 |
| 消息流和消费组 | Stream | ID、ACK、Pending | 需要处理积压和消费组管理 |

### 4.2 关注时间复杂度，而不是只记“快”

常见误区是认为 Redis 的所有命令都是 O(1)。例如：

- `HGET`、`SISMEMBER` 平均 O(1)；
- `LRANGE key 0 100` 需要返回 101 个元素，至少是 O(M)；
- `SMEMBERS` 是 O(N)，集合越大越危险；
- `ZRANGE` 返回 M 个元素时通常是 O(log N + M)；
- `DEL` 大 Key 可能同步释放大量内存，产生延迟尖峰。

在代码评审中，应该同时关注命令复杂度和返回数据量。将 `SMEMBERS` 改成 `SSCAN`，将 `KEYS` 改成 `SCAN`，将大对象拆分，通常比“把 Redis 配置得更大”更有效。

### 4.3 SCAN 为什么比 KEYS 安全

`KEYS pattern` 会一次性扫描整个键空间并阻塞其他命令；`SCAN` 使用游标分批遍历，单次调用工作量较小：

```redis
SCAN 0 MATCH user:* COUNT 1000
```

SCAN 不是强一致快照：遍历期间发生新增、删除或 rehash 时，可能重复返回，也可能漏掉在遍历窗口变化的 Key。因此它适合渐进式运维任务，不适合直接当作精确快照。

## 5. Stream、Bitmap、HyperLogLog、Geo 与布隆过滤器

### 5.0 学习前置：精确数据、近似数据与消息状态

这一章的几个结构解决的是不同问题，不能只按“节省空间”理解：

- Bitmap、HyperLogLog 关注**统计**，有些结果可以是近似值；
- Geo 关注**空间索引**，坐标、距离和范围是核心；
- Bloom Filter 关注**快速判断一定不存在**，存在误判但不能漏掉真实存在；
- Stream 关注**消息生命周期**，要理解消息 ID、消费者、确认、重试和积压。

前置知识是“业务是否允许近似”和“消息是否允许丢失”。UV 可以接受估算，账户余额不能；简单通知可能允许丢失，订单事件通常至少要可重试。为什么要先问这个？因为数据结构的选择不是纯技术偏好，而是由正确性目标决定的。

### 5.1 Stream：Redis 中更适合消息的结构

Stream 是追加型消息流，每条消息有 ID 和字段：

```redis
XADD orders * order_id 1001 user_id 7 amount 99
XREAD COUNT 10 BLOCK 5000 STREAMS orders 0
XGROUP CREATE orders order-workers $ MKSTREAM
XREADGROUP GROUP order-workers c1 COUNT 10 BLOCK 5000 STREAMS orders >
XACK orders order-workers 1700000000000-0
```

消费组中的消息会进入 Pending Entries List（PEL）。消费者处理成功后 `XACK`；消费者宕机时，其他消费者可以通过 `XPENDING`、`XCLAIM` 或 `XAUTOCLAIM` 接管超时消息。

面试要点：

- `>` 表示读取从未投递给该消费组的消息；
- `XACK` 只确认消费组状态，不代表业务一定已经持久化，业务处理和 ACK 的先后要设计好；
- Stream 不是无限磁盘队列，需要通过 `MAXLEN` 或定期裁剪控制长度；
- 跨服务强可靠、复杂重试、海量积压时，Kafka/RabbitMQ 等专业 MQ 往往更合适。

### 5.2 Bitmap

Bitmap 实际上是 String 的位操作：

```redis
SETBIT attendance:2026-10-20 1001 1
GETBIT attendance:2026-10-20 1001
BITCOUNT attendance:2026-10-20
```

适合签到、活跃标记、布尔状态统计。偏移量很大时要估算 String 的空间：最高位为 1 时，中间空洞也会占用空间。

### 5.3 HyperLogLog

HyperLogLog 用很小的固定空间估算基数，例如 UV：

```redis
PFADD uv:2026-10-20 user:1 user:2 user:3
PFCOUNT uv:2026-10-20
PFMERGE uv:week uv:2026-10-20 uv:2026-10-19
```

它适合“只关心大致去重数量”的场景，结果是概率估计，不适合需要列出用户或强一致计费的场景。

### 5.4 Geo

Geo 基于 Sorted Set 保存地理位置，支持附近搜索：

```redis
GEOADD shops 116.397 39.908 shop:1
GEOSEARCH shops FROMLONLAT 116.40 39.90 BYRADIUS 5 km WITHDIST COUNT 20
```

要关注坐标顺序是经度、纬度，距离单位和数据规模。复杂空间查询、路线规划和海量地理数据通常应交给专门的地理数据库。

### 5.5 Redis 能否直接做布隆过滤器

原生 Redis 没有传统意义上完整的布隆过滤器命令，通常使用 RedisBloom 模块，或用 Bitmap + 多个哈希函数自行实现。布隆过滤器只能判断“可能存在”或“一定不存在”，存在误判，不支持可靠删除（除非使用计数布隆过滤器）。

典型防穿透流程：请求先查布隆过滤器，判断一定不存在就直接返回；可能存在再查 Redis 和数据库。布隆过滤器需要随着新数据写入同步更新，并考虑初始化、重建和误判率。

## 6. Redis 过期、淘汰与内存管理

### 6.0 学习前置：容量、生命周期与资源回收

在学习 TTL 前，先区分三个时间概念：

1. **业务有效期**：业务上认为数据什么时候失效；
2. **Redis TTL**：Key 在 Redis 中允许保留多久；
3. **物理释放时间**：内存真正被回收的时间，可能晚于 TTL。

再区分两个容量问题：内存不够时是“数据应该自然过期”，还是“Redis 必须拒绝写入”。缓存和权威状态的答案不同。为什么这一步重要？因为很多新人把 TTL 当作定时删除器，把淘汰当作故障恢复机制，最终出现大量过期 Key 残留、重要数据被淘汰或缓存失效后数据库被打爆。

学习时要养成容量思维：每个 Key 都有生命周期、大小和访问热度；整个实例还需要为复制缓冲区、AOF 重写、RDB fork 和碎片预留空间。

### 6.1 TTL 和过期删除

```redis
SET cache:user:1 '{...}' EX 300
TTL cache:user:1
PTTL cache:user:1
EXPIRE cache:user:1 600
PERSIST cache:user:1
```

Redis 的过期删除通常结合：

- **惰性删除**：访问 Key 时发现已过期，再删除；
- **定期删除**：后台定期抽样检查过期字典并删除一部分。

因此 TTL 到期不代表数据在那一刻一定立刻从内存中消失；如果一个过期 Key 从不访问，可能暂时残留。`volatile-*` 淘汰策略只针对设置了 TTL 的 Key，不能把“过期”和“内存淘汰”混为一谈。

### 6.2 maxmemory 与淘汰策略

当内存达到 `maxmemory`，Redis 会按策略处理新写入：

| 策略 | 含义 | 适用思路 |
| --- | --- | --- |
| noeviction | 不淘汰，写入报错 | 需要强约束、不能自动丢数据 |
| allkeys-lru | 所有 Key 按 LRU 淘汰 | 通用缓存 |
| volatile-lru | 仅有 TTL 的 Key 按 LRU 淘汰 | 混合数据，需谨慎 |
| allkeys-lfu | 所有 Key 按访问频率淘汰 | 热点长期稳定的缓存 |
| volatile-ttl | 优先淘汰剩余 TTL 短的 Key | 过期时间有业务意义 |
| random | 随机淘汰 | 少数特殊场景 |

LRU/LFU 通常是近似实现，不是每次都维护全量精确排序。选择淘汰策略前要先区分：Redis 是纯缓存，还是同时存放不能丢失的数据。混合存储时，自动淘汰可能破坏业务数据。

### 6.3 内存碎片与大 Key

Redis 申请和释放内存后，内存分配器可能留下碎片。监控 `used_memory`、`used_memory_rss`、`mem_fragmentation_ratio` 等指标，不能只看进程 RSS 判断实际数据量。

大 Key 的风险包括：

- 读写一次传输大量数据，阻塞事件循环；
- `DEL` 同步释放造成延迟尖峰；
- 主从复制、AOF、Cluster 迁移成本高；
- 过期或淘汰集中发生造成抖动。

治理方法：限制 Value/Hash/List/Set/ZSet 规模；拆分 Key；使用 `UNLINK` 做异步删除；用 `SCAN`、`--bigkeys` 或采样脚本定位；对批量操作分片执行。

### 6.4 TTL 设计中的随机抖动

如果大量 Key 在同一时间写入且设置相同 TTL，可能在同一时间大量过期，形成数据库洪峰。可设置：

```ts
const ttl = 300 + Math.floor(Math.random() * 60);
await redis.set(key, value, { EX: ttl });
```

TTL 抖动只能缓解集中失效，不能替代热点保护、限流和容量设计。

## 7. 单线程、事件循环与命令执行模型

### 7.0 学习前置：原子性、并发和网络排队

本章的前置概念是“并发不等于并行”。多个客户端可以同时发请求，但 Redis 会在命令执行阶段按顺序处理；网络接收、排队和响应写出则是另一层问题。

还要区分：

- **单条命令原子**：执行过程中不会被另一个普通命令插入；
- **多条命令连续执行**：需要事务或脚本；
- **跨服务原子**：Redis、数据库和消息队列之间无法仅靠 Redis 命令自动实现。

为什么要先理解这些？新人经常把“Redis 单线程”误解成“所有请求都不会并发”，或者认为 Pipeline 就是事务。掌握“命令执行、网络传输、客户端重试”三层边界后，才能正确分析超卖、重复扣款和慢请求。

### 7.1 一个命令为什么具有原子性

Redis 命令在主执行线程中完整运行。执行 `INCR` 时，不会出现另一个普通命令在“读取旧值”和“写入新值”之间插入，因此单条命令天然是原子的：

```text
Client A: INCR counter  ─┐
Client B: INCR counter  ─┼─ Redis 串行执行，结果不会丢增量
Client C: INCR counter  ─┘
```

但“多条命令组合”不天然原子：

```text
GET stock:1
判断 > 0
DECR stock:1
```

两个客户端可能同时读到 1，然后都扣减，导致超卖。需要 Lua、事务或更合适的原子命令。

### 7.2 慢命令为什么影响全局

Redis 主线程执行大范围返回、复杂集合运算、同步删除时，其他连接的命令只能排队。于是一个请求的 O(N) 可能放大为所有请求的 P99 延迟。

常见危险操作：`KEYS`、大范围 `SMEMBERS`、无界 `LRANGE`、超大 `HGETALL`、大集合交并集、对大 Key 的 `DEL`。治理原则是：**限制返回数量、分页、分批、异步删除、离线计算、迁移到专门系统**。

### 7.3 Pipeline 与并发

Pipeline 是客户端把多条命令一次发出、减少网络往返，并不等于 Redis 内部并行执行，也不自动提供事务原子性：

```text
普通：命令1 -> 响应1 -> 命令2 -> 响应2
Pipeline：命令1、2、3 一次发送 -> 批量响应
```

Pipeline 中命令仍可能被其他客户端命令插入。如果要求“批量执行不可插入”，使用 `MULTI/EXEC` 或 Lua；如果只想减少 RTT，使用 Pipeline。

### 7.4 读写线程与瓶颈定位

开启 IO 线程主要是优化网络读写，不等于多个线程并行修改数据结构。判断瓶颈时分别看：CPU、命令执行耗时、网络带宽、客户端连接池、慢查询、fork 延迟和内存分配。不能只看到 CPU 低就认为 Redis 没有性能问题，网络和慢客户端同样可能造成排队。

## 8. 持久化：RDB、AOF 与混合持久化

### 8.0 学习前置：RPO、RTO 与数据权威性

持久化之前先回答两个问题：

- **RPO（Recovery Point Objective）**：故障后最多允许丢多少数据？
- **RTO（Recovery Time Objective）**：故障后最多允许多久恢复？

还要明确 Redis 中的数据是不是系统的最终事实来源。纯缓存丢了可以重建；订单状态、账务记录不能只依赖 Redis 的 AOF。为什么要先做这个判断？因为 RDB 和 AOF 没有绝对优劣：RDB 通常恢复快但快照间隔内可能丢数据，AOF 更接近写入过程但重放和重写成本更高。选型应该从业务损失倒推，而不是从“哪个更高级”出发。

新人可以先画一条时间线：业务写入、Redis 返回、复制到副本、写入 AOF 缓冲区、fsync 到磁盘。每个时间点发生故障，可能丢失的数据不同，这比死记 `appendfsync` 更容易形成正确理解。

### 8.1 RDB 快照

RDB 在某个时间点生成数据集快照，文件紧凑，恢复速度通常较快，适合备份和重启恢复。

```text
主进程 ── fork ──> 子进程遍历内存生成 RDB
   │
   └─ 继续处理请求；写入页面发生 Copy-on-Write
```

优势：文件小、恢复快、适合冷备；缺点：两次快照之间的数据可能丢失，fork 和 Copy-on-Write 在大内存实例上会造成 CPU、内存和延迟压力。

### 8.2 AOF 日志

AOF 记录改变数据集的写命令，重启时重放命令恢复。`appendfsync` 常见策略：

| 策略 | 含义 | 取舍 |
| --- | --- | --- |
| always | 每次写都 fsync | 数据丢失窗口小，吞吐和延迟较差 |
| everysec | 每秒 fsync | 性能与可靠性的常见折中，极端故障可能丢约一秒 |
| no | 由操作系统决定 | 性能较好，持久化时机不可控 |

AOF 会增长，需要重写：读取当前数据集，生成更短的命令序列。重写期间新写命令进入重写缓冲区，完成后合并，确保重写前后的写入不丢失。

### 8.3 混合持久化

混合持久化通常把一个时间点的 RDB 快照放在 AOF 前部，再追加后续 AOF 命令。恢复时先加载快照，再重放增量日志，兼顾恢复速度和较小的数据丢失窗口。

### 8.4 RDB、AOF 如何选择

不要简单回答“线上一定 AOF”。应根据数据价值和恢复目标选择：

- 纯缓存：可以接受丢失，重点是重建能力和启动速度，RDB 或关闭持久化都可能合理；
- 可恢复状态：常用混合持久化或 AOF everysec，并配合 RDB 备份；
- 不能丢失的账务数据：Redis 不能替代权威数据库，必须以数据库和可靠日志为准。

必须明确两个指标：RPO（最多能丢多少数据）和 RTO（多长时间恢复）。持久化只解决“进程/机器重启后的恢复”，不能单独解决误删、错误写入、机房故障和灾备问题。

### 8.5 fork 与 Copy-on-Write 的面试追问

fork 后父子进程共享物理页；父进程修改某页时，操作系统复制该页给父进程，形成 Copy-on-Write。于是“Redis 使用内存 10GB”并不代表生成 RDB 时只需要再增加 0GB 内存；写入越活跃，额外内存压力越大。大实例需要控制 fork 延迟、写入速率和备份窗口。

## 9. 事务、Pipeline、Lua 与原子性

### 9.0 学习前置：把“业务不变量”写出来

学事务和 Lua 前，先把业务必须保持的规则写成不变量，例如：

- 库存不能小于 0；
- 同一个用户同一订单只能成功一次；
- 只有持有锁的实例才能删除锁；
- 任务被取出后，不能同时被两个消费者处理。

然后再判断这个不变量涉及一条命令、多条 Redis 命令，还是 Redis 与数据库的跨系统操作。单命令优先使用原生命令；多条命令在同一实例内需要连续性时使用 Lua/事务；跨系统一致性则要靠幂等、状态机、消息和补偿。

为什么先写不变量？因为“用了 Lua”不等于设计正确。脚本只能保证脚本内部命令连续执行，不能保证脚本执行后数据库事务成功，也不能防止业务进程在外部调用中途崩溃。

### 9.1 MULTI / EXEC / DISCARD

```redis
MULTI
SET order:1:status paid
INCR user:1:points
EXEC
```

Redis 事务的特点：

- `MULTI` 后命令进入队列；
- `EXEC` 时按顺序一次执行，执行期间不会被其他客户端命令插入；
- 没有传统关系型数据库那种回滚机制；某条命令运行时出错，其他命令不会自动回滚；
- 命令入队阶段的语法/参数错误可能导致事务不能执行；运行时错误要由业务处理。

因此 Redis 事务更像“批量、串行执行的一组命令”，不要把它描述成完整 ACID 事务。

### 9.2 WATCH 乐观锁

```redis
WATCH stock:1
GET stock:1
MULTI
DECR stock:1
EXEC
```

如果 `WATCH` 后 Key 被其他客户端修改，`EXEC` 会失败，客户端需要重试。高竞争下会出现大量重试，不如 Lua 把判断和修改放在服务端一次完成。

### 9.3 Lua 脚本的价值

Lua 脚本在 Redis 中作为一个整体执行，适合把多步判断和修改封装为原子操作。库存扣减示例：

```lua
local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock <= 0 then
  return 0
end
redis.call('DECR', KEYS[1])
return 1
```

客户端调用时把 Key 通过 `KEYS` 传入，把普通参数通过 `ARGV` 传入。Cluster 中脚本涉及的 Key 通常必须落在同一 hash slot，因此可以使用 hash tag：`stock:{sku}:1`、`order:{sku}:1001`。

Lua 不是“无限制使用”：脚本运行期间会阻塞其他命令；脚本不能依赖不可控的长循环；Cluster 下需要考虑多 Key 路由；脚本要版本化、测试和监控。

### 9.4 Function 与脚本治理

现代 Redis 可以使用持久化的 server-side functions，但团队仍应关注脚本的发布、回滚、超时和权限。简单操作优先用原生命令；确实需要多步原子逻辑时才使用脚本，避免把业务代码搬进 Redis 形成难维护的“存储过程黑盒”。

### 9.5 原子性不等于持久化和高可用

一条 Lua 脚本原子执行，只能说明同一 Redis 实例中的命令不会被插入。它不保证：

- 数据已经刷到磁盘；
- 从节点已经复制；
- 主节点故障后一定不丢；
- 业务外部系统已经成功提交。

面试中要明确区分：**执行原子性、事务原子性、持久化可靠性、跨系统一致性**是四个不同问题。

## 10. 主从复制、哨兵与故障转移

### 10.0 学习前置：可用性、复制延迟与故障模型

高可用不是“部署多个 Redis”这么简单。先区分三个目标：

- **副本**：数据多一份，主要解决机器故障后的恢复；
- **自动故障转移**：主节点不可用时，系统能选出新主并通知客户端；
- **水平扩展**：把数据和流量分到多个主节点，解决容量和吞吐上限。

主从复制和 Sentinel 主要解决前两个问题，Cluster 才进一步解决分片。为什么要先建立这个区分？因为面试中最常见的错误是说“哨兵可以扩容”，或者说“有副本就不会丢数据”。异步复制意味着主节点已经返回成功时，副本可能尚未收到最新写入。

建议新人画出“主、从、Sentinel、客户端”四类角色，并分别写出它们的职责。之后再考虑网络分区、主从延迟、客户端重连和脑裂，而不要只背故障转移流程。

### 10.1 主从复制流程

```text
Master ── replication stream ──> Replica
   │                                   │
写命令、复制偏移量                 应用命令、回复 ACK
```

复制通常包含：

1. 从节点连接主节点并发送复制请求；
2. 主节点根据复制积压缓冲区判断能否增量同步；
3. 若不能，执行全量同步，传输 RDB；
4. 从节点加载 RDB，同时接收后续写命令；
5. 后续保持增量复制，并通过偏移量确认进度。

复制是异步的，所以主节点返回成功不等于从节点已经收到。主从延迟、网络分区和复制积压区大小都会影响故障切换时的数据丢失。

### 10.2 全量同步与增量同步

如果从节点断线时间短，且断线期间的写命令仍在复制积压缓冲区，可用增量同步；否则需要重新传输 RDB 并补发之后的命令。全量同步会带来网络、磁盘、CPU 和内存压力，高峰期频繁重连可能形成级联故障。

### 10.3 Sentinel 解决什么问题

Sentinel 负责监控、主观下线/客观下线判断、选举领导者、故障转移和通知客户端。它不负责数据分片，适合一个主分片 + 多副本的高可用模式。

故障转移大致过程：

1. Sentinel 发现主节点无响应，先判定主观下线；
2. 多个 Sentinel 达到法定人数后判定客观下线；
3. Sentinel 之间选举 leader；
4. leader 从副本中选择合适节点晋升为新主；
5. 让其他副本复制新主，并通知客户端更新地址。

### 10.4 Sentinel 不能保证什么

- 不能消除异步复制导致的数据丢失；
- 不能把一个主节点的内存和吞吐线性扩展；
- 不能自动修复业务双写、一致性和缓存击穿；
- 客户端必须正确处理重定向、重连、重试和幂等。

### 10.5 读副本的一致性问题

主写从读可能读到旧数据。若业务要求“刚写入马上读到”，应读主、使用版本/时间戳校验，或实现等待复制偏移量的 read-after-write 策略。不能因为部署了主从就默认读写一致。

## 11. Redis Cluster：分片、槽位与扩缩容

### 11.0 学习前置：水平扩展与数据路由

Cluster 的前置知识是分布式系统中的“数据应该由谁处理”。当一个实例容量或网络带宽不够时，不能只增加客户端连接，需要把 Key 按规则路由到不同节点。Redis Cluster 通过 hash slot 建立稳定的路由中间层，客户端或节点根据 slot 找到负责者。

学习前先回答三个问题：

1. 哪些 Key 会被一起读写？
2. 这些 Key 是否必须在同一个节点执行？
3. 数据分布是否均匀，是否存在超级热点？

这就是为什么 Cluster 章节必须先学 Key 设计。Hash tag 可以让多 Key 同槽，但使用过度又会把流量集中到一个节点；跨 slot 的全局操作不能像单实例那样随意执行。扩缩容也不是“加机器后自动变快”，迁移期间会消耗网络、CPU 和内存，并且大 Key 会放大迁移风险。

### 11.1 为什么需要 Cluster

单实例的内存、CPU、网络和故障域有限。Cluster 把 Key 空间分成固定数量的 hash slot，由多个主节点分担；每个主节点可以有副本，用于故障转移。

```text
Key -- CRC16(key) mod 16384 --> slot
                         ├─ node A: slot 0...5000
                         ├─ node B: slot 5001...10000
                         └─ node C: slot 10001...16383
```

### 11.2 MOVED 与 ASK

客户端访问错误节点时，节点会返回 `MOVED slot host:port`，表示该槽位的长期归属已变化；客户端更新槽位缓存后重试。迁移中可能返回 `ASK`，表示本次请求临时去目标节点，客户端不应立刻永久修改槽位映射。

现代 Cluster 客户端通常维护 slot cache、处理重定向和连接池。业务代码应使用支持 Cluster 的客户端，而不是自己把普通单节点客户端拼起来。

### 11.3 Hash Tag 解决多 Key 同槽

Cluster 中多 Key 的事务、Lua 或集合操作通常要求这些 Key 在同一 slot。使用大括号中的 hash tag：

```text
cart:{user:1}
coupon:{user:1}
```

两者只根据 `{user:1}` 计算 slot，因此可以在同一节点执行。但 hash tag 过度集中会造成热点节点，应该根据业务操作边界合理设计，而不是所有 Key 都使用同一个 tag。

### 11.4 扩缩容与数据迁移

扩容本质是重新分配槽位并迁移 Key。迁移期间会产生网络和 CPU 开销；大 Key 迁移更慢，热 Key 可能造成源节点压力。缩容前要确认目标节点容量、复制状态、迁移完成和故障回滚方案。

### 11.5 Cluster 的边界

- 不提供跨 slot 的通用事务；
- 不适合无边界广播和全局集合运算；
- Key 分布不均时会出现热点和容量浪费；
- 客户端重试可能放大请求，需要超时和幂等设计。

## 12. 缓存设计：Cache Aside、读写策略与一致性

### 12.0 学习前置：缓存不是事实来源，而是一个有状态的副本

缓存设计前要先明确四件事：

- 数据的权威来源是什么，通常是数据库或服务内存；
- 缓存丢失后能否重建；
- 允许多长时间的旧数据；
- 更新失败、回填失败和缓存不可用时如何降级。

缓存可以理解成“权威数据的一份有生命周期的副本”。副本天然可能过期、丢失或与源数据暂时不一致，所以设计重点不是追求一句“强一致”，而是把不一致窗口、修复路径和用户可见影响说清楚。

为什么先讲这个？新人很容易把缓存当成数据库的另一个表：写数据库后以为缓存一定同步，删除缓存后以为读请求一定不会回填旧值。实际上还存在并发读写、消息延迟、网络超时和进程崩溃，需要用版本、重试、补偿和幂等把边界补全。

### 12.1 Cache Aside（旁路缓存）

最常见的读流程：

```text
请求 -> 查 Redis
        ├─ 命中：返回
        └─ 未命中 -> 查数据库 -> 回填 Redis -> 返回
```

写流程通常是：

```text
更新数据库成功 -> 删除缓存 -> 返回
```

为什么通常是“更新 DB，再删除缓存”，而不是“删除缓存，再更新 DB”？如果先删缓存，另一个请求可能在数据库尚未更新时读到旧值并把旧值回填，形成旧缓存。先更新 DB 再删除缓存，仍存在并发窗口，但通常更容易配合重试、延迟双删和消息补偿。

### 12.2 Cache Aside 示例

```ts
async function getUser(id: string) {
  const key = `user:${id}`;
  const value = await redis.get(key);
  if (value !== null) return JSON.parse(value);

  const user = await db.findUser(id);
  if (user === null) {
    await redis.set(key, '__NULL__', { EX: 30 });
    return null;
  }
  await redis.set(key, JSON.stringify(user), { EX: 300 });
  return user;
}

async function updateUser(id: string, patch: Patch) {
  await db.updateUser(id, patch);
  await redis.del(`user:${id}`);
}
```

生产实现还应补充：超时、取消、缓存值校验、空值区分、回填失败处理、热点保护、监控和序列化版本。

### 12.3 延迟双删

一种缓解并发旧值回填的做法：更新 DB 前先删一次，更新 DB 后再删一次，第二次删除延迟一小段时间。它不是严格一致性方案，因为延迟、失败和消息丢失都可能发生。更稳妥的方式是通过 CDC/消息队列发送失效事件、带版本号校验或在读路径比较数据版本。

### 12.4 旁路缓存与写回缓存

- Cache Aside：应用显式读写缓存和数据库，最容易理解和控制；
- Read Through：缓存层未命中时由缓存组件加载数据；
- Write Through：写入缓存时同步写底层存储；
- Write Behind：先写缓存，异步落库，性能高但丢数据和一致性风险大。

普通业务优先使用 Cache Aside；Write Behind 只适合能接受最终一致性、且有可靠落库和对账机制的场景。

### 12.5 缓存一致性的真实边界

“缓存和数据库强一致”在分布式系统中成本很高。面试回答应先澄清业务要求：

- 允许短暂旧数据：TTL + 更新后删除缓存；
- 不能读到比某版本旧的数据：版本号、读主、消息失效；
- 余额/库存等强约束：Redis 不能单独替代事务数据库和业务校验；
- 只做加速：缓存丢失可重建，重点是可用性和保护后端。

## 13. 缓存穿透、击穿、雪崩与热 Key

### 13.0 学习前置：从“请求流量”看缓存故障

先定义一条请求链路：客户端 → 网关 → 应用 → Redis → 数据库。缓存问题的本质，是某种流量在某个时间点绕过了缓存保护，集中到下游：

- 穿透：大量请求访问本来不存在的数据；
- 击穿：一个热点 Key 突然失效，很多请求同时回源；
- 雪崩：大量 Key 或整个缓存层同时失效；
- 热 Key：某个 Key 长期承受过高的集中流量。

为什么要先从流量看？因为不同问题的治理对象不同。布隆过滤器主要防穿透，互斥回源主要防击穿，TTL 抖动和限流主要缓解雪崩，副本、本地缓存和分片主要治理热 Key。把四个词混在一起，方案就会失焦。

学习时建议为每种故障画“正常流量”和“故障流量”两张图，并标出数据库连接池、线程池和网关限流的位置。缓存保护的目标不是让所有请求都成功，而是让系统在异常流量下仍能控制损失。

### 13.1 缓存穿透

请求查询一个数据库和缓存都不存在的 Key，每次都打到数据库。

方案：

- 参数校验和鉴权，拦截明显非法请求；
- 缓存空值，TTL 要短；
- 布隆过滤器判断一定不存在；
- 限流和黑名单；
- 对高风险查询设置单独资源池。

空值缓存要区分“不存在”和“查询失败”，不能把数据库超时错误缓存成空对象。

### 13.2 缓存击穿

一个热点 Key 在过期瞬间，大量请求同时未命中，全部查询数据库。

方案：

- 互斥锁：只有一个请求回源，其余等待或返回降级值；
- 逻辑过期：Value 中保存逻辑过期时间，过期后先返回旧值，再异步刷新；
- 热点 Key 永不过期或延长 TTL，并由主动刷新任务更新；
- singleflight：同一进程内合并相同 Key 的并发回源。

互斥锁本身也要有超时、随机 token、释放校验和故障兜底。

### 13.3 缓存雪崩

大量 Key 同时过期、Redis 故障或缓存集群整体不可用，导致请求集中打到数据库。

方案是多层防护：TTL 抖动、预热、限流、熔断、降级、热点保护、Redis 高可用、数据库连接池隔离、缓存分片和定时刷新。不能只说“把过期时间设置成随机值”，那只能解决一种雪崩原因。

### 13.4 热 Key

热 Key 是少数 Key 承担了绝大多数访问或更新，可能让单节点、单分片或单线程成为瓶颈。

治理：

- 本地缓存 + Redis 二级缓存；
- 对只读热点做 Key 副本：`hot:1:0` 到 `hot:1:N`，读时随机分散；
- 写热点按时间桶、用户桶或分片计数；
- 限制单 Key Value 大小和访问频率；
- 通过命令统计、代理日志和应用指标定位，不要只看平均 QPS。

### 13.5 预热和降级

发布或大促前，根据历史访问和业务规则把热点数据提前加载。降级时返回静态数据、旧版本数据或业务可接受的默认值；降级结果必须明确标记，避免把“系统异常”伪装成真实业务结果。

## 14. 分布式锁：正确实现、续期与 Redlock

### 14.0 学习前置：锁保护的到底是什么

学习分布式锁前，先定义临界区和资源不变量：谁不能同时执行？重复执行会造成什么后果？锁失效后有没有第二道防线？

分布式锁只是“让多个进程尽量不要同时进入”的协调机制，不是数据库事务，也不是任务完成证明。网络延迟、进程暂停、GC、租约过期和机器故障都会让持锁者失去判断能力。因此锁内逻辑应该尽量短，业务操作应具备幂等性，关键写入还要有唯一约束、版本号或 fencing token。

为什么必须先讲资源？因为很多新人拿到一个通用锁工具就认为问题结束了，实际上锁的安全性取决于 TTL、释放顺序、重试、业务耗时以及被保护系统是否支持校验。先明确资源不变量，才能判断 Redis 锁是否足够。

### 14.1 最小可用锁

```redis
SET lock:order:1001 random-token NX PX 30000
```

获取成功后执行临界区，释放锁时不能直接 `DEL`，否则可能误删别人新获得的锁。正确做法是比较 Value，再删除，通常用 Lua：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
```

`random-token` 必须每次唯一，用于证明锁的所有权。

### 14.2 锁过期和业务执行时间

如果锁 TTL 为 30 秒，但业务执行 40 秒，锁可能提前过期，第二个实例进入临界区，出现并发执行。解决方式：

- 合理估算 TTL，并设置最大执行时间；
- 续期/watchdog，但要处理进程假死、网络隔离和续期线程故障；
- 把临界区设计成幂等、可重入或带 fencing token；
- 对外部资源使用版本号/租约校验，不能只依赖 Redis 锁。

### 14.3 锁能保证什么，不能保证什么

Redis 锁可以减少同一时间多个实例执行同一段逻辑，但不能自动保证：

- 进程宕机后业务一定完成；
- 数据库事务与锁操作跨系统原子；
- 网络分区时所有节点看到相同锁状态；
- 锁内操作不会重复执行。

因此支付、库存、订单等关键流程应以数据库唯一约束、状态机、幂等 Key、版本号和业务补偿为最终防线。

### 14.4 Redlock 的讨论方式

Redlock 尝试在多个独立 Redis 节点上获取同一锁，并用多数派和剩余有效时间判断成功。面试中不要简单说“Redlock 一定安全”或“一定没用”，应说明：它改善了单实例故障场景，但正确性取决于时钟、网络延迟、租约模型和业务资源；对强一致临界资源，fencing token 和具备共识语义的协调系统通常更容易论证。

### 14.5 可重入锁

Redis `SET NX` 本身不可重入。要支持同一线程/请求重复加锁，需要保存 owner token 和计数，并在 Lua 中完成“同 owner 则计数加一、释放时减一”。同时要有明确线程标识、过期策略和异常清理，不建议手写未经充分测试的锁框架。

## 15. 延迟队列、消息队列与可靠消费

### 15.0 学习前置：消息投递语义和状态机

消息系统的核心不是“把任务放进 Redis”，而是回答消息经历了哪些状态：待处理、处理中、成功、重试、死信。还要区分投递语义：

- 至多一次：可能丢，但不重复；
- 至少一次：不轻易丢，但可能重复；
- 恰好一次：通常需要消息系统和业务幂等共同构建，不能只靠一个 ACK 命令。

为什么要先理解这些？因为消费者在“业务执行成功”和“确认消息”之间崩溃时，重启后通常会再次收到消息；如果先确认再执行，执行失败又可能丢消息。正确做法不是幻想没有故障，而是把消费设计成可重试、可去重、可观测。

延迟队列还需要明确时间语义：是“最早可执行时间”，还是“必须在某时刻执行”；任务延迟时是否允许重复；超时任务如何追回；任务失败是否指数退避。先把状态机画出来，再选择 List、ZSet、Stream 或专业 MQ。

### 15.1 用 ZSet 实现简单延迟队列

生产者：

```redis
ZADD delay:email 1760956800 job:1001
```

消费者周期性获取到期任务。取出和删除必须防并发：

```lua
local items = redis.call('ZRANGEBYSCORE', KEYS[1], '-inf', ARGV[1], 'LIMIT', 0, ARGV[2])
for _, item in ipairs(items) do
  redis.call('ZREM', KEYS[1], item)
end
return items
```

更可靠的流程是先原子移动到 processing 集合，再执行；成功后删除 processing；超时未完成则重试。任务必须带唯一 ID，业务处理必须幂等。

### 15.2 List 队列的可靠消费

`RPOPLPUSH ready processing` 可以让消息从待处理队列转入处理中队列；成功后从 processing 删除。消费者崩溃时，恢复任务需要扫描 processing 并根据时间重新投递。这个方案需要自己实现可见性超时、重试次数、死信队列和监控。

### 15.3 Stream 消费组的可靠性

Stream + Consumer Group 已经提供 Pending、ACK 和接管能力，但业务仍要处理：

- ACK 前失败的消息重试；
- 多次失败进入死信流；
- 消费幂等和去重；
- 消费组积压、消费者失联和消息保留期限；
- 业务处理成功但 ACK 失败造成重复投递。

这体现了消息系统的基本事实：通常是至少一次投递，而不是天然恰好一次；“恰好一次”往往需要业务幂等和事务边界共同实现。

## 16. Redis 性能、容量与生产参数

### 16.0 学习前置：先建立容量模型，再谈调参

性能优化前要区分四个指标：

- **吞吐**：每秒处理多少请求；
- **延迟**：单次请求花费多久，尤其是 P99/P999；
- **容量**：能放多少数据和连接；
- **可靠性**：故障时是否丢数据、是否能恢复。

它们经常相互牵制。例如增大 Pipeline 可以提高吞吐，但也可能增大单批响应和尾延迟；开启更严格的 fsync 可能提高持久化可靠性，却增加磁盘压力；缓存 TTL 变长能提高命中率，却占用更多内存。

为什么先建立容量模型？因为“调大 maxmemory”“增加连接数”“打开 IO 线程”都不是通用答案。先统计 Key 数、Value 大小、读写比例、命令复杂度、网络带宽和峰值倍率，再决定瓶颈在 CPU、网络、内存、磁盘还是后端回源。

### 16.1 估算容量

不要只按 Value 字节数估算。总内存至少包括：Key、Value、对象头、哈希表/跳表节点、过期字典、复制缓冲区、客户端输出缓冲区、AOF/RDB 重写额外开销和碎片。

粗略流程：

1. 统计 Key 数、平均 Key 长度、平均 Value 长度；
2. 区分各数据结构和大 Key 分布；
3. 加上对象和结构开销；
4. 留出复制、fork、碎片和扩容余量；
5. 用压测实例和 `MEMORY USAGE` 校准，不要只相信公式。

### 16.2 连接池与超时

客户端应使用连接池，避免每次请求建立 TCP 连接。必须设置连接超时、命令超时、重试次数和最大连接数。重试不是越多越好：Redis 变慢时，盲目重试会形成请求风暴。

Node.js 示例：

```ts
const redis = createClient({
  url: process.env.REDIS_URL,
  socket: {
    connectTimeout: 1000,
    reconnectStrategy: (retries) => Math.min(retries * 100, 3000),
  },
});
```

重试必须区分读命令和写命令。写命令是否可重试取决于幂等性；`INCR`、追加消息等操作如果客户端不确定服务端是否已执行，重试可能造成重复。

### 16.3 批量操作的正确姿势

- 多次独立读写：Pipeline 减少 RTT；
- 多 Key 原子校验：Lua 或事务；
- 大批量删除：SCAN + 分批 UNLINK；
- Cluster 批量操作：按 slot 分组，避免大量 MOVED；
- 大结果集：分页、游标、流式处理，禁止一次性返回全部。

### 16.4 监控指标

至少关注：

- QPS、命令耗时、P50/P95/P99；
- `used_memory`、RSS、碎片、内存峰值；
- Key 过期、淘汰、命中率和回源率；
- blocked clients、connected clients、拒绝连接；
- 主从复制延迟、断线次数、复制积压；
- AOF rewrite、RDB fork、持久化失败；
- Cluster slot 状态、热点节点、大 Key、慢命令；
- 应用侧超时、重试、熔断、缓存穿透和数据库连接池。

命中率高不代表系统健康：如果热点 Key 读命中但网络发送了几 MB，仍可能造成高延迟；命中率低也不一定是问题，短 TTL 和高变动业务本来就可能低命中。

### 16.5 慢查询与延迟监控

`SLOWLOG` 记录执行时间超过阈值的命令，但它通常不包含网络排队、客户端处理和输出传输时间。因此应同时结合应用端耗时、Redis 延迟监控和网络指标。慢查询采样不要设置成导致额外开销的高频全量记录。

## 17. 安全、运维、监控与故障排查

### 17.0 学习前置：把 Redis 当作生产基础设施

Redis 一旦承载登录态、限流、队列或分布式锁，就不再只是开发机上的一个依赖，而是生产基础设施。基础设施需要四类能力：

1. **安全**：谁能连、谁能执行什么、数据是否泄露；
2. **可观测**：发生慢、错、丢、满时能否看见；
3. **可恢复**：备份是否存在，恢复是否演练过；
4. **可变更**：升级、迁移、扩容能否回滚。

为什么新人要提前学习这些？因为生产事故往往不是命令写错，而是无认证公网暴露、备份无法恢复、连接池重试风暴、慢命令没有告警或扩容迁移没有容量余量。把监控和恢复放到设计阶段，排障时才不会只能“登录机器看看”。

### 17.1 安全基线

- Redis 不要直接暴露公网；使用内网、ACL、TLS 和网络策略；
- 关闭或限制高风险命令，尤其是生产环境的配置、调试和批量危险命令；
- 认证不等于授权，按应用分配最小 ACL 权限；
- 敏感数据加密或脱敏，避免把 Token、密码明文长期放入缓存；
- 对 Lua、脚本和客户端依赖做版本管理；
- 备份文件、AOF、RDB 的访问权限要纳入安全审计。

### 17.2 故障排查顺序

遇到 Redis 延迟升高时，建议按层排查：

1. **应用层**：请求量是否突增、连接池是否耗尽、是否出现重试风暴；
2. **Redis 命令层**：慢命令、命令复杂度、是否出现大范围返回；
3. **数据层**：大 Key、热 Key、内存淘汰、过期集中；
4. **资源层**：CPU、内存、RSS、网络带宽、磁盘、fork；
5. **复制/集群层**：主从延迟、重连、槽位迁移、节点负载不均；
6. **变更层**：发布、配置、扩容、脚本或数据迁移是否刚发生。

不要看到 Redis QPS 高就直接扩容。先确认是 CPU 饱和、网络饱和、单 Key 热点、慢命令还是数据库回源造成的连锁反应。

### 17.3 常见命令

```redis
INFO memory
INFO stats
INFO replication
INFO commandstats
SLOWLOG GET 20
MEMORY USAGE user:1
MEMORY DOCTOR
SCAN 0 MATCH user:* COUNT 1000
CLIENT LIST
LATENCY DOCTOR
```

线上执行诊断命令也要考虑返回量和权限；不要用 `KEYS *`、无界 `HGETALL` 进行“快速排查”。

### 17.4 备份与恢复演练

“有 RDB 文件”不等于“能恢复”。应定期验证：备份是否完整、是否可读取、恢复耗时、数据丢失窗口、权限和密钥、恢复后应用兼容性。灾备要覆盖误删、错误脚本、主机损坏、机房故障和密钥泄露，而不是只测试进程重启。

## 18. 大厂综合场景题与回答框架

### 18.0 学习前置：从单点技术回答升级为系统设计回答

大厂场景题通常不是问“某个命令怎么用”，而是看你能否从业务目标推导技术方案。推荐使用下面的顺序：

1. **澄清目标**：QPS、延迟、数据量、可接受丢失、是否允许最终一致；
2. **定义数据模型**：Key、类型、TTL、分片方式、版本；
3. **说明主流程**：读、写、消费、失败和重试；
4. **补充异常路径**：缓存未命中、Redis 故障、数据库超时、重复请求；
5. **补充治理能力**：监控、告警、限流、降级、备份、恢复；
6. **说明边界**：什么情况下 Redis 不应该承担最终一致性或权威存储。

为什么要这样答？因为一个孤立的“用 ZSet”“加分布式锁”不能证明方案可用。资深工程师需要同时考虑正确性、性能、可用性、可运维性和成本。新人可以把每道场景题都画成“正常链路 + 异常链路 + 数据恢复链路”三张图，再组织语言。

### 18.1 设计一个商品详情缓存

回答框架：

1. Key：`product:{id}:detail`，Value 使用版本化 JSON；
2. 读：Redis 命中直接返回，未命中查 DB 并设置带抖动 TTL；
3. 写：先更新 DB，再删除缓存，删除失败通过消息重试/补偿；
4. 穿透：参数校验、空值缓存、布隆过滤器；
5. 击穿：热点 Key 互斥回源或逻辑过期；
6. 雪崩：TTL 抖动、限流、降级和多级缓存；
7. 监控：命中率、回源率、P99、大 Key、热 Key、删除失败；
8. 一致性：先确认业务允许的旧数据时间，再选择方案。

### 18.2 设计秒杀库存

库存扣减不能用“GET 判断 + DECR”两条普通命令。可以用 Lua 保证判断和扣减原子：

```lua
local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
if stock <= 0 then return -1 end
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return -2 end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1
```

然后异步创建订单，使用用户/商品幂等键和数据库唯一约束兜底。需要考虑库存初始化、Redis 故障、消息丢失、超卖校验、订单取消回补和热点商品分片。Redis 的扣减成功不能直接等价于订单最终成功。

### 18.3 设计排行榜

用 ZSet 保存 `leaderboard:{season}`，member 是用户 ID，score 是分数：

```redis
ZINCRBY leaderboard:{season} 10 user:1
ZREVRANK leaderboard:{season} user:1
ZREVRANGE leaderboard:{season} 0 99 WITHSCORES
```

追问点：分数相同的排序规则、分页期间数据变化、赛季切换、榜单过大、写热点、持久化和最终落库。若需要复杂规则或历史分析，可以 Redis 做实时榜，数据库/数仓做长期事实。

### 18.4 设计分布式锁防止重复任务

先用 `SET NX PX` 获取带唯一 token 的锁，再用 Lua 校验 token 释放。任务超过 TTL 时续期，任务本身设计幂等；关键资源增加 fencing token 或版本校验。最后说明 Redis 锁是协调机制，不是业务事务，数据库唯一约束和状态机仍然要存在。

### 18.5 Redis 挂了怎么办

先区分 Redis 的角色：

- 纯缓存：快速失败、降级、限流，允许回源但要保护数据库；
- 计数/排行榜：接受短暂不可用或异步补偿，避免在高峰无限重试；
- 锁/队列：需要评估重复执行、消息积压、锁失效和业务恢复；
- 权威状态：应有数据库/日志备份，不能把 Redis 作为唯一事实来源。

技术措施包括主从 + Sentinel/Cluster、客户端重连、超时、熔断、备份、恢复演练和容量余量；最重要的是按业务重要性设计降级，而不是只说“部署集群”。

### 18.6 讲一个 Redis 延迟突然升高的排查过程

可以这样组织：先看应用 QPS、超时和重试；再看 Redis P99、慢日志和命令统计；如果存在 `KEYS`、大范围 `HGETALL` 或大 Key 删除，优先止损；并行检查内存淘汰、fork、AOF rewrite、网络带宽和主从延迟；最后定位到具体 Key/接口/发布变更，分批修复并补充监控和压测。这个回答比“扩容 Redis”更能体现生产经验。

## 19. 高频命令速查与复习路线

### 19.0 学习前置：如何把八股变成可迁移能力

复习命令前先记住：面试考的不是能否背出 30 个命令，而是能否从一个新需求推导出正确的 Key、类型、原子边界和故障处理。

建议建立一张个人错题表，每道题记录四列：

| 记录项 | 要写什么 |
| --- | --- |
| 业务目标 | 例如“防止同一订单重复处理” |
| 最小数据模型 | Key、类型、字段、TTL |
| 失败场景 | 超时、重试、宕机、主从延迟 |
| 兜底措施 | 幂等、唯一约束、补偿、监控 |

这样复习的原因是，真实面试通常会改变题目背景：把“库存扣减”换成“优惠券领取”，把“排行榜”换成“延迟任务”。如果只记模板，换一个业务就不会答；如果理解前置知识和不变量，就能迁移。

### 19.1 命令速查

| 目标 | 常用命令 | 注意 |
| --- | --- | --- |
| 基础读写 | `GET`、`SET`、`MGET`、`MSET` | 关注 Value 大小和超时 |
| 原子计数 | `INCR`、`INCRBY` | 不要用 GET + SET 替代 |
| Hash | `HSET`、`HGET`、`HINCRBY`、`HSCAN` | 避免无界 `HGETALL` |
| List | `LPUSH`、`RPOP`、`BLPOP`、`LRANGE` | 消费可靠性需额外设计 |
| Set | `SADD`、`SISMEMBER`、`SSCAN` | 大集合不要 `SMEMBERS` |
| ZSet | `ZADD`、`ZINCRBY`、`ZRANGE`、`ZRANGEBYSCORE` | 范围结果要分页 |
| 过期 | `EXPIRE`、`PEXPIRE`、`TTL` | TTL 是 Key 级别 |
| 批量/原子 | Pipeline、`MULTI/EXEC`、Lua | 分清降 RTT 和原子性 |
| 消息 | `XADD`、`XREADGROUP`、`XACK` | 处理 PEL、重试、死信 |
| 运维 | `INFO`、`SLOWLOG`、`SCAN`、`MEMORY USAGE` | 线上谨慎控制返回量 |

### 19.2 三轮复习法

第一轮，能说清五大类型、过期淘汰、RDB/AOF、主从哨兵 Cluster。

第二轮，能手写 Cache Aside、缓存穿透/击穿/雪崩、Lua 扣库存、分布式锁释放脚本。

第三轮，按场景回答：数据丢失怎么办、Redis 挂了怎么办、热点和大 Key 怎么治理、如何证明一致性、如何做容量和监控设计。

### 19.3 最后背诵的十句话

1. Redis 快不只是因为单线程，还因为内存、专用数据结构和 IO 多路复用。
2. 单条命令原子，不代表多条命令组合原子。
3. Pipeline 减少 RTT，不自动提供事务隔离。
4. Redis 事务没有传统数据库那样的自动回滚。
5. 过期删除和内存淘汰是两个概念。
6. `KEYS` 可能阻塞线上实例，渐进遍历用 `SCAN`。
7. 主从复制通常是异步的，读副本可能读到旧数据。
8. Sentinel 解决高可用，不解决分片；Cluster 解决分片，也带来跨 slot 限制。
9. 分布式锁必须有唯一 token、带 TTL、校验所有权释放，并考虑续期和幂等。
10. Redis 是加速和协调组件，关键业务的最终正确性仍要由数据库约束、状态机、幂等和补偿共同保证。
